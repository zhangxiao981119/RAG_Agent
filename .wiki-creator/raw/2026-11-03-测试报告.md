### 3.3 项 3：`purge_derived` 事务正确性 —— 真库回滚实验

**两个写入点都覆盖**：`grep -n "delete(Chunk)"` 全仓只有 2 处（`parse_job.py:191` 普通路径、
`parse_job.py:499` 扫描件聚合路径），两处的 `purge_derived` 分别在 188 / 498 行，均在
`delete(Chunk)` **之前**、且在同一个 `async with SessionLocal()` 块内。
python 代码里 `upsert_subgraph` 的调用点只有 `graph_job.py:108`（arq 与脚本共用同一函数）。

**「写入后提交前抛异常会不会残留孤儿」——用真库做实验（不是 AST 推断）**：

```
=== C. purge_derived 事务原子性（真实 PG）===
   初始：mentions=3, graph_status=done
PASS  C0 初始状态：done + 有提及
   purge_derived 返回删除关系数=2
   回滚后：mentions=3, graph_status=done
PASS  C1 提交前异常 → 图数据与状态**整体回滚**，不留孤儿  mentions 3->3, status=done
PASS  C2 同一事务证据：回滚后旧 chunks 仍在（purge 与 chunk 写入同事务）  chunks=1
   提交后：mentions=0, status=pending, model=None
PASS  C3 提交路径：提及清零 + graph_status=pending + 口径列置空
   kb 内实体 1，其中孤儿 0
PASS  C4 delete_by_document 清掉了无引用实体（孤儿=0）  entities=1, orphans=0
```

实验构造：`s = Session()` → `purge_derived(s)` → `DELETE chunks` → `INSERT 新 chunk` → `flush` →
`raise`。异常离开 `async with` → 会话关闭回滚。断言：mentions 从 3 回到 3（**不是 0**）、
`graph_status` 仍是 `done`（**没有被改成 pending**）、旧 chunk 仍在。
这证明 `purge_derived` 与 chunks 写入**确实共享同一个事务**（若 `purge_derived` 内部自行
`commit()`，回滚后 mentions 会是 0）。随后单独验证提交路径：mentions→0、`graph_status→pending`、
两个口径列→NULL、孤儿实体被清。

**结论：不会残留孤儿。** 唯一残留风险不在事务，而在「关图期间重解析」这个跨状态场景（见 P2-6）。

### 3.4 项 4：口径 fail-closed —— 最危险的静默项，实测通过

```
PASS  B0 旧口径（old-model/gprompt-v0）的提及被当前口径完全排除  got=0
   旧口径 hop 分布: [('36aab3d0', 2, 2)]
PASS  B1 反向 fail-closed：按旧口径查只走旧口径的边（hop=2），不把新口径的 hop=1 混进来  got=[('36aab3d0', 2)]
PASS  B2 只改 prompt_version 也会把全部行排除（口径两列都生效）  got=0
PASS  E2 空 GRAPH_EXTRACTOR_MODEL 解析为 llm_model 的实际值（不落空串）
   GRAPH_EXTRACTOR_MODEL='' LLM_MODEL='deepseek-v4-flash' -> 口径模型='deepseek-v4-flash'
```

- 检索 SQL 的 WHERE 里，**关系边与提及边各带一次** `extractor_model = :x AND prompt_version = :y`
  （`postgres_store.py:351-352`、`368-369`），无 `OR prompt_version IS NULL` 之类兜底。
- 默认值路径不退化成「匹配所有口径」：空串先被 `graph_profile.current_graph_profile()` 解析成

### 3.5 项 5：权限不泄漏 —— 真库越权矩阵 23/23 PASS

`neighbors()` 的取片 SQL 用 `from app.services.retrieve import _WHERE_BASE` **导入同一字符串对象**
（`postgres_store.py:334-371`），不是复制一份；四闸门 + `is_latest` 全在：

```
WHERE c.tenant_id = :tenant_id
  AND c.is_latest = true
  AND c.level_rank <= :clearance
  AND c.kb_id = ANY(:authorized_kb_ids)
  AND NOT (c.deny_subjects && :user_subjects)
  AND c.acl_tags && :user_subjects
```

参数全部走 bind（`params = {…}` + `:name`），**无字符串拼接用户输入**；唯一的 f-string 插值是
模块常量 `_WHERE_BASE`。递归 CTE 在边扩展侧另加了 `tenant_id / kb_id = ANY(authorized)` 与
「同一路径不重复经过同一实体」的防环条件。结果集 JOIN 回 `chunks` 后才返回，两跳不会绕过闸门。

真库实测（构造 6 类文档 + 7 条提及 + 2 条不同口径的边）：


### P1（会让功能失效或极难排查）

**P1-1 dev `docker-compose.yml` 未注入 10 个新环境变量 → 开发/验收栈开不了图能力**

- 位置：`code/docker-compose.yml`（`api` 段 `environment:` 约 60-95 行、`worker` 段同构处）
- 证据（两次独立确认）：

  ```
  $ docker compose -f docker-compose.yml config | grep -cE "GRAPH_ENABLED|GRAPH_STORE_BACKEND|WIKI_ENABLED|WIKI_SCOPE"
  0                       ← dev：一个都没有
  $ docker compose -f docker-compose.prod.yml --env-file .env.prod.example config | grep -cE "GRAPH_ENABLED|WIKI_ENABLED"
  4                       ← prod：api + worker 各 2（含新增的 LLM_* 3 行，已在 diff 中确认）
  ```
- dev compose 是**显式列出** `environment:`（没有 `env_file:`），所以 `.env` 里写
  `GRAPH_ENABLED=true` 不会进容器。后果：在 dev 栈里按 `.env.example` 的新注释开启能力，
  容器内仍是 `GRAPH_ENABLED=false` —— 正是本方案要消灭的「配了却不生效」。
- 建议：在 `api` 与 `worker` 两段的 `environment:` 各补 10 行，取值方式与 prod 一致
  （`GRAPH_ENABLED: ${GRAPH_ENABLED:-false}` …）。

**P1-2 补建脚本把 `GraphExtractSkip` 记成 `failed`（arq 路径记 `skipped`）**

- 位置：`code/apps/api/scripts/backfill_graph.py:184-193`
- **真库复现（不需要 LLM）**：构造一篇 `status='indexed'` 但零 chunks 的文档，`extract_document`
  按设计抛 `GraphExtractSkip`（「明确跳过」），然后直接调 `scripts.backfill_graph.main()`：

  ```
  seeded empty-indexed doc: 9b7180a3-a144-4b08-81d5-d938e5514f27
  待处理 1 篇（模式=all）
    [1/1] FAILED 9b7180a3-… empty.txt: GraphExtractSkip: 文档无已索引分片（内容为空或尚未解析）
  完成：成功 0 · 跳过 0 · 失败 1
  脚本退出码 = 1
  最终 graph_status = 'failed'   （按设计语义应为 'skipped'）

  $ python -m scripts.backfill_graph --check
  失败(failed)   : 1
  跳过(skipped)  : 0
  未就绪合计     : 1
  CHECK_RC=1
  ```
- 后果：① 状态语义丢失（「明确不该抽」被记成「抽失败了」），横幅与 `--check` 把它算进
  「失败」，运维会去查 LLM 而真实原因是「文档超 200 片」；② `_base_select('all')` 只排除
  `skipped`（`backfill_graph.py:71-74`），所以这批文档**每次 `--all` 都会被重新选中**，
  反复刷同样的失败日志。
- 建议：在 `_run` 的循环里加 `except GraphExtractSkip: 置 skipped + skipped += 1 + continue`，
  与 `graph_job.py:169-181` 对齐（最好是抽一个共用函数）。
