## 1. 先排重后裁剪（dedup-before-trim）

- 落点：`apps/api/app/services/graph/recall.py` 的 `recall_by_graph(... exclude_chunk_ids=...)`。
- 现象：图扩展得到的一跳邻居里，权重最高的那批往往就是主检索已经召回的同一批文档片。
- 若「先裁剪、后去重」，这些重复片会占满 `GRAPH_RECALL_MAX_CHUNKS` 名额，真正来自图结构、
  主检索没召回的新片被截断——旁路（side channel）名存实亡。
- 正确顺序：遍历邻居时 `if neighbor.chunk_id in exclude: continue` 必须在预算累加之前，
  重复片只用于统计 `graph_covered`，不占名额。
- `graph_covered = sum(1 for n in neighbors if n.chunk_id in exclude)`，在预算裁剪前统计，
  是 v1.2 契约里「图到底补了多少新东西」的对照基准。
- 关联：旁路召回（side-channel-recall）的具体实现纪律；图召回 v1.2 契约口径（graph-recall-v12-contract）。

## 2. 独立预算扩展（independent-budget-expansion）

- 落点：`apps/api/app/services/keyword_text.py` 的 `build_ilike_pattern(..., extra_terms=...)` 与
  `build_fts_query(..., extra_index_tokens=...)`。
- 真实 bug（C4/F6）：`keyword_text.py` 的 `[:FTS_QUERY_MAX_TERMS]` 把主查询窗口（向量 / tsquery（全文检索）
  / ILIKE（大小写不敏感匹配）三路共用的核心词元）和 lexicon（词表）别名放进同一列表后截断。
  主查询窗口达上限时，别名被**静默吞掉**，主召回路径悄然退化（核心 206 条 `0/206`、全源并集 `0/233`）。
- 修复：别名走独立预算 `LEXICON_FTS_ALIAS_MAX_TERMS`；wiki 导航术语走独立预算
  `WIKI_NAV_MAX_FTS_TOKENS`，上限 `FTS_QUERY_MAX_TERMS + WIKI_NAV_MAX_FTS_TOKENS`。
- 主 `ilike_terms` / `fts` 窗口冻结，扩展词元用 keyword-only 默认参 `extra_terms` / `extra_index_tokens`
  承载，禁止 append 后截断主词元。
- 关闭态必须零成本：`extra_*` 为空时 `build_ilike_pattern` / `build_fts_query` 逐字节等价于不传扩展，
  Golden 快照 `tests/retrieve/golden_wiki_nav_baseline.json` 钉死。
- 量化报告：`02-design/C4-别名静默截断影响面量化.md`（217 条精确占比实测 `0/217 = 0.00%`）。

## 3. 图召回 v1.2 契约口径（graph-recall-v12-contract）

- 落点：`apps/api/app/services/retrieve/__init__.py` 的 `path_stats`；裁决见
  `02-design/架构设计文档.md` §9.8。
- v1.2 定义（交付上下文口径）：
  - `graph_unique = len(graph_recall_chunks)`：最终进入响应上下文的图召回片数（**不是**候选池大小）。
  - `graph_covered = len(neighbor_ids & retrieved_ids)`：图邻居集合与主检索命中片集合的交集，预算裁剪前统计。
  - `graph_degraded_reason`：图召回 fail-open（失败时开放降级）时贯穿响应 / 拒答 / SSE（服务端推送事件）观测 /
    评测聚合的原因字段。
- v1.1 用「三路候选池」做分母，分母天然含已被主检索命中的片，导致 `graph_unique` 结构性恒 0。
  真库实测（dev 库）纠正：按交付上下文口径 `graph_unique` 才能正确反映旁路实际补入的片数。
- 口径是契约：设计 / 代码 / 测试 / 评测报告必须统一按 v1.2，不能各写各的分母。

## 4. 真库探针与宿主 skip 假绿（realdb-probe-vs-skip-green）

- 落点：`apps/api/tests/wiki/test_nav_acl.py`（真库 ACL（访问控制）探针）；报告见
  `04-test/测试报告-第4步wiki导航.md` §0.7 与 P1-1 章节。
- PGlite 是 WASM（网页汇编）PostgreSQL，只投影 5 张表的最小 schema，可做部分行为级验证，
  **但不是** 26 迁移真实 schema，不能把 PGlite 的 passed 写成「26 迁移真实 schema 全链通过」。
- 真 bug（P1-1）：迁移 0011 把 `chunks.embedding_model` / `embedding_text_version` / `chunker_version`
  置 `NOT NULL`（非空约束）且无 `server_default`（服务端默认值）；`_seed` 的 `INSERT` 没给这三列。
  PGlite 5 表投影没有这三列，宿主缺 DB 时 9 条真库探针 `pytest.skip`，形成「全绿」假象；
  真库探针实跑才暴露 9 FAILED（`NotNullViolationError`）。
- 对抗性反证：故意删回这 3 列后，宿主「全绿、exit=0」而真库「9 FAILED、exit=1」——
  证明宿主 skip 是假绿，真库探针才是真验证。
- 结论形式：验证报告必须写明跑的是 PGlite 还是真库、skip 了几条、对抗性实测是否通过。

## 5. statement_timeout 事务级三段式还原（statement-timeout-three-phase）

- 落点：`apps/api/app/services/graph/recall.py` 与 `apps/api/app/services/wiki/navigate.py`
  的 `_read_statement_timeout` / `_restore_statement_timeout`。
- `set_config('statement_timeout', :ms, true)` 的 `true`（local）是**会话级事务内有效**，不是单语句；
  作用域是整个事务。图召回 / wiki 导航设了超时后，同一事务还要跑表格回捞、章节补全，若不还原，
  后续查询也受超时约束，轻则误超时、重则拖垮整事务。
- 三段式：①`_read_statement_timeout(session)` 读出调用前原值；② 目标 SQL 前
  `set_config(..., :ms, true)`；③ 成功后 `set_config(..., :previous, true)` 还原为调用前读到的值
  （**不是**硬编码 `'0'`）；一旦异常则 rollback（回滚）整事务，不再单独发还原 SQL（local 改动随事务消失）。
- 硬编码 `'0'` 是错的：调用前可能本来就不是 `'0'`（上游设了某值），硬写会篡改上游语义。
  真库 P3 复核过 `previous='1234ms' → after='1234ms'` 一致。
- wiki 导航 SQL 比图召回更靠前地设超时，同样吃这条纪律。
