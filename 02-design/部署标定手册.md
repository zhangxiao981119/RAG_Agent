## 1. 部署前必须实测的参数（每项 6 个字段：造集 / 样本量 / 指标 / 判据 / 留档 / 不达标）

### 1.1 M-1 `RELEVANCE_THRESHOLD_VECTOR`（现 0.50，`decisions.py:34`）

| 字段 | 内容 |
|---|---|
| **① 测试集怎么造** | 正例：从**本部署已入库的文档**逐篇出题，每条必须能指着某一段回答，JSON 形如 `{"question":"…","answerable":true,"expect":["文件名.pdf"]}`；负例：与本库话题**相邻但无答案**的问题（库里有「部署文档」就问「GPU 显存型号」），JSON 只有 `question` + `"answerable":false`。负例 MUST 人工确认「库中确实无答案」，**不许用分数筛负例**——用分数筛等于提前决定了两组分布 |
| **② 样本量下限** | **50 条（正负合计）**。依据只有两条：脚本在 `n<50` 时打印 `[!] 样本仅 N 条`（`calibrate_threshold.py:180-181`）；`decisions.py:32` 记录「30 条样本分离度仅 0.025，偏窄」。**这是经验下限，脚本不做置信区间，没有统计理论依据** |
| **③ 指标怎么算** | 设阈值 t，`拒答正确率 = #{不可答且 s<t} / #{不可答}`，`漏答率 = #{可答且 s<t} / #{可答}`，`F1 = 2·拒答正确率·(1−漏答率) / (拒答正确率 + 1−漏答率)`（`calibrate_threshold.py:146-155`）；`分离度 = min(可答 s) − max(不可答 s)`（`:193`），s = top1 的 `final_score` |
| **④ 判定阈值** | 四条同时满足才算过：样本 ≥50；打印的「主导口径」= `vector`（`:173-179`）；分离度 **≥0.05**（`MIN_SEPARATION`，`:39`）；建议值取 F1 最高点。灰区：`0 ≤ 分离度 < 0.05` → **不许上线**，扩样本到 100 再测；`分离度 < 0` → 两组重叠，改检索或换语料，**不许靠调阈值掩盖** |
| **⑤ 记录模板** | `\| 日期 \| 样本数 \| 正/负 \| 口径 \| 分离度 \| 选定阈值 \| F1 \| 拒答正确率 \| 漏答率 \| 语料批次 \|`；示例行（历史记录，`decisions.py:29-33`）：`\| 2026-09-25 \| 30 \| 20/10 \| vector \| 0.025 \| 0.50 \| 1.000 \| 100% \| 0% \| 未登记 \|` |
| **⑥ 不达标怎么办** | 分离度 <0.05：先扩样本（评估集不够时结论不稳），仍不达标则**说明这批语料下向量分不开可答/不可答**——此时不要动阈值，改语料切分或换 embedding 模型（换模型要全量重算，见 §3）；分离度 <0 且扩样后依旧：该环境不适合把 top1 分数当拒答闸门，须把结论上报平台方，**不许**用 0.30 之类的低阈值「跑通再说」 |

```bash
# 1) 造集：在宿主机写 /tmp/cases.json（格式见上），先拷进容器
docker compose -p kagent cp /tmp/cases.json api:/tmp/cases.json
docker compose -p kagent exec -T api python -m scripts.precheck_cases \
    --in /tmp/cases.json --out /tmp/pre.json --thresh 0
# 2) 导入（--keep-failed 保留负例；负例在 thresh=0 下必然标 fail，这是预期）
docker compose -p kagent exec -T api python -m scripts.import_eval_cases \
    --in /tmp/pre.json --tag <批次>
# 3) 标定（脚本内部把两个阈值临时置 0 采集，见 :42-47/:59-60）
docker compose -p kagent exec -T api python -m scripts.calibrate_threshold --mode vector
```

> **必须避开的循环论证**：`precheck_cases.py` 默认 `--thresh` 是 `0.50`（`:124`），且按 `score >= thresh` 判可答（`:89`）。用默认值预检 = **评估集已被当前阈值截断过一遍**，再标定必然收敛回 0.50 —— 与 `calibrate_threshold.py:17-21` 自己写的循环论证陷阱同类。

### 1.2 M-2 `RELEVANCE_THRESHOLD_RERANK`（现 0.50，`decisions.py:37`，自述未标定）

**脚本能力先说清**（读码结论，不要按 docstring 猜）：`--mode` 只决定**建议值写到哪个常量**
（`calibrate_threshold.py:209-212`），**不改变采集口径**；采集永远跑线上真实链路（`:104-120`）。
所以「标定 rerank 口径」= 先让线上真的处于 rerank 口径，再跑同一脚本。脚本**没有**「强制打开重排后采集」的开关。

| 字段 | 内容 |
|---|---|
| **① 测试集怎么造** | 与 M-1 **必须是同一套**（同一批题、同一批负例）。换一套题两个阈值就不可比 |
| **② 样本量下限** | 同 50（同一条脚本告警线；经验下限，无理论依据） |
| **③ 指标怎么算** | 同 M-1 的三个式子，但 s 必须来自 rerank 分。前置校验：每条样本的 `score_source` 必须全为 `rerank`（字段见 `services/retrieve/base.py:49-58`），出现 `vector` 即样本无效 |
| **④ 判定阈值** | 除 M-1 四条外**多一条**：脚本打印的「主导口径」必须是 `rerank`。出现混口径告警（`:124-132`）→ 本次作废重跑 |
| **⑤ 记录模板** | M-1 模板 + 两列：`重排模型`、`8 条重排耗时(s)`。示例（数值留空由部署者填）：`\| 2026-11-20 \| <样本数> \| <正>/<负> \| rerank \| <分离度> \| <阈值> \| <F1> \| <拒答率> \| <漏答率> \| bge-reranker-v2-m3 \| <实测耗时> \|` |
| **⑥ 不达标怎么办** | 8 条重排耗时 ≥3.0s（超时线 `settings.py:130`）→ 该环境**不具备**重排能力：关掉 `RERANK_ENABLED`，并**禁止**任何场景配置 `relevance_threshold_rerank`。**不要**调大 `rerank_timeout_seconds`——那只是把「白等 3s」变成「白等 10s」，降级结果一样 |

```bash
# 前置：必须是 GPU（或实测 8 条 <3s 的算力）。CPU 上 8 条 10.5s / 50 条 66s（settings.py:85-86）
#       → 每次都超时降级 → 采到的全是向量分，脚本却把建议写到 rerank 常量上（跑得通、结果错）
# 1) 打开重排并重启，确认口径真的生效 —— 看指标，不看响应体
#    （集成接口的 meta 只有 4 个键，不含 score_source，见 integrations.py:227-239）
#    RERANK_ENABLED=true → docker compose -p kagent up -d --build api
curl -s http://localhost:8000/metrics | grep 'rag_rerank_duration_seconds_count'
#    必须出现 mode="on" 且计数在增长；只有 mode="degraded" 说明每次都在超时降级
# 2) 跑同一脚本，只换 mode（此时采集才是 rerank 分）
docker compose -p kagent exec -T api python -m scripts.calibrate_threshold --mode rerank
# 3) 必须先核对输出里的「主导口径: rerank」，再去抄建议值
```

### 1.3 M-3 `RECALL_TOP_K_MAX`（现 200，`policy_spec.py:40`，**站位值**）

| 字段 | 内容 |
|---|---|
| **① 测试集怎么造** | 不需要评估集，需要**有内容的库 + 固定问题池**：直接用 `loadtest_chat.py` 内置的 8 条问题（`:44-52`）。每档 `recall_top_k` 跑一次，同一 KB、同一机器、同一时刻（避免缓存/负载漂移） |
| **② 样本量下限** | 每档 ≥**200 请求**：`10 并发 × 300s`，按单请求 3~5s 计可得 600~1000 个样本，留足余量。p95 是尾部指标，样本 <100 时它退化成「最大的那几个值」，不具代表性。**经验下限，无理论依据** |
| **③ 指标怎么算** | `retrieve_ms` = 发出请求 → `citations` 事件（含检索+组装，不含生成，`loadtest_chat.py:9-12`）；`增幅 = (p95_k − p95_50) / p95_50`。失败率单列，**不计入**延迟（失败请求的延迟没有意义） |
| **④ 判定阈值** | 功能下限：任意场景 `recall_top_k ≥ TOP_K_RERANK(=8)`，否则重排取不满 8 条（S-2）。**注意：这条目前没有任何代码校验**（`policy_spec.py` 只保证 `1..200`，`grep TOP_K_RERANK services/scenario/` 仅命中 `final_top_n` 的 max），Step 3 接线时才加。性能上限：取 `增幅 ≤ 50%` 的最大 k（1.5×，取自框架稿 §3A.3.2 `:300`——**该值本身是占位值**，`:304` 已声明）。灰区 `(20%, 50%]` → 取小一档 |
| **⑤ 记录模板** | `\| 日期 \| top_k \| 请求数 \| 失败 \| p50 \| p95 \| 增幅 \| 判定 \|` ×4 档（50/100/150/200） |
| **⑥ 不达标怎么办** | `k=50` 的 p95 就已超预算 → 问题不在 k，在 DB/索引，先查慢查询；`k=200` 增幅仍 <20% → 200 可接受，但要同时看 DB CHECK 兜底 `BETWEEN 1 AND 1000`（`0028:201`）与 §4 的连接/内存余量，**不要**因为「还能跑」就上调；测不出稳定 p95（波动 >30%）→ 先隔离压测环境，数字不可用 |

```bash
# 改 policy_spec.py:40 不影响默认召回（默认值来自 decisions.TOP_K_RECALL=50）；Step 3 前要测不同 k 需临时改 decisions.py:176 并重建
docker compose -p kagent up -d --build api
docker compose -p kagent exec -T api python -m scripts.loadtest_chat \
    --kb <kb_id> --concurrency 10 --duration 300 --think 0 --out /tmp/rt_<k>.json
```

### 1.4 M-4 场景快照缓存 TTL（现 60s，`resolver.py:40`）

| 字段 | 内容 |
|---|---|
| **① 测试集怎么造** | 选一个已发布场景，准备一次「可观测的口径变更」：把 `policy` 的 `relevance_threshold_vector` 改成 `0.99`（该值会让几乎所有问题被拒答，切换瞬间可见）。因为发布接口不存在（Step 4），当前用 `UPDATE scenario_versions SET policy=… WHERE state='published'` 模拟 |
| **② 样本量下限** | 1 次变更 + **120 次探测**（1 次/秒 × 120s，覆盖 TTL 的 2 倍）。少于 2×TTL 无法区分「没生效」与「还没到 TTL」 |
| **③ 指标怎么算** | `生效时延 = 首次返回新口径的时刻 − 变更提交时刻`。判定依据用**可观测行为**（同一问题从「正常回答」变为「拒答」），不用日志时间戳（时钟/缓冲会引入误差） |
| **④ 判定阈值** | 单副本：≤1s（有主动失效 `invalidate()`，`resolver.py:94-100`）；多副本：≤ TTL = 60s（跨进程只能等 TTL，`resolver.py:44-45`）。要求秒级 → **必须换 Redis 频道**，调小 TTL 不算达标（只是把 DB 压力换成时延，且副本越多越不准） |
| **⑤ 记录模板** | `\| 日期 \| 副本数 \| TTL \| 变更时刻 \| 首次新口径 \| 生效时延 \| 达标 \|` |
| **⑥ 不达标怎么办** | 单副本 >1s → 主动失效没接上（发布接口未调 `invalidate`，或调在事务内导致回滚后缓存与库错位）；多副本 >TTL → 缓存实现有问题（时钟用了 `time.time` 而非 `time.monotonic` 会被系统改时影响）；要求秒级而副本 >1 → 上 Redis 频道，别调 TTL |

```bash
# 探测循环（宿主机，1 次/秒）；变更（另一终端）：UPDATE scenario_versions SET policy='{"relevance_threshold_vector":0.99}'
#   WHERE scenario_id='<sid>' AND state='published';
for i in $(seq 1 120); do date +%T; curl -s -X POST http://localhost:8000/api/integrations/search \
  -H "Authorization: Bearer <token>" -H "X-Application-Id: <id>" -H "X-Application-Key: <key>" \
  -H 'Content-Type: application/json' -d '{"query":"<同一句问题>","kb_ids":["<kb>"]}' | head -c 200; echo; sleep 1; done
```

### 1.5 容量常量与阈值标定（Step 7 容量看板）

看板 `GET /api/system/capacity` 的常量与四条阈值现在**全部可由环境变量覆盖**（`app/config/settings.py`
的 `CAPACITY_*`），改值不再需要改代码。但「可配置」不等于「已标定」：只有填写了
`CAPACITY_CALIBRATION_REF`，看板的 `calibrated` 才会变 true。**未实测不得填写 ref**；
ref 为空时看板必须显示 `calibrated=false`，这是判据不是提示。

| 项 | 怎么测 | 样本量 / 判据 | 不达标怎么办 |
|---|---|---|---|
| **`CAPACITY_M_SHARED_MB`**（默认 8192） | 目标机稳态（无压测、模型已加载）下跑 `docker stats --no-stream --format "table {{.Name}}\t{{.MemUsage}}"`，取 embedding + reranker 两个容器的驻留内存之和 | **3 次采样、间隔 ≥5 分钟**；变异系数 CV < 20% 才可用；记录每次采样值与时间 | CV ≥20% → 先排除模型冷启动/并发请求干扰，仍不稳则保持默认并保持未标定 |
| **`M_CONTROL_PG`**（默认 128） | 不需要人工标定：看板每次请求都执行 `SHOW shared_buffers` / `current_setting('shared_buffers')`，该项 `calibrated` 恒 true | 值与 `SHOW shared_buffers` 一致即可 | 解析失败应直接报错（仓库既有纪律，不做「读不到就用 128」兜底） |
| **`CAPACITY_M_SCENE_PG_MB`**（默认 300） | 先记录 PG 容器 RSS 基线；加 **1 个 hot 库**并压测 30 分钟后，读 `docker stats` 的 PG 容器 RSS，取与基线之差 | **3 次重复**；CV < 20% 才可用；同时记录库大小与索引规模 | 不可测（无 hot 库 / 环境不允许）→ 保持默认 300 且**保持未标定**，不得填一个「看起来合理」的数 |
| **`CAPACITY_INSTANCE_MEMORY_MB`**（默认 0=未提供） | 取 PG 容器内存上限：`docker inspect <pg容器> --format '{{.HostConfig.Memory}}'`（字节，换算为 MB）；或实例可用内存 | 必须记录来源（容器上限 / 宿主机可用）；**0 表示未提供**，不是「实测为 0」 | 拿不到来源就不填；填 0 时看板 `db_size_vs_instance_memory` 必须 `evaluable=false` |
| **`CAPACITY_RETRIEVAL_P95_BASELINE_MS`**（默认 0=未提供） | 目标机用 `scripts/loadtest_chat.py` 压测（默认召回 `TOP_K_RECALL=50`，见 §1.3；并发 / 时长用 `--concurrency` / `--duration` / `--stages`），取输出 JSON 的 `retrieve_p95`（发请求 → `citations` 事件，含检索不含生成）。**线上 `rag.retrieve.total` 只在 chat 主链路 `RetrievalService.retrieve_chain` 埋点；`/integrations/search` 与评测路径直连 `retrieve()`，不计入** —— 基线必须用同一链路测 | 样本量按 §1.3 的 **每档 ≥200 请求**；记录并发、样本量、日期；同一机器同一语料 | 无稳定 P95（波动 >30%）→ 先隔离压测环境，不填基线、保持未标定 |
| **三条数值阈值**（`CAPACITY_DB_HIT_RATE_MIN`=0.95 / `CAPACITY_DB_SIZE_RATIO_MAX`=0.30 / `CAPACITY_RETRIEVAL_P95_RATIO_MAX`=1.5） | 命中率取 **7 天窗口的 p5**（不是瞬时值）；库大小占比用 `pg_database_size()` 最大值 ÷ 实例内存；检索倍数用实测 P95 ÷ 基线 | 记录观测窗口、样本量、允许误差；调整条件写在报告里（例：连续 7 天 p5 低于阈值才收紧） | 无观测窗口数据 → 保持默认并保持未标定；**调整阈值后 MUST 更新 `CAPACITY_CALIBRATION_REF`** |

**统一记录模板**：

```
CAPACITY_CALIBRATION_REF=YYYY-MM-DD/<机器标识>/<报告路径>
```

- 格式固定为 `YYYY-MM-DD/<机器>/<报告路径>`，例如 `2026-11-24/<hostname>/reports/capacity-2026-11-24.md`。
- 报告里逐项写：采样值、采样时间、样本量、CV / 观测窗口、结论（采用值或「保持默认、未标定」）。
- **未实测不得填写 ref**；ref 为空时看板必须显示 `calibrated=false`。
- 只改了 `CAPACITY_*` 而没写报告 → 属于「配置了但没标定」，看板仍为 false，这是预期行为。

## 2. 环境绑定项（MUST 显式配置）

这 4 项在默认场景种子行里**不以字面量落库**，而以 `env_bound` 数组声明（详细设计 §A.5.1 `:225-231`）。
原因不是「没有默认值」（`settings.py:77/79/80/82` 都有），而是**默认值属于部署环境，不属于迁移**：
写死等于把某环境的模型名写进所有环境的迁移（§A.6 障碍 1 `:280`）。自检把 `env_bound` 展开成当前
`settings` 的实际值逐字段比对（S-9 `:1179`）。

| 项 | 默认值（出处） | 配错的后果 | 什么时候发现 |
|---|---|---|---|
| `embedding_model` | `bge-m3`（`settings.py:79`） | 空串 → **启动直接拒**（`decisions.py:1324-1327`）。换成与已入库向量不同的模型 → 不报错，但新旧向量不同构；向量路按口径过滤 → 旧 chunk 查不到（`retrieve/__init__.py:97-98`） | 启动 / 检索静默为空 |
| `embedding_dim` | `1024`（`settings.py:80`） | 非 1024 → **启动直接拒**：`chunks.embedding` 是 `vector(1024)`（`decisions.py:1319-1323`）。模型返回维度不符 → 入库即抛错（`services/embedding.py:64-66`） | 启动 / 入库 |

## 4. 分库部署的容量算式（最容易出事的一块）

### 4.1 算式与代入值

```
40 × N × K + 10 ≤ PG max_connections − 预留
   N = api 副本数；K = 每个副本同时连接的场景库数
   40  = pool_size 20 + max_overflow 20   # docker-compose.prod.yml:198-199、.env.prod.example:93-94、settings.py:58-59
   10  = worker 5 + 5                     # docker-compose.yml:269-270、.env.prod.example:96-97
   100 = PG 默认；postgres 服务未设 command:（docker-compose.yml:5-17），本项目未覆盖
   预留 = 20（迁移 / psql 排障 / 监控）；编排未定义，由部署者决策
```

预算 = 100 − 20 = **80**：

> **预留量的用途**：应用以集群超级用户连接（compose `POSTGRES_USER`），`superuser_reserved_connections` 不挤压应用可用连接；预留量仅用于迁移 / 备份 / 监控 / 排障等临时连接。

| N | K | 算式 | 占用 | 需 `≥`（含预留 20） | 判定 |
|---|---|---|---|---|---|
| 1 | 1 | `40×1×1 + 10` | **50** | 70 | ✅ 可行 |
| 2 | 1 | `40×2×1 + 10` | **90** | 110 | ❌ 默认 100 下超限（须 max_connections ≥ 110，或降池） |
| 3 | 1 | `40×3×1 + 10` | **130** | 150 | ❌ 超 50 |
| 1 | 3 | `40×1×3 + 10` | **130** | 150 | ❌ 超 50 |
| 2 | 2 | `40×2×2 + 10` | **170** | 190 | ❌ 超预算 80 |

> **两处前提**：① `settings.py:57` 注释写「`40 × 副本数 + worker 20`」，编排给 worker 的是 `5+5=10`——按注释 N=1 是 60、N=2 是 100，按实际值是 50 / 90，**以编排为准**，注释里的 20 已过期。
> ② worker 项取 10 而**不是** 10×K，前提是解析任务被 `OCR_MAX_CONCURRENCY=1` 串行化（`.env.prod.example:95`），同一时刻只有一个库的池在用；若放开该并发或调大 arq `max_jobs`，worker 项 MUST 改回 `10×K`。

### 4.2 分库对并发的真实代价（最容易被低估的一段）

池**不能跨库共享**（框架稿 §3A.3.1 `:287`：「池数 = 场景数」）。所以 K 个库不是「多占几条连接」，而是**把同一份预算切成 K 份，每份变小 → 每个库能同时服务的请求变少**；`:23` 实测「池 20 → 20 并发崩」（47% 失败，`:17`），即池 20 只服务**不到 20 个在途请求**：

```
每个池的上限 ≈ (max_connections − 预留 − worker 10) ÷ (N × K)      # 上界：预算 80 再扣 worker 10 得 70
2 副本、K=1 → 70 ÷ 2 = 35/池 → 约 30 并发（本机实测点，非承诺值）
2 副本、K=2 → 70 ÷ 4 = 17/池 → 已在崩溃线上
2 副本、K=3 → 70 ÷ 6 ≈ 11/池 → 必然在 20 并发前崩
```

**所以「分库」与「加副本」不是两个独立动作，而是同一预算里的联立方程**：加一个副本 = 每个池小一半，多一个库 = 每个池再小一份。要同时满足副本数与库数，只能提高 `max_connections`（§4.3-A）或上连接池中间件（§4.3-B）。

### 4.3 两条出路

**A. 调大 `max_connections`**：`≥ 40·N·K + 10 + 预留`。单库：N=1 需 70（默认够）、**N=2 需 110**（建议 150）、N=3 需 150（建议 200）。编排当前未传该参数，需自行注入，并配套调 `shared_buffers`——连接涨一倍、每连接内存上下文一起涨，只调连接数会先撞内存。

**B. PgBouncer**：池总量降为 `default_pool_size × 库数`。代价是 transaction 模式与**预编译语句**冲突：

| 冲突点 | 表现 | 依据 |
|---|---|---|
| 命名 prepared statement 跨事务失效 | 后端连接被换走，报 `prepared statement "s0" does not exist` | asyncpg 默认启用语句缓存 |
| 本项目的额外依赖 | `plan_cache_mode=force_custom_plan` 是刻意设的：不设则全文召回 2ms → 45ms | `database.py:16-21`、`:29` |

二选一：① PgBouncer ≥1.21 且 `max_prepared_statements>0`；② asyncpg 关语句缓存（`statement_cache_size=0`）——但 `force_custom_plan` 的收益一并消失，每次重新解析。**不要**在没实测检索延迟时选 ②。

**另一个等价闸门**：单库 `chunks` 行数 × 4KB（1024 维 × float32，框架稿 §3A.3.2 `:302`）> `shared_buffers` 的 50% → 分区或拆库（50% 是**占位值**，`:304`）。

| **记录模板** | `\| 日期 \| 机型/核数 \| 池(api/worker) \| 档位 \| requests \| failed \| error_rate% \| qps \| retrieve_p95 \| 判定(上限档) \|` |

**两个天花板并列，不分先后**（`RAG-并发压测报告.md:21`「两个天花板，都与核数无关」）：

| 天花板 | 由什么决定 | 典型值（本机实测，非承诺） | 加什么能提 |
|---|---|---|---|
| **QPS** | 单 uvicorn 进程（`AGENT_CONTEXT.md:208`） | ≈**4.5**（c=20 → 4.29、c=30 → 4.45，CPU 单核 126%，`:24`） | **加 worker 进程/副本**；加核无效（GIL + 单事件循环）。注：`:208` 要求**先改 prometheus multiprocess 再扩 worker**，否则多进程指标互相覆盖 |
| **并发（在途请求）** | DB 连接池容量 | 池 40 ≈ **30** 并发；池 20 → 20 并发即崩（`:23`） | **加池 / 加副本**；加核无效（崩溃时 CPU 均值仅 18.2%，`:19`） |

**给部署者的判别口诀**：用户抱怨**「慢」**（TTFT 涨、QPS 不涨）→ 看 **worker 数**；
抱怨**「报 500/503、等一会儿就超时」** → 看**池容量**（`QueuePool ... timeout` 就是它，`:18`）。两个症状对应两个不同的扩缩容动作，不要混成一句「性能不够」。
