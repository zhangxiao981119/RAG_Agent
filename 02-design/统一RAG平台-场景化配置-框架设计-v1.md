## 0. 一页结论（TL;DR）

| 问题 | 结论 |
|---|---|
| **可行性** | **有条件可行** —— **5 条**硬前提，任一缺失即退化为静默劣化（§2） |
| **分层** | **4 层**：平台层（全局不变式）/ 租户层（调用方边界）/ 场景层（一套策略）/ 请求层（一次调用）；依赖严格单向向下，覆写严格单向收紧（§3） |
| **场景是什么** | **不可变 DNA + 可调 Policy + 绑定 Binding** 三段式；切分判据是「改这个值，已落库派生数据是否还有效」（§4） |
| **MCP 契约** | **推荐「场景绑定在凭证上、工具签名不变」**（候选③）—— 因为 `IntegrationApplication` 已存在且已带 kb 白名单 + 配额 + 审计，是现成的最强同构（§5） |

| **演进** | **7 步**，每步「零影响或默认关」，复用本项目已验证的 opt-in（显式开启）开关纪律（§7）；**口径（Step 4）先于搬库（Step 6）** —— 一次只引入一个变量 |

## 1. 需求规格

### 1.1 用户已确认的形态（不可推翻的前提）

| # | 已确认 | 对本设计的约束力 |
|---|---|---|
| C1 | 「RAG 系统通过 MCP 作为工具暴露，用于企业中不同 agent 的知识库」 | RAG 是 **tool provider（工具提供方）**，不是给人用的应用；接口必须对调用方 agent 友好（同步可序列化、不依赖 `SSE`（服务端推送事件）长连接） |
| C2 | 场景 = 企业中可能出现的各种项目 / 各种 agent，**不是**某个具体业务 | 场景是**寻址维度**，不是**功能分支**；不允许出现 `if scenario == "hr"` 这类特化代码 |
| C3 | 场景差异表达为「同一套能力，按不同策略检索不同知识集合」 | 差异只允许落在 **策略参数** 与 **知识集合绑定**；**拓扑不变** |
| C4 | 明确**不要**把招聘 SaaS 的业务逻辑（结构化筛选、匹配评分、反歧视约束）搬进 RAG | §1.2 逐条列出「属于调用方职责」的能力，平台拒绝接收 |
| C5 | 先框架、后详细方案 | 本文不出 DDL / 迁移 / 字段级清单（§16） |
| C6 | **不同场景 agent 使用不同的库，不要把所有场景堆在一个库里** | 数据层按场景隔离（§3A）；但**模型服务不分裂**（I-5）—— 分的是数据，不是整套栈 |

### 1.2 边界：明确不做什么

| 不做 | 为什么 | 归属 |
|---|---|---|
| 结构化筛选（按薪资/年限/学历过滤候选人） | 是**业务谓词**，不是检索相关性；进 RAG 会让检索层承担调用方的数据 schema | 调用方 agent |
| 匹配评分 / 排序打分（人才-岗位适配度） | 需要业务 `ground truth`（基准真值），RAG 无法验证其正确性 | 调用方 agent |
| 反歧视 / 合规规则引擎 | 是**决策约束**，违反时后果属法律责任，不能藏在检索参数里 | 调用方；平台审计只记录不判定 |
| 多轮业务流程编排（面试预约、发 offer） | 是 **agent 的 E 层（执行循环）**职责；RAG 只提供知识与引用 | 调用方 agent |
| 场景级 DAG（自定义「解析→分块→索引」管线） | 见 §9 范式 P 与 §12 反例 R1 | **不做，永不做** |

**判据（可复用）**：一条需求若「RAG 不做，调用方也能做，且做错会被业务侧发现」→ 归调用方；若「RAG 不做，调用方无从做，且做错不报错」→ 归平台。

## 2. 问题 1：可行性判定

### 2.1 结论

**有条件可行。**

不是「可行」：把它做成「让场景自由拼装检索管线」是**不可行**的 —— 会退化成 `pipeline jungle`（管线丛林：每个场景一条自定义链，半年后无人能说清两条链的差异），见 `Sculley et al., NeurIPS 2015`（引自研究简报 §三 / §六）。
不是「不可行」：差异的真实形状是**参数 + 知识集合**，不是拓扑；本项目已有 13 个能力包组成的固定链，参数注入点清晰。

### 2.2 五条硬前提 + 失效模式

> 每条失效模式都必须是「**不报错的错**」，不是「效果变差」。

| # | 硬前提 | 不满足时的具体失效模式 |
|---|---|---|
| **P1** | **场景只配参数，不配拓扑**：执行链顺序、是否经过 `RRF`、阈值闸门存在性、是否做引用校验、是否做注入检测，一律不可配 | 场景 A 关掉章节补全、场景 B 保留 → 同一份 217 条评测集在两个场景下**跑不出可比数字**；bug 复现需先问「你在哪个场景」；回归测试组合数 = N 场景 × M 拓扑 |
| **P2** | **场景 DNA 必须带指纹且检索期 fail-closed**：向量空间三要素（模型 / 维度 / 文本公式）不匹配即**拒绝检索**，不是警告后继续 | 换 embedding 后旧 chunk 未重算、新旧向量被同一查询混检：余弦相似度跨模型无意义（**同维度也不行** —— `text-embedding-3-small` 与 `ada-002` 都是 1536 维但互不可比，引自研究简报 §四.1）。表现为**答案逐渐不相关且无任何报错**，通常被误诊为「rerank 不行」或「分块要重做」 |
| **P3** | **场景是唯一取值入口的下沉，不是并列第二套口径**：`current_index_profile()` 等现有函数改为「从场景快照派生」，函数名与返回类型不变 | 「场景说用 A 模型、`.env` 说用 B 模型」两个真源并存 → 改了场景不生效但界面显示已改；更坏：写入侧读场景、检索侧读 `.env`，一侧新一侧旧，表现为「刚入库的文档查不到」，无报错。本项目已在 `config_profile.py` 注释里记录同类故障：「两个真源比一个都没有更危险」 |
| **P4** | **场景绑定必须来自已认证上下文**，不接受调用方在请求体里自选任意场景 | 调用方传 `scenario="finance"` 就能用财务场景的策略与知识集合 → 越权且**返回的是别人的数据、看起来完全正常**。业界同类硬口径：Qdrant「租户索引帮助存储与检索，**它不授权请求**」；Azure「索引名**不是授权边界**，租户身份必须从已认证上下文推导」（引自研究简报 §四.4） |
| **P5** | **数据层按场景隔离，但模型服务不分裂**：库可分裂（I-7 寻址只来自凭证），`embedding` / `reranker` / `ocr` 永不分裂（I-5），向量口径锁 L0（I-6） | ① 若模型服务随场景分裂 → **第 2 个场景即突破 16GB**（§3A.4.2 推导），私有化交付不可行；且同文本被不同实例编码 → 向量不可比，P2 的 `index_profile` fail-closed 退化为「每库私事」。② 若允许按场景配 embedding → 平台无法回答「本部署的向量空间是什么」，模型升级变成逐库滚动重建，任何一次失败留下「旧口径孤岛」。③ 若库名可由请求体指定 → 与 P4 同源的越权（读别人库且不报错） |

## 3. 问题 2：分层架构

### 3.1 四层定义

> 层不是「配置文件层级」，而是**生效覆盖链**。判据：谁能改、改了影响谁、什么时候生效。

| 层 | 放什么 | 谁有权改 | 变更影响面 | 生效时机 | 允许运行时改 |
|---|---|---|---|---|---|
| **L0 平台层**（全局不变式） | ① 现有 `decisions.py` 的冻结常量：`CONTRACT_VERSION`、`RRF_K`、阈值**语义**、质量守门开关、权限判定口径、四闸门 SQL 语义、拒答文案锁定区；② `settings.py` 中决定向量同构的项：`embedding_model / embedding_dim / embedding_base_url`；③ 执行链拓扑 | 只有**发版**（PR + review） | 全平台所有场景、所有租户；改一次等于换一代数据 | 重启 + 启动自检 | **禁止**（尝试配置应**报错拒绝**，不是忽略） |
| **L1 租户层**（一个调用方或部门一套边界） | **可用场景清单（场景启用清单）**、场景版本钉定（钉住具体 version，不自动跟新版）、**库的可见性上限**（该租户可见哪些库位，只能收窄）、配额（日/月 token、每分钟请求数）、可见知识集合**上限**、保留期、允许请求级覆写的字段集 | 运营 / 部门管理员（受平台封顶） | 该租户的全部请求 | 下一请求（读快照） | **允许，但只能收紧不能放宽**（§3.3） |
| **L2 场景层**（一个场景一套策略） | **DNA**（平台 DNA 的只读引用，见 §4.2 / §3A.5.3）+ **Policy**（检索参数、链路开关、预算）+ **Binding**（知识集合逻辑键 + **数据源（库）绑定** + 模型覆写） | 产品 / 算法（后台表单，不改文件） | 该场景的**后续请求 + 新入库数据**；不影响其它场景 | 草稿→校验→发布版本后 | **允许**，但发布后不可改，只能发新版本；**库绑定不可在表单里改**（属 Binding，由部署动作落位） |
| **L3 请求层**（一次调用） | `query` / `question`、可选 `scenario`（仅限凭证允许时）、`top_k`（区间内）、`filters`（文档集/时间/标签）、`conversation_id` | 调用方 agent | 单次调用 | 立即 | **允许**，但**结构性受限于上层：越界拒绝（400），不是取默认、不是静默忽略** |

**为什么 L0 必须存在且不可穿透**：研究简报 §四的判定标准 —— *一旦做成配置项，两个不同取值的组合会产生「不报错的错误结果」*。L0 装的就是这类维度（清单见 §6）。

**为什么没有「L-1 模型层」**：模型不是配置层，是 L1 部署项 + L2 可空覆写（场景默认模型为空则回退平台默认 —— Dify 的 workspace 默认模型 + 应用不指定即回退，引自研究简报 §二.2）。

### 3.2 单向依赖方向（不变式 I-1 ~ I-4）

```
请求(L3) ──读──▶ 场景快照(L2) ──读──▶ 租户边界(L1) ──读──▶ 平台不变式(L0)
   │                  │                    │                    │
   └── 只可「收紧」────┴──── 只可「收紧」────┴──── 只可「收紧」────┘
                        （覆写方向与依赖方向相反，且单调）
```

| 不变式 | 内容 | 违反后的可观测症状 |
|---|---|---|
| **I-1** | **依赖只向下**：任何层不得读上层。L0 代码不得 `import` L2 模块（`decisions.self_check` 已有同类纪律：「配置层 MUST NOT import `app.services.*`」） | 启动期拉出检索模块 → 「关闭态零加载」被破坏；循环 import |
| **I-2** | **覆写只收紧**：L3 只能在 L2 给定区间内取值；L1 只能缩小 L2 允许的能力集 | 场景允许 `top_k ∈ [3,20]`，租户设 50 → 检索变成全表扫；租户打开场景本没开的图召回 → 图数据覆盖率为 0 却走了图路 |
| **I-3** | **数据只向下盖章，不向上回写**：chunk 行盖 `embedding_model` / `embedding_dim` / `embedding_text_version` / `chunker_version`；图行盖 `extractor_model + prompt_version`。场景**不写任何 chunk 行**，只选参数 | 场景改参数时顺手 `update` chunk 行 → 一份数据被多场景共享时互相踩踏；审计无法回答「这片是谁按什么口径生成的」 |
| **I-4** | **物理 ID 不进配置**：场景里只允许逻辑键（`scenario_key`、`kb_logical_key`），物理 UUID 由环境映射表在解析时绑定 | 导出场景配置到另一台机器 → 知识库关联全部丢失。Dify 导出 DSL **不带**关联知识库，跨 workspace 导入后「每个知识检索节点都会丢失关联的知识库」（引自研究简报 §六.4） |

### 3.3 覆写收敛真值表（只收紧，不放宽）

> 「收紧」的方向必须逐参数定义，不能一句「越小越好」。

| 参数 | L0 语义（锁死） | L2 场景可设区间 | L1 租户可设 | L3 请求可设 | 「收紧」的方向 |
|---|---|---|---|---|---|
| `recall_top_k` | — | `[3, 20]` | `≤ 场景值` | `≤ 场景值` | **减小** |
| `relevance_threshold` | 阈值**语义** =「top1 低于它整条拒答」锁 L0 | `[0.40, 0.70]` | `≥ 场景值` | `≥ 场景值` | **抬高**（更严 = 更容易拒答） |
| `rerank_enabled` | 开关不改数据形态，故属可配 | `开 / 关` | 只能 `关` | 不可设 | **关** |
| `graph_enabled` / `wiki_enabled` | 同上 | `开 / 关`（且受部署能力闸约束，见 §8 Q8） | 只能 `关` | 不可设 | **关** |
| 知识集合 | 授权项，不是优化项 | 场景绑定的集合（逻辑键） | `⊆ 场景集合` | `⊆ 上层集合`（交集；现有 `_integration_kb_ids` 已是三重交集） | **取子集** |
| **库位**（§3A 新增） | 由 Binding 推导 | **不可设**（由知识集合所属场景推出） | 可指定「哪个物理实例」（部署动作，非业务配置） | **禁止**（属授权面，无方向） | **无方向 —— 禁止** |
| 质量守门（grounding / 注入 / 敏感词 / 溯源） | **MUST 恒为真** | 不可设 | 不可设 | 不可设 | **无方向 —— 禁止** |
| 执行链拓扑 | 固定 | 不可设 | 不可设 | 不可设 | **无方向 —— 禁止** |

**诚实标注**：「L1/L3 只能收紧不能放宽」的**单调收敛原则**在业界未找到成文规定（研究简报 §八 待核线索 #1，出处为 WeKnora 的 `min(share, role)` 思路，属设计推理）。本设计采用它，是因为它让「生效值 ∈ 已知集合」成为**可断言的不变式**（I-2）；反之「任意层可任意覆写」会退化成研究简报 §六.5 记录的「隐藏优先级 / 多层覆写」反模式 —— 没人能预测实际生效值。

|---|---|---|---|

## 3A. 数据层隔离（控制面 / 数据面分离）

> **本章来源**：用户追加硬约束 —— 「不同场景 agent 使用不同的库，不要把全部场景堆在同一个库里」。
>
> **本章仍是框架级**：给判定表、边界清单、不变式、可测阈值、成本公式；**不写 DDL、不写逐字段连接配置清单**（→ §16）。表名只用于**锚定边界归属**，不是最终 schema。
>
> **本章与前三章的关系**：§4 定义「场景是什么」、§5 定义「调用方怎么找到场景」、本章定义「场景的数据住在哪」。三者通过 **Binding 里的「库位逻辑键」** 串起来（§3A.9）。

### 3A.1 先给结论：分的是数据，不是整套栈

| 判断 | 结论 |
|---|---|
| 「一场景一库」是否可行 | **可行，但必须限定为「只分 PostgreSQL + 向量」，不能整栈 per-scene**（§3A.4 有测算：整栈分裂在第 2 个场景就突破 16GB） |
| 默认形态 | **同实例不同 database（温）**；热场景按阈值升独立实例；冷场景直接**共享表 + 强 ACL**（`schema` 仅作对照项，不推荐 —— 迁移成本反高于 database，见 §3A.3.1） |
| 控制面能不能跟着分裂 | **绝对不能**（§3A.2 边界清单；否则「改一次场景配置要连 N 个库」「审计无法全局检索」「跨场景被拒查不到原因」） |
| embedding 能不能按场景配 | **绝对不能**，且分库让它从「不该」升级为「技术上自相矛盾」（§3A.5） |
| 分库是否等于安全 | **不等于**。分库只解决「数据住哪」与「召回不被稀释」，不解决授权（§3A.6 给 8 个仍须守的判定点） |
| 跨场景检索 | **一期不做联邦聚合**，调用方编排多次调用（§3A.7 给代价表与二期触发条件） |

### 3A.2 控制面 / 数据面边界清单

#### 3A.2.1 三条判定判据（先判据，后清单）

| 判据 | 内容 | 判为控制库 |
|---|---|---|
| **J1 跨场景读** | 一次读路径是否可能同时用到多个场景的数据？（如：鉴权、配额、审计检索、跨场景评测对比） | 是 → 控制库 |
| **J2 证据性** | 是否是「回答为什么这样」的证据链？（配置版本、指纹、审计、评测口径）—— 证据必须能被**全局一条 SQL 查出来** | 是 → 控制库 |
| **J3 同构绑定** | 是否与派生数据同生共死？（重建时必须与 chunk 同批重算；检索时必须与 chunk 同库 JOIN） | 是 → 场景库 |

> 三条判据**冲突时的优先级：J2 > J1 > J3**。理由：证据链丢一次就永久无法复原（不可重算），而跨库 JOIN 可以改用「引用 + 二次查询」替代。

#### 3A.2.2 边界清单（按现有 31 张表归属）

| 数据类别 | 具体表（现有表名） | 归属 | 依据 |
|---|---|---|---|
| **身份与组织** | `tenants` `departments` `users` `groups` `user_groups` `roles` `user_roles` | **控制库** | J1：鉴权在每个场景的每次请求都要用；J2：越权排查证据 |
| **知识库目录（关键）** | `knowledge_bases` `kb_members`；库位权威列在 `scenarios.db_binding` | **控制库**（映射见 `v_scenario_db_routing`；`knowledge_bases` **不加库位列**） | J1：需要「逻辑库键 → 场景 → 物理库」的路由表；否则无法决定连哪个库。**场景行是分库枢纽** |
| **场景注册与版本** | `scenario_profile`（§4 新增）及其版本行 | **控制库** | J2：配置漂移归因的唯一依据 |
| **租户边界与配额** | `tenant_quotas` | **控制库** | J1：配额必须跨场景汇总（否则一个 agent 用 3 个场景就绕过日限额） |
| **凭证与集成会话** | `integration_applications` `integration_conversations` | **控制库** | J2：凭证与「谁调用了什么」的证据；J1：鉴权入口 |
| **审计** | `audit_logs` | **控制库**（**新增 `scene_key` + 库标识列**） | J2 最高优先：跨场景被拒必须能一条 SQL 查出原因。**只存引用不存正文**（正文在场景库，见下） |
| **评测** | `eval_cases` `eval_runs` | **控制库** | J2：跨场景可比的前提；`caliber` 含场景键后才能归因 |
| **平台级策略口径** | `sensitive_words` `feature_flags` `prompt_versions` `finetune_samples` | **控制库** | 属 L0/L1 口径（§6 第 6 条：守门类不可按场景配）；`finetune_samples` 是平台级训练样本 |
| **知识内容** | `documents` `chunks` `kb_terms` | **场景库** | J3：检索必须与 `chunks` 同库 JOIN；`kb_terms` 是查询期别名表，跨库会多一次往返 |
| **图与 wiki** | `graph_entities` `graph_entity_mentions` `graph_relations` `wiki_pages` | **场景库** | J3：与 chunk 同生共死（DNA 变了一起重建） |
| **解析与治理作业** | `parse_jobs` `parse_segments` `governance_jobs` | **场景库** | J3：结果直接写 `chunks` / `documents`，跨库写会引入分布式事务 |
| **同步采集** | `sync_sources` | **场景库** | J3：采集目标就是本场景的知识库；凭据加密字段仍加密存储 |
| **会话历史** | `conversations` `messages` | **场景库**（**新增 `scene_key`**） | **取舍点**：J1 单场景（一次会话属一个应用 → 一个场景），J3 无关，J2 部分。判给场景库是因为体量大、热、单场景访问；代价是**审计不能 JOIN 消息正文** → 审计只存 `message_id` 引用。**这是有意识的取舍，不是遗漏** |
| **模型服务** | `embedding` / `reranker` / `ocr` 容器 | **平台级共享，永不分裂** | I-5；§3A.4 测算 |
| **队列与缓存** | Redis | **平台级共享**（按 key 前缀区分场景） | 分裂会让 arq 任务与限流失去全局视图 |
| **对象存储** | MinIO（`kagent-docs` bucket） | **共享实例，按前缀分** | 对象存储天生多租户；分裂无收益 |

**三条边界纪律**：

1. **场景库不允许存「跨场景要读」的东西** —— 一旦某张表被标识为场景库表，就视为「不可被其它场景 JOIN」，需要跨场景的信息必须上提到控制库（这就是 `knowledge_bases` 必须留控制库的原因）。
2. **控制库不允许存业务正文** —— 控制库只存元数据、引用、指纹、指标。否则控制库会变成「所有场景数据的副本」，分裂就白做了。
3. **库位是逻辑键，连接串在 L1** —— 场景 Binding 里只放 `db_logical_key`；真实连接串（host/port/db/user/password）属部署期环境变量（L1），**绝不下沉到场景配置**（否则违反 §4.2 Binding 的「密钥不下沉」，且导出配置即泄漏凭据）。

#### 3A.2.3 现有 27 个 alembic 迁移的归位规则（给归类表，不逐条）

> 判据同上（J1/J2/J3）。**不逐条列 27 个迁移** —— 它们按"建了什么"归类后自然归位；第二阶段的迁移脚本必须**按库拆分成两条链**（控制链 / 场景链），这是本表存在的目的。

| 迁移类别 | 典型内容（据已知迁移名/编号） | 归位 | 拆分后的执行方式 |
|---|---|---|---|
| **身份与权限** | 租户 / 用户 / 角色 / 部门 / 组、`0003_add_tenant_acl_epoch` | **控制链** | 只在控制库跑 |
| **知识库目录** | `knowledge_bases` / `kb_members` 建表与列变更；视图 `v_scenario_db_routing`、函数 `fn_kb_db_binding_conflicts()` | **控制链**（路由输入是 `scenarios.db_binding`，视图只读展示） | 只在控制库跑 |
| **场景与配置** | `scenario_profile`（新增）、`0010_add_prompt_versions`、feature flags、配额 | **控制链** | 只在控制库跑 |
| **审计与评测** | `audit_logs`、`eval_cases` / `eval_runs` | **控制链**（新增 `scene_key` 列） | 只在控制库跑 |
| **向量与内容** | `chunks` 建表、`0011_add_chunk_index_profile`、`fts_text` 生成列与 GIN 索引、`0022` 章节补全相关列 | **场景链** | **每个场景库各跑一次** |
| **图与 wiki** | `graph_*` 三表、`wiki_pages`、抽取口径列 | **场景链** | 每个场景库各跑一次 |
| **解析与治理作业** | `parse_jobs` / `parse_segments` / `governance_jobs` | **场景链** | 每个场景库各跑一次 |
| **同步采集** | `sync_sources` | **场景链** | 每个场景库各跑一次 |
| **会话历史** | `conversations` / `messages`（新增 `scene_key`） | **场景链** | 每个场景库各跑一次 |
| **跨链共用（谨慎）** | 若某迁移同时动控制表与场景表 → **必须拆成两个迁移文件** | 拆 | 控制链先跑，场景链后跑 |

**三条硬规则**：

1. **每条迁移只属于一条链** —— 一条迁移同时动控制库表和场景库表，就必须拆开。否则「控制库已升级、场景库未升级」的中间态无法表达。
2. **场景链的 head 必须在每个场景库都跑到同一版本** —— 迁移脚本要能报出「哪个库落后哪个版本」（这是 §3A.8 D4 的验收项之一）。
3. **可空列优先，避免停机** —— 分库后一次迁移要跑 N 个库，任何需要 `ACCESS EXCLUSIVE` 锁的重写都会放大 N 倍停机时间（本项目已有同类纪律：先加可空列 + 回填，见既有迁移风格）。



### 3A.3 四种隔离粒度的对照与升级阈值

> 术语先对齐：
> · **instance（实例）** = 一个 PostgreSQL 服务进程 + 一份数据目录（一个容器）。
> · **database（库）** = 同一实例内由 `CREATE DATABASE` 建立的独立库，各自有独立 catalog，**互不可跨库 JOIN**。
> · **schema（同一数据库内的命名空间）** = 同一库内的表命名空间，可跨 schema JOIN。

#### 3A.3.1 四粒度 × 六维度对照

| 维度 | ① 同实例不同 database | ② 同实例不同 schema | ③ 不同实例（独立容器） | ④ 不同物理机 |
|---|---|---|---|---|
| **隔离强度（谁能看到谁）** | 中：应用层可跨库查（需 `dblink`/`postgres_fdw`/两次连接），**普通 SQL 不能跨库 JOIN**；一个连接只能连一个库 → 天然「选错库就查不到」 | **弱**：同库内可 JOIN，`search_path` 一错就跨场景；**等于没隔离，只换了目录** | 强：物理进程隔离，连接串不同，故障不互相影响 | 最强：机器级；合规最好讲 |
| **单实例资源开销** | 低：共享一个 `shared_buffers` + 一份 WAL + 一份 autovacuum 进程 | **最低**：完全共享（几乎零增量） | 中：每实例独立 `shared_buffers` + WAL + 后台进程（按 PostgreSQL 默认 `shared_buffers=128MB` 起算，加连接与后台开销） | 高：每台机器操作系统 + 实例 |
| **连接池成本** | 需按库维护连接池（每库一份池）→ **池数 = 场景数 × 副本数**（每副本对每个库位各持一份池）；本项目每个在途请求长期占 1 条连接、流式中瞬时占 2 条（`RAG-并发压测报告.md:23`），每副本每库 `pool_size + max_overflow = 40`（`settings.py:58-59`）→ **总连接 = 40 × 副本数 × 库位数 + worker 10**（`docker-compose.yml:269-270`），随两者相乘而涨。★ **但它是「两条独立约束」中的一条，既不是唯一的、也不是以后的**：池 40 今天就把并发压在约 30（c=40 崩 18.28%，`:125`）；另一条独立的 **≈4.5 QPS** 天花板由单 uvicorn worker 决定（`:24`）。二者同时成立、各管一个指标，见 §3A.4.0 | 只需一份池（但要在连接上切 `search_path`，**易漏**） | 同 ①，但池隔离彻底 | 同 ③ |
| **备份恢复粒度** | **可按库备份**（`pg_dump -d`）→ 满足「某场景独立 RPO」 | 差：按 schema 备份要逐 schema 导出，恢复顺序敏感 | 可按实例备份，最干净 | 最干净 |
| **迁移成本（alembic）** | **中**：每库独立 `alembic_version` 表，需对每个库跑一次 `upgrade head`；但工具天然按 database 工作，**无需改造** | **最高**：每 schema 一套 `alembic_version`，且 ORM 的 `search_path` 必须逐连接设置，**一个漏设就是跨场景写** | 同 ①，另加编排（多容器 + 多卷） | 同 ③，另加运维 |
| **适用条件** | 默认形态：场景数中等、需要独立备份/恢复、数据量中等 | **仅当「必须共享同一套迁移版本且绝不独立备份」** 时；不推荐作为默认 | 热场景：数据量大、QPS 高、合规要求物理隔离 | 合规硬要求（等保/数据分级）或单机内存装不下 N 个实例 |

**反直觉但重要的结论（本项目的专业判断）**：**schema 隔离的成本高于 database 隔离**。原因是迁移与 ORM 天然以 database 为单位工作；schema 隔离要对每条连接设置 `search_path`，本项目 `_WHERE_BASE` 四闸门是裸 SQL 字符串（`acl/visibility.py::PUSHDOWN_WHERE_SQL`），一旦某条连接漏设 `search_path`，**检索会静默查到别的场景的表**——这是典型的不报错的错。所以本设计**把 schema 从「默认温层」降级为对照项**，不建议作为默认落地形态。这与 `01-research/研究简报.md` §5.1 的结论同向（pgvector 官方对多租户推荐「LIST 分区或独立表」，**不推荐**纯共享索引 + filter）。

#### 3A.3.2 升级阈值（可测，不写「较大」）

| 升级方向 | 触发条件（满足任一） | 测量方式 | 常量标定状态 |
|---|---|---|---|
| 共享表 → **schema 或 database**（即「该场景需要独立库」） | ① 该场景要求**独立备份窗口 / RPO / 保留期**；② 该场景数据含「不可与其他场景共实例」的合规约束 | 需求侧（合规清单 / 合同条款），非数值 | 已可判定 |
| schema → **database**（若曾用 schema） | ① 需要按场景独立恢复（`pg_dump -d` 粒度）；② 连接上 `search_path` 漏设风险无法用测试兜住 | 后者由「单测覆盖每条连接初始化路径」判定 | 已可判定 |
| database → **独立实例** | ① 该场景 P95 检索延迟 > 平台基线 **×1.5**，且已排除检索参数 / 索引原因；② 该实例 `pg_stat_database.blks_hit / (blks_hit + blks_read)` < **95%**（缓存命中塌了）；③ `pg_database_size` 超过实例可用内存的 **30%**；④ 需要按场景独立限流（到连接池级） | `/metrics` 已有分段计时（`embed` / `vector_sql` / `keyword_ilike` / `keyword_fts` / `section_recall` / `rerank` 各自 p50/p95）+ `pg_stat_database` + `pg_database_size()` | 1.5× / 95% / 30% **均为待标定占位值**，须用本项目真实数据标定 |
| 任意级 → **独立物理机** | ① 按 §3A.4 公式算出单机内存装不下 N 个实例；② 合规硬要求 | 资源测算 + 合规清单 | 可算 |
| **单库向量规模闸**（决定是否需要再拆或分区） | 单库 `chunks` 行数 × 单条裸向量字节数 > 该实例 `shared_buffers` 的 **50%** | 算术：**1024 维 × float32 = 4KB/条**（本项目 `vector(1024)`），故 10 万条 ≈ **400MB 裸向量**（不含 HNSW 图边开销，边开销本项目待实测） | 50% 待标定；4KB/条是算术值 |

> **诚实标注**：上表的 1.5× / 95% / 30% / 50% 是**占位常量**，依 `01-research/研究简报.md` §八「待核线索 #2」——pgvector 在本项目数据规模下的召回/延迟**从未实测**。本章给的是**测量方法与判定式**，不是结论。**不得把占位值写成已验证阈值**（本项目已有同款纪律：`GRAPH_SKIP_MIN_CHUNKS=8` / `WIKI_NAV_SELECTIVE_MIN_TERMS=3` 至今仍标「站位值」）。

### 3A.4 成本约束与分级策略（必须算，不拍脑袋）

#### 3A.4.0 两条独立约束：QPS 天花板 vs 并发天花板（**不是先后关系**）

> **本小节为 2026-11-20 订正（v1.2 二次订正）**：§3A 此前只测算了**内存**（3A.4.1~3A.4.4），并在 §3A.3.1「连接池成本」一格写了「必须先算 `max_connections` 余量」。这个提醒本身没错，但它**容易被读成「连接池是分库的首要瓶颈」**——那是错的。本小节给出准确的约束结构。**§3A.3 的四种粒度对照、§3A.4.1~3A.4.4 的内存测算与分级策略结论均不变。**

**先纠正一个错法**：不能把下面两条线排成「先撞谁、后撞谁」。它们是**同时存在、各管一个指标**的两条独立约束 —— 压测报告的原始表述就是并列的「**两个天花板，都与核数无关**」（`RAG-并发压测报告.md:21`），不是排序。

| 约束 | 管什么指标 | 天花板（本项目实测；**并发那一格的 `30` 是占位值，见注 1**） | 随什么变化 | 出处 |
|---|---|---|---|---|
| **单 uvicorn worker 的吞吐** | **QPS / 延迟** | **≈ 4.5 QPS**（c=20 → 4.29、c=30 → 4.45，加并发不再涨） | 只有**多进程 / 多副本**才变；**与核数无关**（api 进程单核打满 126%，换 64 核也提不上去） | `RAG-并发压测报告.md:24`、`:178`；`:16`（30 分钟 8077 请求 / 0 失败 / 4.48 QPS） |
| **连接池容量** | **并发数（在途请求上限）** | **池 40 → 30 并发能扛、40 并发崩（18.28% 失败）** | **改池即变**（`:188`「这个点是『池 40』的推论，不是"系统极限"。改池即变」）；分库后每库各持一份池 → 池总量 ×K、每库可扛并发 ÷K | `RAG-并发压测报告.md:23`、`:125`、`:130`、`:177` |

> **注 1 · `30` 是「待标定占位值」，不是承诺值。** 它是**本机 16 核 + LLM 桩上游**条件下的实测拐点，`RAG-并发压测报告.md:188` 自己就写着「这个点是『池 40』的推论，不是"系统极限"。改池即变」；同文 `:182-188`（§7.2 不可移植）把绝对 QPS、绝对 TTFT 与该失败率一起列入「**禁止当服务器容量承诺**」。所以在**换算到目标机的副本数之前 MUST 重新跑阶梯压测**，`30` 只能当占位输入用。做法与本项目既有纪律一致：`decisions.py:132`、`:941` 的站位值都在 docstring 里写明「站位值，待标定」，本文件 §3A.3.2 亦要求「**不得把占位值写成已验证阈值**」。
>
> **注 2 · 目标机怎么测出这个数（方法即判据）**：固定池大小，**按阶梯提升并发**（c=20 → 30 → 40 → …），每档记录失败率与 `QueuePool limit … reached` 次数；**取「失败率首次 > 0」的前一档作为该池下的并发上限**。`RAG-并发压测报告.md:118-130` 就是这条方法的完整样例：池 40 下 c=20 / c=30 均 0 失败，c=40 崩 18.28%（443 请求 / 81 失败 / 615 次池超时 / 350 个请求走到拒答）→ 上限判为 **30**。**换池必须重测**：池 20 时同一方法给出的是 20（`:23`）。

**为什么池 40 只扛得住 30 并发**：每个在途问答请求**长期占 1 条连接**（`get_db` 的 `yield` 覆盖整条 SSE 流）、**流式中瞬时占 2 条**（`:23`）→ 池里必须留出给瞬时翻倍的那部分，不能整池都当成"可同时进入的请求数"。实测崩点落在 c=30 与 c=40 之间：`c=40 → 443 请求 / 81 失败 / 18.28%`、`615 次池超时`、`350 个请求走到拒答`（`:125`、`:130`）。

**所以「现状（N=1、K=1、池 40）到底卡在哪」必须分两句话说，不能合成一句**：

- 问 **QPS**：卡在 **~4.5**。且 c=30 相比 c=20 只涨 3.7%、TTFT 从 4.4s 涨到 6.3s —— **加并发只是加排队**（`:129`）。
- 问 **并发**：卡在 **30**。**c=40 今天就已经崩 18.28%**（`:125`）——**连接池此刻就在压着并发上限，不是"加副本之后才成为约束"**。这是本小节要纠正的关键一句。

**两个动作吃的是同一个预算**：想要更高吞吐 → 加副本（连接池总量随副本数 ×N）；想要更高并发 → 加池（总量同样上涨）。两者都撞在 PG `max_connections` 这一道硬顶上 —— **这是一对联立方程，不是两步走**。下面的算式只回答「占了多少 PG 连接」，不回答「并发够不够」（后者由池大小直接决定，见上表）。

**容量算式**（连接预算是硬约束，必须先算）：

```
api 连接数    = 40 × 副本数 N × 库位数 K     # pool_size 20 + max_overflow 20
worker 连接数 = 10                            # 5 + 5，以编排实际值为准
总连接数      = 40 × N × K + 10  ≤  100 − 预留
```

三档代入（`预留` 取 10 —— **这是设定值，不是实测**；PG `max_connections` 默认 100，本项目未覆盖该参数）：

| 副本数 N | K=1（现状单库） | 占 100 | K=2（分出第 1 个场景库） | K=3 |
|---:|---:|---:|---:|---:|
| **1** | 40×1×1+10 = **50** | 50% | 40×1×2+10 = **90** | 40×1×3+10 = **130**（**超限**） |
| **2** | 40×2×1+10 = **90** | **90%** | 40×2×2+10 = **170**（**超限**） | — |
| **3** | 40×3×1+10 = **130** | **超限** | — | — |

**代入值读法（只回答「占了多少 PG 连接」，不回答「并发够不够」）**：

- **N=1、K=1 → 50/100，占五成。** 但「占五成」**不等于**「并发有余」：这 40 条池对应的是**约 30 的并发上限**（`:23`、`:125`）。**两个数不可互相替代** —— 前者是 PG 连接预算占用率，后者是在途请求上限；把 50/100 读成「池够用」正是本节要根除的误读。
- **想提 QPS → 只能加副本 → N=2 就是 90/100（九成），N=3 直接 130 超限。** 也就是说单库形态下副本数已被连接预算压到 **2** 顶天，而 2 副本只把 ~4.5 QPS 提到 ~9。
- **再叠分库 → K 也进乘积**：N=1 时 K=3 就超限（130）；N=2 时 K=2 已超限（170）。

**分库对并发的真实代价**：连接池不能共享，每副本、每个库位各持一份，**每库就分不到 40 条**。而并发上限由池大小直接决定（池 40 → 30 并发；池 20 → 20 并发就崩，`:23`）—— 所以分库不是"池不够用"，而是**把同一份 PG 连接预算摊给 K 个库，每个库能扛的并发随之下滑**。

**落到动作**：若要在分库形态下保住 2 副本，每（副本 × 库位）的池合计必须 ≤ `(100 − 10 预留 − 10 worker) ÷ (2 × K)` = **80 ÷ (2K)**：

- K=2 → **20/池**（即 `pool_size=10` + `max_overflow=10`）；
- K=3 → **约 13/池**（`pool_size=8` + `max_overflow=5`）。

这会**降低单库并发**，必须重跑压测：`RAG-并发压测报告.md:125` 记录「池 40 → c=40 崩（18.28% 失败）」，池减半后崩点随之前移（同文 `:23` 的「池 20 → 20 并发崩」就是缩小池的直接实证）。**降池与加副本不是两个独立动作，是一道联立方程。**

> **待修项（源码注释与编排不一致，不是本文笔误）**：`settings.py:57` 注释写「`40 × 副本数 + worker 20 ≤ PG max_connections(100) − 预留`」，而编排给 worker 的是 `DB_POOL_SIZE=5` + `DB_MAX_OVERFLOW=5` = **10**（`docker-compose.yml:269-270`）。**以编排为准**（本文算式用 10）：按注释算 N=1 得 60、N=2 得 100（恰好触顶）；按实际值得 50 / 90。注释里的 `20` 已过期，待更正。同一处不一致已由 `02-design/部署标定手册.md:173` 记录，此处因算式的输入值必须确定，复述一次并指明以编排为准。

#### 3A.4.2 形态 A vs 形态 B（内存差一个数量级）

| | **形态 A：只分 PostgreSQL（推荐）** | **形态 B：整栈 per-scene（否决）** |

#### 3A.4.3 形态 A 的内存公式与典型值

**公式**：

```
M_A(N) = M_shared + M_control_pg + N × M_scene_pg
```

| 项 | 含义 | 取值与来源 |
|---|---|---|
| `M_shared` | 平台级共享服务（不随 N 变） | `embedding` + `reranker` 的 `mem_limit` 各 4g（compose 声明上限），`ocr` / `api` / `mcp` / `worker` / `web` / `redis` / `minio` 未设上限（README 经验值口径） |
| `M_control_pg` | 控制库实例 | 1 份 PG 实例开销 |
| `M_scene_pg` | 每个场景库实例 | `shared_buffers`（PostgreSQL 默认 **128MB**）+ 连接/后台开销。**本项目待实测**；下表按 **300MB/场景** 作示例假设 |
| `N` | 独立实例的场景数（注意：**温/冷场景不乘**，见 §3A.4.4） | — |

**典型值（示例假设 `M_scene_pg = 300MB`，可替换为实测值复算）**：

| N（独立实例场景数） | postgres 侧累计增量 | 占 16GB 比例 | 交付判定 |
|---|---|---|---|
| 1 | +0.3 GB | ~2% | 宽裕 |
| 3 | +0.9 GB | ~6% | 宽裕 |
| 5 | +1.5 GB | ~9% | 宽裕 |
| 10 | +3.0 GB | ~19% | **需纳入容量测算**（README 的 16GB 是经验值，不是硬约束，但已吃掉近 1/5 余量） |
| 20 | +6.0 GB | ~38% | **必须做容量规划**，或把部分场景降级到「共享库 + 强 ACL」 |
| 30 | +9.0 GB | ~56% | **单机 16GB 方案接近不可交付** → 触发 §3A.3.2「独立物理机」评估 |

> 关键：**只有「热场景」才乘 N**。温场景（同实例不同 database）共享一份 `shared_buffers`，增量远小于 `M_scene_pg`；冷场景增量近似 0。这就是 §3A.4.4 分级策略存在的原因 —— 分级不是为了好看，是为了让 `N` 变小。

#### 3A.4.4 分级策略（热 / 温 / 冷）与切换条件

| 层 | 形态 | 内存增量 | 适用 | **升到上一层**的条件（可测） | **降到下一层**的条件 |
|---|---|---|---|---|---|
| **热** | 独立实例（独立容器 + 独立卷，形态③） | ≈ `M_scene_pg`（完整一份） | 数据量大 / QPS 高 / 合规要求物理隔离 / 有独立 RPO | 已达顶（下一步是独立物理机） | 连续 30 天 P95 延迟 < 基线 ×1.2 且数据量下降 → 降为温 |
| **温** | 同实例不同 database（形态①，**默认**） | 只增 catalog + 各自 WAL/连接（远小于 `M_scene_pg`） | **绝大多数场景** | 命中 §3A.3.2 任一条（延迟 1.5× / 命中率 95% / 库大小 30% / 需独立限流） | 数据量小且无独立备份需求 → 降为冷 |
| **冷** | 同实例共享表 + 强 ACL（schema 仅作对照，见 §3A.3.1 结论） | ≈ 0 | 试验性场景 / 极小知识库 / 已归档但仍需可查 | 需要独立备份/保留期 → 升为温 | — |

**分级不是静态配置，而是可监控的运维动作**：每个场景的层级必须由 §3A.3.2 的指标驱动，且**层级变更本身也要写审计**（否则「为什么这个场景昨天开始变慢了」无法回答 —— 与本项目 `capabilities.py` 记录的「闸门永远红 → 运维学会无视」是同一类治理问题）。

### 3A.5 embedding 同构性：分库最关键的连带后果（与 §3A.3 / §3A.4 是同一件事的三个侧面）

#### 3A.5.1 若允许按场景配 embedding，会发生什么

| 后果 | 具体形态 |
|---|---|
| **向量空间碎片化** | 每个库自成一套向量空间。跨场景比较（哪怕只是「同一问题在两个场景的 top1 分数」）失去意义 |
| **平台级模型升级变成逐库滚动重建** | 从「改一次 env + 重建一次」变成「N 个库各重建一次，且期间版本不一致」——升级窗口从一次变成 N 次，任何一次失败都留下一个「旧口径孤岛」 |
| **`index_profile` fail-closed 退化** | 现有机制是「按当前指纹过滤，不匹配就查不到」（`index_profile.py`：「宁可查不到，不可查错」）。一场景一库后，每个库自带一套口径 → 平台**无法再回答「这个部署的向量空间是什么」**，指纹从「平台级不变量」退化为「每库的私事」 |
| **与模型服务共享冲突** | `embedding` 是共享实例（I-5），它一次只能加载若干模型；若场景 A 要模型甲、场景 B 要模型乙，共享实例无法同时满足 → 要么分裂模型服务（违反 I-5 且吃内存），要么排队切换（延迟不可预测） |

#### 3A.5.2 本章不变式（I-5 ~ I-8；前三条与 embedding / 寻址直接相关）

| 编号 | 不变式 | 违反后的可观测症状 |
|---|---|---|
| **I-5** | **`embedding` / `reranker` / `ocr` 是平台级共享的模型服务，不随场景分裂** | 第 2 个场景即突破 16GB（§3A.4.2 推导）；且同文本被不同实例编码 → 向量不可比 |
| **I-6** | **embedding 模型 / 维度 / 向量文本公式版本锁死在 L0（平台层），不可按场景配置；场景库只承载数据，不承载向量口径** | 同一查询对两代向量算余弦 → 「逐渐不相关」且无报错；平台无法回答「本部署的向量空间是什么」 |
| **I-7** | **场景 → 库的寻址只能来自已认证上下文**（与 P4 同源）：调用方不得在请求体里指定库名，只能由凭证解析出的场景间接决定库位；解析失败一律 400，不降级 | 调用方传 `?db=finance` 即可读财务库 → 越权且**返回的是别人的数据、看起来完全正常**；库名若可拼接则叠加注入风险 |
| **I-8** | **控制面元数据永远留在控制库，不随场景分裂** | 「改一次场景配置要连 N 个库」；审计无法全局检索；跨场景被拒查不到原因 |

#### 3A.5.3 与「场景 profile 是 index_profile 上游」如何共存（关键调和）

分库后 **DNA 的「归属」上移，但「不可变性」不变** —— 这是本章对 §4.2 的**修订**（§3A.10 有对照）：

| | v1 表述 | v1.1（本章修订后） |
|---|---|---|
| DNA 归属 | 场景快照的一个段（`ScenarioSnapshot.dna`） | **平台唯一** `platform_dna`；`ScenarioSnapshot.dna` 降级为**对平台 DNA 的只读引用（值拷贝）** |
| 场景能否选 DNA | 可以在场景维度选（多 DNA 并存） | **不能**。场景**只能选策略**，选不了向量空间（I-6） |
| 多 DNA 并存的含义 | 「多场景各自一套口径」 | 改为「**同一平台 DNA 的代次灰度**」：升级时先建新代次库、双写/双读、比对、切换、下线旧代次 |
| 「场景 profile 是 index_profile 上游」是否还成立 | 成立 | **仍成立，但只有一层**：`resolve_scenario()` 决定「用哪套策略」；`current_index_profile()` 仍从**平台 DNA** 派生。即：**策略按场景，口径按平台** |

一句话：**场景可以选择「怎么检」，选择不了「向量怎么算」。**

### 3A.6 分库与「filter 不是授权边界」的关系

#### 3A.6.1 分库解决了什么、没解决什么

| 问题 | 分库的作用 | 说明 |
|---|---|---|
| **召回塌陷**（近似索引下 filter 后置导致回不满） | **部分解决**，不是全解 | 分库让「跨场景稀释」消失（每库索引只含本场景向量）。但**库内仍有用户级 / 密级 / 知识库级 filter**（一次检索只带 `authorized_kb_ids` 与 `clearance`），所以塌陷在**库内依然可能发生**，只是选择率更高、命中率更好。研究简报 §5.1 的算例（10% 选择率 × `ef_search=40` → 平均只回 4 行）正是**同库内 filter** 的失效形态 —— 分库不能消除它 |
| **授权边界** | **完全不解决** | 分库是「数据住哪」，不是「谁可以问哪」。研究简报已核到三条一手口径：Qdrant「租户索引帮助存储与检索，**它不授权请求**」；Azure「请求里的索引名**不是授权边界**」；pgvector RLS「若无策略适用，默认**拒绝**」 |
| **备份/恢复的越权** | 不解决 | 恢复一份备份后，ACL 仍须重新生效；「恢复即恢复权限」是常见误解 |

#### 3A.6.2 分库之后仍须在应用层守的 8 个判定点

| # | 判定点 | 现状落点 | 分库后是否仍必须 |
|---|---|---|---|
| 1 | **库由凭证推导，不由请求参数决定** | 新增（对应 §5.4 真值表 + I-7） | **必须**。禁止 `?db=` 这类入参；库名不得由请求拼接（防注入 + 防越权） |
| 2 | **用户授权知识库 ∩ 场景绑定集合 ∩ 请求 kb_ids** | `api/chat.py::_integration_kb_ids`（已有三重交集） | **必须**，且三重交集必须发生在「选库之前」（先定集合，再定库） |
| 3 | **四闸门 SQL 逐条保留**：`tenant_id` / `level_rank <= clearance` / `kb_id = ANY(...)` / `NOT deny_subjects &&` / `acl_tags &&` | `acl/visibility.py::PUSHDOWN_WHERE_SQL`（唯一真源，图/wiki 复用同一字符串） | **必须**。分库**不能替代任何一条**——库内仍是多用户多知识库 |
| 4 | **跨库清单白名单** | 新增 | **必须**：任何多库查询的库清单必须来自服务端白名单，不允许动态构造 |
| 5 | **库选择写审计**（含 `scene_key` + 库标识） | 新增（`audit_logs` 加列） | **必须**：否则「为什么这次没查到」无法归因（分库后最常见的故障是「连错库」） |
| 6 | **连接串不下沉到场景配置** | `settings.py`（L1） | **必须**（§3A.2.2 纪律 3） |
| 7 | **库不存在 / 连不上 → fail-closed 报错**，不降级为「查控制库」或「返回空」 | 新增 | **必须**：降级为「返回空」会被读成「知识库没这内容」，属静默错误 |
| 8 | **迁移/补建脚本的库范围显式化** | `scripts/*`（现状单库） | **必须**：脚本必须显式声明目标库（`--db-key` 或 `--all-scenes`），禁止「默认连默认库」 |

> **一句话**：分库降低的是「物理混住」的风险，**不降低任何一条逻辑授权判定的必要性**。把「分了库」当成「不用 ACL 了」，是把最危险的一类错误（返回别人的数据、看起来完全正常）主动打开。

### 3A.7 跨场景检索的取舍

| 选项 | 延迟 | 排序口径 | 引用编号一致性 | 失败降级 | 实现成本 | 判定 |
|---|---|---|---|---|---|---|
| **A. 不支持，调用方编排多次 MCP 调用后自行合并**（推荐） | N 次串行/并行调用（N = 场景数） | **由调用方定义**（平台不对跨场景排序负责） | 每次调用的 `citations` 编号各自从 1 开始 → **天然冲突**，须调用方自己加重前缀 | 单场景失败不影响其它（调用方决定） | **≈0**（不改代码） | ✅ **一期采用** |
| **B. MCP 层联邦聚合（federated aggregation，跨库聚合后统一返回）** | 1 次调用内部并发 N 库 → **最慢库决定整体**（长尾） | 平台必须自己定义跨库 RRF（各库 `final_score` 口径已不同：rerank 分 vs 余弦分，且 `active_threshold` 双口径） | 平台负责全局编号（可行，但需新契约） | 需定义「部分库超时是否返回部分结果」—— 返回部分结果 = **静默不完整**，属最坏降级 | 高（新契约 + 跨库事务边界 + 新的评测口径） | ❌ 一期不做 |

**推荐 A 的三条理由**：

1. **排序口径不可比**：`RRF` 需要**同一个候选池内**的排名（研究简报 §三：跨链路口径不可比正是 pipeline jungle 的失败模式之一）。跨库 RRF 必须先定义「库间名次如何归一」，而各库的 `final_score` 甚至可能一个来自 rerank、一个来自向量余弦（`active_threshold()` 的双口径已存在）。
2. **引用编号一致性是硬问题**：`citations` 是给调用方渲染给终端用户看的，编号冲突会让用户点到错误的原文 —— 这是**可观测的错误**（比静默劣化好，但体验差）。
3. **失败语义无法干净定义**：部分库超时时，返回部分结果 = 静默不完整；不返回 = 整体失败。两者都不好，而调用方编排时它可以自己决定（这是把决策放在信息更全的一方）。

**A 的代价（必须承认）**：调用方要实现「多场景合并 + 编号重排 + 部分失败处理」。缓解：在 MCP 工具描述里给出**合并范式**（示例代码级指引），并在响应 `meta` 里回带 `scene_key`，让调用方能稳定重编号。

**B 的二期触发条件（三条同时满足才评估）**：① ≥3 个独立 agent 提出同一需求；② 有 A/B 证据表明「平台内合并」比「调用方合并」在命中率或延迟上显著更优；③ 跨库排序口径已能定义（`active_threshold` 双口径问题先解决）。

### 3A.8 迁移路径（沿用 opt-in 纪律，每步可回滚）

> **与 §7 主路线的对应**：D1+D2 = **Step 5**（数据层目录 + 连接路由），D3+D4 = **Step 6**（首个场景迁出），D5 = **Step 7** 的容量分级部分。本节用 D1~D5 编号描述数据层自己的顺序，§7 用 Step 编号描述全局顺序，两者一一对应、不新增阶段。

> **总开关**：`SCENE_DB_SPLIT_ENABLED`（默认 **False**）。**关闭态不变量**：所有场景解析到现有单库 `kagent`，连接获取路径与未实现本章时**逐字节等价**（不新增任何查询、不新增任何连接、不读路由表）。这是 §7 同一套纪律（`GRAPH_RECALL_SELECTIVE` / `WIKI_NAV_SELECTIVE` 已验证）。

| 步 | 交付物 | 验收信号 | 回滚点 | 对基线影响 |
|---|---|---|---|---|
| **D1** | **库位权威列**：复用 0028 已建的 `scenarios.db_binding`（`NULL` = 默认库），**`knowledge_bases` 一列都不加**；只读视图 `v_scenario_db_routing`（展示虚拟键 `'default'`）；冲突检测函数 `fn_kb_db_binding_conflicts()`；`kb_catalog` 推迟到 Step 6 | ① `SELECT count(*) FROM scenarios WHERE db_binding IS NOT NULL` = 0；② `v_scenario_db_routing` 行数 = `scenarios` 行数；③ `fn_kb_db_binding_conflicts()` 返回 0 行；④ **新增失败集合为空**（口径见 §7.3）；⑤ 检索链路 `git diff` 为空 | 视图/函数 DROP / PR revert | **零** |
| **D2** | **连接路由层**：新增 `db_router.py`（`resolve_db_key` 纯函数 + 注册表 + 启动期预算闸门）与 `data_session()`；`get_db` **一行不改**；池按库位分桶，桶数启动期封闭为 `K=1` | ① 关闭态下 `data_session` 零调用点，且 `engine_for('default') is app.database.engine`；② `get_db` 源码金标准哈希不变（C-3）；③ 池实例数量与现状相同；④ 关闭态下存在非 NULL `db_binding` 时启动 WARN | 开关关闭时不调用；`db_router` 不被引用 | **零** |
| **D3** | **首个场景迁出**（白名单单场景，形态①同实例不同 database） | ① 该场景检索结果与迁出前逐条一致（同一评测集，diff = 0）；② 其它场景不受影响；③ 审计含库标识 | 把该场景库位改回 `default`（数据仍在新库，只切连接）→ 旧路径恢复 | **关闭态零**；开启仅影响白名单场景 |
| **D4** | **控制面/数据面读写分离收口**：审计、评测、配额全部走控制库；补建脚本支持 `--db-key` / `--all-scenes` | ① 跨场景审计一条 SQL 可查（含被拒原因）；② 配额跨场景汇总正确（一个 agent 用 3 场景不绕过日限额）；③ 脚本误连默认库应报错 | 脚本开关回退为「只跑默认库」 | **零** |
| **D5** | **分级策略与容量闸门**：热/温/冷层级 + §3A.3.2 阈值监控 + 升级动作审计 | ① 容量看板能算出 `M_A(N)`（§3A.4.3 公式）；② 任一场景触阈值时产生告警；③ 层级变更写审计 | 层级配置置回「全部温」 | **零** |

**为什么这个顺序**：**先有目录（D1）→ 再有路由（D2）→ 才敢迁第一个（D3）→ 再收口控制面（D4）→ 最后谈容量分级（D5）**。反过来做（先分级/先迁库）会在没有目录与路由的情况下产生「谁是哪个库」的口口相传，那正是分库最典型的长期债务。

**D1 的隐藏价值**：库位是**场景属性**，权威列已在 0028 落地（`scenarios.db_binding`）；D1 新增的是**只读视图与冲突检测**，不产生第二个可写真源。它仍是 §5 MCP 契约里「场景 → 知识集合 → 库位」这条链的落点（§3A.9）——落点用视图表达，而不是在 `knowledge_bases` 上复制一份。

### 3A.9 与 §4 / §5 的交叉一致性（三章对齐）

| 位置 | 本章要求的一致性 | 落点 |
|---|---|---|
| §4.2 **Binding**（场景绑定资源） | 新增一项 **`db_binding`：库位逻辑键**（不是连接串）；与 `kb_logical_key` 集合**成对出现**（库位由知识集合所属场景推出，不单独配置） | `ScenarioSnapshot.binding.db_binding` |

## 4. 问题 3：场景抽象模型

### 4.1 为什么切三段：一个判据，而不是三个形容词

**判据（唯一）**：*改了这个值，已落库的派生数据**是否还有效**？*

| 判据结果 | 归类 | 处理方式 |
|---|---|---|
| 派生数据**仍然有效** | **Policy（可调策略）** | 改了下一请求生效，无需重算 |
| 派生数据**不再同构** | **DNA（不可变身份）** | 改了必须触发重建；且检索期必须按指纹过滤，防新旧混检 |
| 不产出派生数据，只决定**用哪些已有数据 / 用谁的凭据** | **Binding（绑定资源）** | 改了下一请求生效；改错是**越权**，不是「效果差」 |

三段切的直接收益：**「改了要重做什么」从口头约定变成可计算**（§4.5 真值表）。这正是研究简报 §六.3 指出的最容易骗过测试的一类故障 —— 「你改了、也发布了、生产行为没变」（RAGFlow：数据集保留当时选的管线版本、现有 chunk 不会自动重新生成、自动元数据只对新解析文档生效）。

### 4.2 三段定义

#### DNA（不可变身份 —— 决定物理同构性）

| 项 | 内容 | 为什么必须不可变 |
|---|---|---|
| `embedding_model` / `embedding_dim` | 向量空间身份 | 不同模型向量**不同构**；本项目 `chunks.embedding` 是 `vector(1024)`，维度由 DDL（数据定义语言，此处指表结构）固定（`decisions.self_check` 已校验） |
| `embedding_text_version` | 喂给模型的**文本公式**版本（`to_embedding_text()` 的语义版本） | 语义变更代码无法自动感知（改了函数体输出也可能恰好不变），**必须人工 bump**（`index_profile.py` 模块注释原文） |
| `chunker_version` | 分块参数派生指纹（`c{target}-{max}-{overlap}`） | 影响**粒度**而非向量空间：旧切法的向量仍可比，但「章节补全 / 表格回捞」的边界会错位 |
| `graph_extractor_model` / `GRAPH_PROMPT_VERSION` | 实体 / 关系抽取口径 | 换模型或改 prompt 后旧行**不同构**；`graph_profile.py` 已按 `(model, prompt_version)` 双列过滤，fail-closed |
| `wiki_generator_model` / `WIKI_PROMPT_VERSION` | wiki 页生成口径 | 同上；`wiki_pages` 已有 `caliber_mismatch` 统计 |
| `contract_version` | 契约版本（当前 `v1.1`） | 跨版本行为不可比，评测基线只在同 contract 内有效 |

**DNA 组合指纹** = `index_fingerprint`（既有，sha1 前 12 位）× `chunker_version` × `graph fingerprint` × `wiki fingerprint` × `contract_version`。

> ⚠ 关键设计约束：**DNA 不进「可编辑的策略表单」**。DNA 字段一旦出现在产品可改的界面里，就等于给了「允许静默劣化」的入口（§6 第 1~4 条）。DNA 只**只读展示** + 「更换需走运维流程」。

#### Policy（可调策略 —— 改了只影响后续请求）

分三组（分组依据 = 「谁最常改」，不是「技术上像不像」）：

| 组 | 内容 | 谁改 | 为什么放这一组 |
|---|---|---|---|
| **检索形状** | `recall_top_k`、`rerank_enabled`、`relevance_threshold`（数值）、是否混合检索、`fts_max_terms`、关键词扩展开关 | 算法 | 高频调、需 A/B（对照实验）、不改变数据形态 |
| **旁路开关** | `graph_enabled`、`wiki_enabled`、章节补全、表格回捞、各自 token 预算 | 算法 | 全是「锦上添花的上下文补充」，不改主链排序语义（本项目已验证：这些片分数恒 0 或不进排序，不污染阈值语义） |
| **生成与预算** | 场景默认模型（nullable，空则回退平台默认）、上下文窗口预算、历史轮数 | 产品 | 成本直接相关；nullable 覆写避免「每场景必填」（Dify 三层默认模型口径） |

#### Binding（绑定资源 —— 改了是越权风险）

| 项 | 内容 | 约束 |
|---|---|---|
| 知识集合 | 场景可见的 `kb_logical_key` 集合 | **逻辑键**；物理 UUID 由环境映射解析（I-4） |
| **库位（数据源绑定）** | `db_binding`：该场景数据所在的**库逻辑键**（不是连接串） | **逻辑键**，由知识集合所属场景推出，与 `kb_logical_key` 集合成对出现；**连接串（host/port/db/user/password）属 L1 部署期环境变量，绝不下沉到场景配置**（否则导出配置即泄漏凭据，且违反 I-4）。场景表单不可编辑此项 |
| 凭证 / 调用方 | 哪些 `IntegrationApplication` 绑到本场景 | 一个应用绑一个场景（§5.3）；多集合靠多应用（§8 Q6） |
| 模型覆写 | 场景默认 LLM（nullable） | 端点与密钥**不下沉到场景**（凭证属 L1；进场景 = 密钥扩散） |
| 限额默认值 | 场景级配额**建议**值 | 仅建议；实际以租户层为准，且只能被 L1 收窄 |

### 4.3 与现有 `index_profile` 的关系：场景是**上游**，不是并行

**现状**：`current_index_profile()` = `f(settings.embedding_*, EMBEDDING_TEXT_VERSION, _chunker_version(decisions.CHUNK_*))` —— 全局单值，唯一入口。

**演进后**：

```
        ┌─────────────────────────────────────────────┐
        │  场景快照 ScenarioSnapshot (L2)             │
        │  DNA ──▶ Policy ──▶ Binding                 │
        └───────┬─────────────────────────────────────┘
                │ 派生（单向；不改函数名 / 返回类型）
                ▼
   current_index_profile(scenario)  ──▶  IndexProfile(embedding_model, dim, text_version, chunker_version)
                                          └─ 仍是**唯一取值入口**
                ▼
   current_graph_profile(scenario) / current_wiki_profile(scenario)
                ▼
   retrieve() / chunk() / graph recall / wiki nav  ← 一处读，不许各读一份
```

**三条硬约束（第二阶段必须写成单测）**：

| # | 约束 | 理由 |
|---|---|---|
| D-1 | `IndexProfile` 的**返回类型与字段名不变**，只把「值从哪来」下移 | 13 个能力包都在读它，改类型 = 全仓改 |
| D-2 | **不存在「场景之外」的第二套运行口径**：`.env` 里的 `EMBEDDING_*` 在场景化后降级为「默认场景的初始种子值」，不再是独立真源 | P3 + I-2；这是本方案最容易做错的地方（两个真源） |
| D-3 | 默认场景（`scenario_key="default"`）的 DNA **必须等于**当前 `.env` + 代码常量 | 保证 Step 1~2 零影响（§7） |

### 4.4 场景生命周期状态机

```
     create            validate             publish             deprecate
  ─────────▶ draft ──────────────▶ ready ──────────▶ published ──────────▶ archived
                │  ▲                  │                   │
                │  └── 校验失败回草稿 ─┘                   │ 只能发新版本；published 行不可改
                └──── checksum 乐观并发（他人已改 → 保存被拒）──┘
```

| 状态 | 可被请求使用 | 可编辑 | 说明 |
|---|---|---|---|
| `draft` | 否 | 是（带 `checksum` 乐观并发） | RAGFlow 口径：「仅保存草稿不能作为解析方式被选中」（引自研究简报 §六.2） |
| `ready` | 否 | 是 | 已过 schema 校验 + DNA 合法性校验（指纹可算、kb 逻辑键可解析） |
| `published` | **是** | **否**（只读快照） | 版本号单调递增；唯一约束保证同场景只有一个生效版本 |
| `archived` | 否（存量请求按钉定版本继续） | 否 | 归档不删数据；已钉此版本的租户可继续用，显式迁移才切版本 |

## 5. 问题 4：MCP 工具契约演进

### 5.1 现状与已存在资产（这决定选型）

**现状签名**（`apps/mcp/main.py`，89 行，全部是转发）：

```python
knowledge_ask(question: str, kb_ids: list[str], conversation_id: str | None = None) -> dict
knowledge_search(query: str, kb_ids: list[str]) -> dict
```

**已有资产（本设计的关键）**：请求不只带 `kb_ids` —— MCP 适配层强制要求三个身份头（`X-User-Token` / `X-Application-Id` / `X-Application-Key`），主 API 用它们完成双认证，并把生效 kb 集合取成 **应用白名单 ∩ 用户授权 ∩ 请求 kb_ids** 三重交集（`api/chat.py::_integration_kb_ids`）；应用对象上已带 `rate_limit_per_minute` / `daily_token_limit` / `daily_message_limit`。

**推论**：调用方**今天已经无法**通过 MCP 访问任何不在应用白名单内的知识库 —— 也就是说，**「知识集合」这一维的场景语义，今天就已经绑在凭证上了**，只是它还没有名字、没有版本、没有策略。

### 5.2 三个候选对比

| # | 形态 | 表达能力 | 授权安全性 | 迁移成本 | 工具清单稳定性 | 失败模式 |
|---|---|---|---|---|---|---|
| **①** | **场景作为工具入参**：`knowledge_search(query, scenario, kb_ids?)` | 高（一个端点跑所有场景） | **弱**：场景可能与凭证解耦 → 必须服务端校验 `app → scenario` 白名单，漏一处即越权；调用方传错场景**不报错只能用错** | 低（加可选参数） | 稳定（2 个工具） | 场景变成「字符串参数」→ 无法阻止跨场景调用；审计要额外字段归因；与 P4 冲突（场景来自请求体） |
| **②** | **一场景一工具实例 / 一端点**：`/mcp/{scenario}/mcp` 或按场景注册 `knowledge_search_finance` | 高（场景即地址） | **强**：场景在 URL 上由服务端解析，调用方无法自选 | 高（MCP 客户端要按场景配端点与凭据） | **不稳定**：场景数 = 工具数或端点数，工具披露随场景膨胀（研究简报 §三：profile 组合的组合爆炸风险） | 连接数随场景线性增长；场景改名 = 客户端全改；同一 agent 跨场景需多连接 |
| **③** | **场景绑定在凭证上，工具签名不变**：`IntegrationApplication += scenario`（nullable） | 中高（够用：一个 agent 一组知识 + 一套策略） | **最强**：场景由已认证凭证推导，请求体无从干预 | **低**（旧调用方零改动；凭证对象已存在） | 稳定（2 个工具，签名不变） | 一个 agent 要两个场景 → 需两个凭证（多凭据管理）；场景切换需后端改绑定而非前端传参 |

### 5.3 推荐：**候选 ③**，理由四条

| 理由 | 依据 |
|---|---|
| **R1 与现状最强同构，不是新造** | `IntegrationApplication` 已有 `kb_ids` / 配额 / `status` / `tenant_id` / 审计（`api/integrations.py` 每次调用都 `audit.record`）。绑定场景只是**给它已有的内涵起名字** |
| **R2 满足 P4（授权从已认证上下文推导）** | 场景是「身份的一部分」而非「参数」。这正是 Qdrant「租户身份必须**从已认证用户推导**，而不是接受请求里传来的不受限 tenant ID」、Azure「由可信应用层从已认证上下文推导」的同一口径（研究简报 §四.4） |
| **R3 迁移期成本最低** | 工具签名不变 → 现有调用方（以及任何已接入的 agent）**零改动**；新增能力是「可选参数 + 可选绑定」，不是破坏性变更 |
| **R4 配额与审计天然可归因** | 「哪个场景花了多少 token、跳过了多少次图召回」直接可查（应用维度），不需新增归因字段；与现有 `/metrics` + `eval_runs` 口径一致 |
| **R5 补上「凭证 → 场景 → 库」寻址链的最后一跳**（§3A） | 分库后「这个请求该连哪个库」必须有人在服务端回答。③ 天然给出答案：`凭证 → 场景（Binding.db_binding）→ 库位 → 连接池`。**库名不出现在任何对调用方可见的契约里**（不在工具签名、不在响应体、不在文档示例）—— 调用方既无法指定库，也无法感知库名，从而 I-7 不靠「记得别传」而靠「没有入口」保证 |

**为什么不是 ①**：① 的功能等价于「给 `kb_ids` 加个别名」。而 `kb_ids` 的越权风险今天已被三重交集兜住了 —— 若场景绕过凭证走请求体，等于**把已经关上的门重新打开**。
**为什么不是 ②**：② 最干净，但与本项目的调用方形态不匹配 —— 调用方是「企业内部各 agent」，数量多、变更频繁，端点即场景会让 MCP 客户端配置成为运维负担；且它把「场景数」变成「工具披露规模」的乘数（而工具披露顺序变化会让调用方前缀缓存失效）。

### 5.4 迁移三阶段兼容表（关键：旧调用方逐字节不变）

| 阶段 | 工具参数 | 凭证 | 服务端解析逻辑 | 旧调用方行为 |
|---|---|---|---|---|
| **S0 现状** | `(query, kb_ids)` | 无场景 | 请求 `kb_ids` ∩ 白名单 ∩ 授权 | — |
| **S1 可选绑定**（Step 2） | **签名不变**（新增可选 `scenario: str \| None = None`） | 可绑场景，也可不绑 | 见下解析真值表；未绑 → `default` 场景（= 当前全局策略） | **逐字节一致**（`scenario=None` 走 `default`） |
| **S2 默认化**（Step 3 后） | 同上，`kb_ids` 变为**可省略** | 建议绑定 | 省略 `kb_ids` → 用场景 Binding 集合；仍传 → 取交集 | 仍一致（传了就照旧取交集） |
| **S3 收口** | 同上 | 必须绑定 | 未绑场景的应用拒绝创建（管理面强制） | 需一次性配置绑定（运维动作，非代码改动） |

#### 场景解析真值表（服务端唯一实现，不变式 I-7）

| 凭证绑定场景 | 请求带 `scenario` | `scenario` 是否在应用允许清单 | 结果 |
|---|---|---|---|
| 无 | 无 | — | `default` 场景 |
| 无 | 有 | 是 | 用请求场景（过渡期能力，S3 后移除） |
| 无 | 有 | 否 / 清单为空 | **`400 SCENARIO_NOT_ALLOWED`**（显式拒绝，不静默降级） |
| **有** | 无 | — | 用**凭证绑定场景** |
| **有** | 有且一致 | — | 用凭证绑定场景（幂等） |
| **有** | 有且不一致 | — | **`400 SCENARIO_MISMATCH`**（不静默覆盖：静默覆盖会让调用方以为换了场景，实际没换） |

**I-7**：*场景解析结果（含它绑定的**库位**）只依赖（已认证凭证, 请求参数），不依赖任何可被调用方改写的状态；**库名不由请求参数指定、不由入参拼接**；解析失败一律 400，不降级。*（与 §3A.5.2 同一条不变式）

### 5.5 MCP 侧必须回答的三个 T 层问题

| 问题 | 结论 |
|---|---|
| **注册 ≠ 披露 ≠ 授权** 怎么分？ | **注册**：两个工具常驻注册（不按场景动态增删，否则工具披露顺序变 → 调用方前缀缓存失效）；**披露**：工具 schema 与原函数分离（现状 `mcp.tool(fn)` 显式注册以保留函数对象，便于检查签名与离线单测）；**授权**：由凭证 + 场景在服务端判定，**不在 MCP 层** |
| **凭证是否进执行环境**？ | **不进**。MCP 适配层只做 header 映射（`x-user-token` → `Authorization: Bearer`），应用密钥明文只在创建响应出现一次，库里只存 SHA-256（`api/integrations.py::_application_key_hash`）。场景化**不得**把密钥或端点下沉到场景配置（§4.2 Binding） |
| 场景是否新增工具？ | **一期不加**。可选候选：`knowledge_capabilities()`（只读，返回当前凭证绑定的场景、知识集合摘要、能力开关），用于调用方「先问能用什么」。列 §16 可选项，不进主路线 |

## 6. 问题 5：不可配置清单（硬约束）

### 6.1 判定标准（与「可配但会报错」区分的唯一依据）

> **一旦做成配置项，两个不同取值的组合会产生「不报错的错误结果」（静默劣化），而不是「报错的失败」。**

配套判据：*可配的是「**怎么取**」（`top_k`、阈值、策略开关）；不可配的是「**算出来是什么**」（向量空间、派生公式、授权边界、质量守门）。*

### 6.2 清单（8 类）

| # | 不可配维度 | 若配置化会发生的**具体错误**（不是「效果差」） | 代码归属 | 现状 |
|---|---|---|---|---|
| **1** | **embedding 模型 / 维度 / 向量文本公式版本** | 场景 A 用模型甲、场景 B 用模型乙（哪怕同维度）→ 若指纹过滤被放宽或忘 bump：同一查询对两代向量算余弦，**跨模型余弦无意义**，结果「逐渐不相关」且无报错，常被误诊为 rerank 或分块问题。若**维度**被改 → `vector(1024)` 列类型失配（这一条**会**报错，属「可配但会报错」，反而不是最危险的）；真正危险的是**同维度不同模型**与**公式版本漏 bump** | `index_profile.py`（`EMBEDDING_TEXT_VERSION`）+ `self_check`（dim == 1024） | ✅ 已锁 |
| **2** | **派生数据的生成公式标识**（`embedding_text_version` / `chunker_version` / `GRAPH_PROMPT_VERSION` / `WIKI_PROMPT_VERSION`） | 版本号做成环境变量 → 允许「版本说 v2、实际跑 v1」：旧口径数据被当成新口径**混算**，且没有任何报错。Elasticsearch 的对应硬约束是「不能改已有字段的 mapping，要改只能新建索引 + reindex」（研究简报 §四.3）——**派生数据的生成契约只能换代，不能原地改** | `index_profile.py` / `graph_profile.py` / `wiki_profile.py` 的 `Final[str]` 常量 | ✅ 已锁 |
| **3** | **分块参数的「物理后果」**（不是参数值本身） | ⚠ **本条是本清单里唯一有内部张力的，必须精确表述**：分块参数**值**（target / max / overlap）**可以**进 L2 DNA（研究简报 §二.1 亦把「分块目标/上限/重叠」列为场景级）；但 **`chunker_version` 必须由参数派生并随 chunk 行盖章**，且「改参数后旧 chunk 标过期」必须自动发生。若把 `chunker_version` 也做成配置（或允许改参数不重建）→ 新旧粒度混存：**章节补全按 `heading_path` 补同节片**时会把旧粒度的片当成同节片拉进上下文（预算被吃掉、答案里出现半截条款），且**没有任何报错** | `index_profile._chunker_version()`（派生，不手写） | ✅ 已派生；⚠ 需新增「过期视图」 |
| **4** | **图抽取 / wiki 生成的 prompt 版本** | 版本号必须与 prompt **正文同源**。做成环境变量 → 正文改了版本没改（或反之）：旧口径的图行被检索侧 `WHERE extractor_model=:m AND prompt_version=:pv` 判为同口径 → **旧图与新图混在同一张图里扩展**，实体归一与关系谓词口径不同，返回的「邻居」语义可疑且无报错 | `graph_profile.py` / `wiki_profile.py` | ✅ 已锁 |
| **5** | **权限判定口径**：四闸门 SQL 语义、`VISIBILITY_GRANTS`、`DOC_TAG_ANCESTOR_EXPANSION`、`ACL_PUBLIC_MUTEX`、`ACL_LEVEL_TAGS_ALLOWED`、`tenant_id` 过滤、租户身份来源 | 做成配置 = 一条配置就能让全租户数据互见，且**返回的是别人的数据、看起来完全正常**。Qdrant 原文：「租户索引帮助存储与检索，**它不授权请求**。持有不受限凭据的客户端可以省略 filter 访问其它租户的点」；Azure：「请求里的索引名**不是授权边界**」。更细的坑：`DOC_TAG_ANCESTOR_EXPANSION=True` 一改就是「全公司互通」（`decisions.py` 原注释） | `decisions.py`（`self_check` 已 fail-closed 拦 6 项）+ `acl/visibility.py::PUSHDOWN_WHERE_SQL` | ✅ 已锁 |
| **6** | **质量守门类开关**：`GROUNDING_CHECK_ENABLED` / `INJECTION_GUARD_ENABLED` / `SENSITIVE_FILTER_ENABLED` / `MEMORY_SOURCE_TRACE_REQUIRED` / 拒答文案必须落在 `qa_system` 锁定区 | 这类开关「关掉更省事、指标更好看」，一旦可配，**第一个被关掉的就是它们**；关掉后系统仍然能跑能答，只是答案不可信。`OWASP`（开放 Web 应用安全项目）口径：**fail-safe defaults**（失败即安全默认）——「除非显式授权，否则默认拒绝」「默认配置应尽可能安全，而不是尽可能好用」 | `decisions.py`（`self_check` 逐条拦） | ✅ 已锁 |
| **7** | **执行链拓扑**：步骤顺序、是否经过 RRF、阈值闸门是否存在、是否做引用双向校验、是否做注入检测这一步 | 拓扑可变 → 两个场景的数据不可比、217 条评估集不可复用、回归测试组合爆炸（N 场景 × M 拓扑）。学术命名：`pipeline jungle` / `glue code`（胶水代码）/ `CACE`（Changing Anything Changes Everything，改任何东西都改了全部）（Sculley 2015）。**边界**：rerank 的**开关**属 L2（可配），因为它不改数据形态、只改候选排序 | `retrieve/__init__.py` 主链 | ✅ 现状固定 |
| **8** | **阈值 / 判定的「语义」**：阈值是过滤还是加权、低于阈值是拒答还是低置信作答、`active_threshold()` 的双口径映射、MCP 响应事件序列与 `CONTRACT_VERSION` 语义 | **数值**可下沉 L2（§3.3）；**语义**必须留 L0。否则场景 A 改成加权、场景 B 保持过滤 → 同一份评估集**无法比较**（同一个 0.50 在两处含义不同）；调用方也无法写稳定的解析代码 | `decisions.py`（`active_threshold` / `CONTRACT_VERSION`） | ✅ 已锁 |

### 6.3 一条附加规则：尝试配置应**报错**而不是忽略

| 场景 | 现状风险 | 本设计要求 |
|---|---|---|
| 有人在场景表单里填 `embedding_model` | 若无校验：静默写入 → 无效果 → 用户以为已切换 | **保存即 400 / 422**，报「该维度属平台不变式，不可场景化」——静默忽略是最坏的一种：调用方 / 运维以为生效了（研究简报 §二.2 L4 口径） |
| 有人在请求里传 `grounding=false` | 若被忽略：调用方以为关掉了（或以为能关） | **400** |
| 有人改 `.env` 的 `EMBEDDING_MODEL` 但没重建数据 | 现状：写入侧盖新指纹、检索侧按新指纹过滤 → 旧 chunk 全部查不到（fail-closed，这是**正确的报错态**） | 保留该行为；并在启动横幅显式打「DNA 与库内 chunk 指纹不一致，X 篇待重算」 |

| **Step 5** | **控制库只读目录 + 连接路由**（§3A.8 D1+D2） | `v_scenario_db_routing` + `fn_kb_db_binding_conflicts()`；`db_router` 按 `scenarios.db_binding` 取连接（**默认全部落现有库**）、池按库位分桶；`get_db` 不改；`knowledge_bases` 不加列 | ① 关闭态下 `engine_for('default')` 与现连接对象恒等、`get_db` 源码哈希不变；② `scenarios` 中 `db_binding IS NOT NULL` 行数 = 0，且视图行数 = 场景行数；③ **新增失败集合为空**（口径见 §7.3）；④ 检索链路 `git diff` 为空 | 视图/函数 DROP / 路由层不启用（只读不写） | **零**（全部指向现有单库） |

| **Step 7** | 租户层收敛 + 治理面 + 容量分级（§3A.8 D5） | L1 可用场景清单 / 库可见性上限 / 版本钉定 / 配额 + 草稿→发布→审计 + `provenance` + 热/温/冷分级与阈值监控 | ① 越界收紧被拒（400，非静默）；② `provenance` 能回答「这个 `top_k` 来自场景还是租户」；③ `checksum` 并发保存被拦；④ 发布新版本后旧钉定客户端行为不变；⑤ 容量看板能按 `M_A(N)` 公式算出 postgres 侧累计内存 | 租户层全部 nullable，读不到 → 落回平台默认；分级配置置回「全部温」 | **零**（未配置租户 = 现状） |

### 7.1 为什么是这个顺序（依赖链，不是偏好）

```
Step 1（有地方放值）
   └─▶ Step 2（有办法把调用方路由到值）
          └─▶ Step 3（值真的被读到 —— 第一次跑 A/B）
                 └─▶ Step 4（值开始影响派生数据 —— 唯一「重算」不可逆的一步）
                        └─▶ Step 5（库有目录、连接有路由 —— 但全部指向现有库，零影响）
                               └─▶ Step 6（首个场景迁出 —— 唯一「数据搬迁」不可逆的一步）
                                      └─▶ Step 7（多租户 / 多部门收敛 + 容量分级 —— 管理面）
```

**Step 4 必须在 Step 6 之前，不能并行**：Step 4 改的是「数据怎么算」（DNA / 分块 / 抽取），Step 6 改的是「数据在哪」（库）。两者同时变，一旦出现「某场景召回变差」，**无法区分是口径变了还是库变了** —— 这就是研究简报 §六.3 记录的「配置漂移」最难查的形态。先锁定口径（Step 4 验收 = 指纹与过期视图可解释），再搬库（Step 6 验收 = 逐条 diff = 0），每一步只引入一个变量。

**两类不可逆性的区别**（这是 7 步而非 5 步的核心理由）：

| 不可逆类型 | 步骤 | 失败代价 | 撤回方式 |
|---|---|---|---|
| **重算不可逆**（算出来的数据变了） | Step 4 | 重跑全链：解析 → 分块 → 嵌入 → 抽取 → wiki | 无法撤回，只能重算（时间成本） |
| **搬迁不可逆**（数据位置变了） | Step 6 | 数据在新库、连接指向旧库 → 「一半文档查不到」；或双库同时服务 → 结果不稳定 | 库位改回 `default` 即**立刻**恢复（数据不丢），这是搬迁比重算更容易回滚的原因 |

### 7.2 每步的禁止事项（防步子迈大）

| 步 | 禁止 |
|---|---|
| Step 1~2 | 禁止改 `retrieve/` 任何语句块；禁止把场景值接进主链 |
| Step 3 | 禁止一次性把全部 Policy 参数接入（先 3 个无损参数）；禁止在开关开启时改动链拓扑 |
| Step 4 | 禁止「顺手」改 `CHUNK_*` 常量值（会让 217 条基线不可比）；禁止让旧 chunk 在**硬 DNA** 不匹配时进入**向量路**候选集（必须空集，不是低分片）；**禁止把口径过滤扩到关键词路** —— 三条硬 DNA 列只改变**向量**、不改变 `chunk.content`，关键词路判正文，命中的是正确内容，加过滤只有召回损失、零收益；`chunker_version` 属软 DNA，**不得**据此排除（判据与反证见 `第五阶段-Step4B-详细设计.md` §A.3，四条非向量路径的清单见其 §C.2） |
| Step 5 | 禁止在开启路由的同时迁库（两步分开：Step 5 只建目录与路由但**全部指向现有库**）；禁止让路由层「猜」库（解析不到就报错，不回落默认库） |
| Step 6 | 禁止一次迁多个场景（一次一个，单个可回滚）；禁止迁库时改 DNA（一变量原则）；禁止「同一场景两个库同时服务」（会一半文档查不到且不报错） |
| Step 7 | 禁止给场景表单暴露 §6 的 8 类维度；禁止把库位做成可编辑表单项（属部署动作）；禁止「先上 `WHERE tenant_id` 当隔离」（研究简报 §5.1：pgvector 在近似索引下过滤发生在索引扫描**之后**，10% 匹配 × HNSW 默认 `ef_search=40` 只回 4 行，**不报错**） |

### 7.3 验收口径：为什么不再用「N passed」这种绝对数字

Step 1 / Step 5 的验收信号原本写「638 passed」。这个口径有三个问题，Step 5 起改用**失败集合**：

1. **数字会自然过期，而且过期后没人敢改**。当前全量已是 1343 tests，`638 passed` 在任何新代码上都不可能成立 —— 于是只有两条路：被无声忽略，或者有人去「凑」一个 638（少收集、多跳过）。两种都是假绿。
2. **passed 变多不代表没坏**：新增用例会让总数上涨，同时坏掉 3 条也能被净增长掩盖；反过来总数下降也可能是「有人删了用例」。单看 passed 数分不清这三种情况。
3. **真正要守的是「没有新增失败」**，不是「总数是多少」。总数是症状，失败集合才是判据。

**Step 5 起的验收口径（可执行）**：

- 改动**前**在目标环境跑一次全量，junit xml 留档作为基线；
- 改动**后**再跑一次，判据是 `failed_after − failed_before = ∅`（按 nodeid 集合做差，不是比数量）；
- 同时要求 `skipped_after ≤ skipped_before`：**禁止用新增 skip 换绿**（skip 是验收的逃逸口，与放宽断言同等性质）；
- 基线必须注明环境：有无 `SCENARIO_TEST_DB_URL` 会改变 skip 集合（实测有库 15 / 无库 107），跨环境只能比较 `failed`，不能比较 `skipped`。

**当前基线（2026-11-22 实测，Step 4B-1 收尾后）**：

| 环境 | tests | failed | errors | skipped |
|---|---|---|---|---|
| 有 `SCENARIO_TEST_DB_URL`（真库） | 1343 | 2 | 0 | 15 |
| 无 `SCENARIO_TEST_DB_URL` | 1343 | 2 | 0 | 107 |

两条 failed 均为环境类（本机无网）：`tests/test_health.py::test_openapi_contains_health`、`tests/wiki/test_worker_and_script.py::test_rebuild_wiki_script_fails_closed_when_disabled`，都是 `socket.gaierror [Errno 11001]`。**基线里保留它们，而不是为了让数字好看去修或跳过** —— 它们代表「这台机器没有那个外部依赖」，是环境事实，不是代码结论。

## 9. 架构范式 P（决策 + 理由，第一性原理推导）

> P 是**开放多维决策集**（不是四选一）。逐子维度先给判据，再给结论；案例只作印证。

| 子维度 | 决策 | 第一性原理理由（判据先行） | 业界印证（引自研究简报） |
|---|---|---|---|
| **扩展方式** | **插件化（受限）**：新增一个场景 = 新增一行配置；新增一种**能力**（如第四路召回）= 新增一个能力包 + 一个开关，**必须默认关** | 判据 = 变更频率。场景是高频变更对象（产品 / 算法自助），能力是低频对象（发版）。把高频对象做成代码 = 需求排队；把低频对象做成配置 = 配置面爆炸 | Vespa 的 `rank-profile`（一个 schema 定义多个 profile，查询时按名选）↔ 场景行；本项目 `GRAPH_*` / `WIKI_*` 已是这个形状 |
| **配置方式** | **声明式（数据库行 + 版本）**，**不是** DAG（有向无环图）管线 | 判据 = 需要表达的是什么。本项目场景差异集中在**参数取值**与**集合绑定**，不涉及步骤顺序 → 声明式的表达力刚好够，DAG 的表达力用不上而成本全付 | 反面印证：RAGFlow 自己都在给 DAG 加护栏（每类节点限一个、Checklist 校验、发布版本），说明自由编排的代价已大到必须用约束换回来 |
| **部署拓扑** | **单机部署 + 无状态适配层**（MCP 适配层仅转发；主 API 单 uvicorn worker，QPS 平台约 4.5 是已知瓶颈） | 判据 = 当前瓶颈位置。瓶颈在单进程与 CPU 推理，不在调度。引入分布式只增加故障面 | 本项目已知缺口（`AGENT_CONTEXT.md` §10：单 uvicorn worker、需先改 prometheus multiprocess 再谈扩容） |
| **编排模式** | **中心化、单执行链、固定拓扑**；场景只改参数 | 判据 = 任务是否有独立可并行的子结构。RAG 主链是**强串行依赖**（召回→融合→补全→重排→闸门→生成→校验），并行收益低而协调成本高 → 不上多编排 | 若上多 Agent 会命中「过度分解」反模式（`production-checklist.md` 多 Agent 反模式自查） |

**为什么不做「场景级 DAG」——三条独立理由（任一条成立即可否）**：

1. **表达力错配**：场景差异在参数，拓扑本来就一样；给不需要的维度开自由 = 纯粹的负债。
2. **可验证性崩塌**：拓扑可变 → 217 条评估集不可横向比（研究简报 §三：pipeline jungle 的失败模式正是「评估集跑不出可比数字」）。
3. **失败不可归因**：拓扑不同则「这个场景答得差」无法区分是参数问题还是链路问题。

## 10. 模型组合与任务分派（强制项）

### 10.1 形态判定

> 本文设计的对象是 **RAG 平台（tool provider）**，它本身不是 agent（没有自主循环、不选工具）。但**其内部执行链是异质多步骤**，必须做分派表。

**判定：形态 B（单执行链 + 循环内多档模型）**，不是 A 也不是 C。

| 质疑（纪律要求显式做） | 结论 |
|---|---|
| 为什么不是 **A 单模型**？ | 链路内步骤的**成本敏感度差一个量级以上**：离线实体抽取对每 4 个 chunk 调一次 `LLM`（全库逐篇），生成对每次用户提问调一次。同一档模型承担两者 = 要么抽取太贵、要么生成太弱。**成本敏感 + 任务异质 → 分档条件成立** |
| 为什么不是 **C 多智能体**？ | 主链是强串行依赖，无「可拆分的独立子任务」。多 Agent 的唯一合理位置是「生成 vs 评估分离」（§13 第 7 项），而那已用「独立模型调用 + 独立上下文」实现，不需要多 agent 拓扑 |
| 分档有没有「用大炮打蚊子」？ | 有一处**必须点出**：`Query` 改写 / 拆解用主模型是浪费（输出约 100 字符的 JSON）。但**不能随意换更小模型** —— `QUERY_REWRITE_TIMEOUT_SECONDS` 由 5→12 的依据是本机上游实测约 15 token/s、真实耗时 5.41 / 6.88 / 9.46s（`decisions.py` 原文）；换更弱模型可能更慢或 JSON 合法性下降 |

### 10.2 任务-模型分派表

> 具体模型取项目已验证的现役项（不虚构规格）；单价未核实的不填数字。

| 步骤 | 档位 | 具体模型（项目现役） | 理由 | 成本 / 延迟预算 |
|---|---|---|---|---|
| 查询归一 / 词元化 / ILIKE 模式构造 | **确定性代码** | — | 答案可枚举（2-gram 预切分 + 3 字窗口 OR），不需要语义理解 | 单路 p95 4.8ms（FTS）/ 10.7ms（ILIKE），本项目实测 |
| 权限四闸门下推 | **确定性代码** | — | SQL 谓词 + `acl` 包，答案可断言 | 随召回 SQL 一并执行 |
| RRF 融合 / 章节补全 / 预算裁剪 | **确定性代码** | — | 十余行排序逻辑；「不值得引语言模型框架」（`decisions.py` RRF 注释） | 微秒级 |
| Query 改写 / 澄清打分 / 链式拆解 | **快速低价 LLM** | `deepseek-v4-flash`（当前 `llm_model`） | 封闭输出（百分制 + 是否拆解 + ≤3 子问题），任务简单、容错有兜底（超时 / 解析失败 → 回退原问题） | 改写 12s 超时、拆解 10s 超时（均为本项目实测定值） |
| 离线实体 / 关系抽取 | **快速低价 LLM** | `graph_extractor_model`（空则回退 `llm_model`） | 结构化输出（类型闭集 + 长度上限），单次 4 片，可失败重试 | `GRAPH_EXTRACT_BATCH_CHUNKS=4` ≈ 2K token 输入（`decisions.py` 原文） |
| wiki 页生成 | **快速低价 LLM** | `wiki_generator_model`（项目曾用 `qwen-flash` 做静态建页） | 摘要类任务，可人工复核 | `WIKI_INPUT_MAX_CHARS` 限输入 |
| 答案生成（主链） | **强力 LLM** | `llm_model`（可升级 `deepseek-v4-pro`，约 3.1 倍价格，本项目 `decisions.py` 注释） | 开放生成、跨片综合、冲突披露，是唯一「答错要负责」的步骤 | 上下文上限 32000、输出预留 4000 |
| 知识治理四维审查 | **强力 LLM（独立上下文）** | 与生成同档但**不同调用**；`prompt` 锁定区含三类禁止约束 | 评估者需理解语义；独立性由「不看生成推理链 + 只看原文」保证 | `GOVERNANCE_PROMPT_MAX_CHARS=12000`、每轮 50 任务限流 |
| 引用双向校验 / 拒答判定 / `PII`（个人可识别信息）脱敏 | **确定性代码** | — | 引用必须由程序从可追溯来源绑定（不许生成方自由发挥，`production-checklist.md` V 层） | 字符串比对级 |
| Embedding / Rerank | **专用小模型** | `bge-m3`（1024 维）/ `bge-reranker-v2-m3` | 不是 LLM 档位，是固定功能组件 | rerank 超时 3s，超时降级为向量分 |

### 10.3 token 预算按档位分配（口径，不是虚构数字）

| 口径 | 说明 |
|---|---|
| 分配依据 | 按**调用次数 × 单次 tokens** 而非拍占比。离线抽取 = 文档数 × (chunk 数 ÷ 4) 次；在线生成 = 请求数 × 1 次 |
| **必须计入但最易漏的一项** | **评估 / 验证步骤的成本**：`run_eval.py` 217 条 × 每轮 = 一次全量生成的费用，**且每个场景要自己的基线**。Step 3 的验收就是一次全量 A/B —— 这是显性支出，必须写进预算（`production-checklist.md`：「别让它成为预算外的隐性支出」） |
| 当前不可给准确占比的原因 | 本机无按档位拆分的 token 计量（`caliber` 只记 `llm_model` 等，不按步骤拆分 token）→ **未知区 U4**：需先加按 `step` 标签的 token 计数器 |
| 级联升级条件 | 现有两处已验证的「升级」：① 检索充足却拒答 → 重试一次生成（条件 ≥3 片 **且** top1 ≥ 0.70，本项目 217 条标定）；② 复杂度高（改写分 < 90）→ 走链式多轮检索。**没有**「换更大模型」的自动升级（需先标定，属 §16 待办） |
| 降级链 | 重排不可用 → 降级为向量余弦分（已实现，`metrics: rag.rerank.degraded`）；LLM 首 token 超时 15s → 走拒答 / 错误；图召回超时 → 不阻断主链，透传 `graph_degraded_reason`；改写 / 拆解超时 → 静默回退单趟检索（**已实现且是主链稳定的关键**） |
| 评估者档位与生成者档位 | 评估者（治理审查）可与生成同档，但**必须独立上下文、不看生成推理链**；`COT_REASONING_EXPOSED=False` 已保证推理链不外泄，评估侧也拿不到 |

### 10.4 缓存与重算账（最易被整份漏掉的一节）

| 项 | 现状 | 场景化后的风险 | 应对 |
|---|---|---|---|
| **前缀稳定** | 生成侧上下文 = `system`（锁定区 + 可编辑区）+ 长期画像 + 短期历史 + chunks + 问题；`system` 与锁定区稳定 | 若允许场景改 `system` 可编辑区 → 不同场景前缀不同（可接受，前缀按场景隔离）；但若把「场景名 / 版本号」这类易变字符串插进 `system` → 每次发布版本前缀全失效 | **规则**：易变内容（版本号、时间戳、场景统计）只进尾部或不进 prompt；锁定区**永不可配**（§6 第 6 条） |
| **重写失效代价** | 压缩历史 → 前缀重写；上下文上限 32000 使其在正常流量下**很少触发**（原 128K 时「永不触发」是设计错误，已修正） | 场景级预算若调小 → 压缩频率上升 → 重写次数上升、成本反而增加（省了上下文，赔了重算） | 场景预算设下限护栏；观测 `compression_count` |
| **结果复用** | 章节补全 / 表格回捞 / 图召回都做「先排重后裁剪」（新片不重复占名额） | 若场景允许 `recall_top_k` 极大 → 排重成本上升 | `top_k` 上界 20（§3.3） |
| **不可缓存的项** | `ask` 非幂等（每问一次都写 message + 计费） | 调用方重试 → 重复计费 | §8 Q9（幂等键） |

## 11A. 技术栈选型（继承现状，不新选型）

> **本方案的定位是「在既有栈上加一张策略寻址层」，不是换栈。** 因此本节只需说明「继承什么」与「明确不引入什么」。

| 项 | 选型 | 理由 |
|---|---|---|
| 语言 | Python 3.12 | 全仓既有；场景 resolver 是纯函数 + 一次 DB 查询，无性能理由换语言 |
| 运行时 / 框架 | FastAPI + SQLAlchemy + asyncpg + arq | 场景表读写走既有 ORM；不新增 Web 进程 |
| 关键依赖 | `fastmcp`（MCP 服务端，已在用）、`pydantic`（场景配置校验，已在用） | 复用既有依赖，零新增常驻组件 |
| 数据存储 | PostgreSQL 16 + pgvector（场景表与版本行落同库） | 与 `chunks` 同库才能在一个事务里做「读场景 → 检索」；跨库会引入分布式一致性问题 |
| 运行环境 | Docker Compose **11 个服务、其中 `migrate` 为一次性任务，常驻 10 个**（现有编排，见 §3A.4.1 事实基线） | 不新增常驻容器；不引入配置中心 |

**明确不引入（每条给理由，防止第二阶段"顺手引入"）**：

| 不引入 | 理由 |
|---|---|
| 配置中心（Apollo / Nacos / Consul） | 场景表需要**版本 + 发布态 + 乐观并发 + 审计**四件事，配置中心只解决「下发」；且引入外部依赖违背「数据不出内网 + 少容器」的私有化前提 |
| YAML 管线引擎（DAG 编排器） | 见 §9 范式 P：表达力错配 + 可验证性崩塌 + 失败不可归因 |
| 语言框架（LangChain / LlamaIndex 等） | 本项目定位是 harness（运行时宿主），不是 import 进来写代码的库；且主链已手写 RRF 十余行，引框架属净负债（`decisions.py` RRF 注释原话：「10 行代码不值得引语言模型框架」） |
| 外置向量库（Milvus / Qdrant / Weaviate） | 场景化不改变「向量存在哪」；换库属另一议题，与本方案正交 |

## 11C. 关键接口签名（只给形态，字段与错误码见 §16）

> 阶段边界要求：**不逐字段定义**。以下给函数名 + 语义 + 不变式；入参/出参字段清单、错误码表 → §16 #4、#5。

## 11D. 核心数据结构（只给对象与三段归属）

| 结构 | 性质 | 三段归属 | 关键不变式 |
|---|---|---|---|
| `ScenarioSnapshot` | **不可变**（frozen，构造后只读） | `dna` / `policy` / `binding` | ① 只能由 `resolve_scenario()` 构造；② 不持有 DB 会话（防延迟加载导致「读场景时又查库」）；③ 段内字段清单 → §16 #3 |
| `IndexProfile`（既有） | 不可变 dataclass | 由 `dna` 派生 | 字段名与 `fingerprint` 算法**一字不改**（D-1；改算法 = 全部历史指纹失效） |
| 场景版本行 | DB 行，`published` 后只读 | 承载三段 | 版本号单调递增；同场景唯一生效版本；`checksum` 支持乐观并发 |
| `caliber` 快照（既有） | 每答案一份 | 审计面 | 场景化后必须含场景键 + 场景版本（§14 S↔V 交叉检查） |

**为什么 `ScenarioSnapshot` 必须 frozen**：R9 反例的缓解手段 —— 注入的是不可变值对象而非可变配置；同时防止「检索跑到一半场景被改」这类不可复现的故障。

## 11E. 配置文件格式（本方案**不用配置文件**）

> 这是个**明确的架构决策**，不是省略：场景配置落在**数据库行 + 版本**，不是 YAML / JSON 文件。

| 载体 | 形态 | 谁写 | 说明 |
|---|---|---|---|
| 场景表 | 一场景一版本一行（`draft` / `ready` / `published` / `archived`） | 管理面（产品 / 算法） | 三段分组存储；字段清单 → §16 #1/#3 |
| 版本钉定 | 租户 / 应用行上的一个引用列 | 管理面 | 钉具体版本，不自动跟新版（Q4 推荐） |
| `.env` | **仅作 `default` 场景的初始种子值** | 运维 | 场景化后**不再是运行期真源**（D-2 / U9） |

**为什么不用 YAML / JSON 文件 —— 三条硬理由**：

| 理由 | 说明 |
|---|---|
| 文件做不到「版本 + 发布态」 | 需要草稿 / 发布两态 + 单调版本 + 归档，文件只能靠目录约定伪造（研究简报 §六.2 三道闸的第一道） |
| 文件做不到「乐观并发」 | `checksum` 冲突检测需要服务端原子读改写；多实例部署时文件共享本身是问题（Dify 的草稿哈希口径即为此设计） |
| 文件容易把物理 ID 写进去 | 违反 I-4（跨环境断链）；DB 行可以用外键 + 环境映射表把逻辑键解析成物理 UUID |

## 12. 魔鬼代言人：反例与反驳

> 规则：每条反例必须指明「在什么条件下它成立」。不能成立的写「为什么不成立」；成立但可接受的写「为什么可接受」。

### 12.1 对「候选 ③ 凭证绑场景」的反例

| # | 反例（攻击） | 判定 |
|---|---|---|
| R1 | **一个 agent 服务多个业务线时必然要两个凭证**，而调用方往往只有「一个 MCP 地址 + 一套配置」，运维会倾向把两个场景合并成一个"大场景" → 最终回到「一个巨大 kb 集合 + 一套中庸参数」 | **成立且需承认**。缓解：① 场景组（§8 Q6）留二期；② 一期在文档层面明确支持「一个 agent 配多个应用」。**不接受"让它先合并"** —— 合并后越权面反而扩大 |
| R2 | **场景绑定是后端改的，调用方看不见** → 排查「为什么这个 agent 召回变了」时，调用方看不到自己的场景版本，只能问平台 | **成立**。缓解：`knowledge_capabilities()` 只读工具（§5.5 可选项）+ 响应 `meta` 回带场景键与版本（不进正文）。列 §16 待办 |
| R3 | **凭证泄露的影响半径变大**：原来泄露一个应用密钥只泄露一组 kb，现在还泄露一套策略（可被观察出阈值 / 开关） | **部分成立**。缓解：策略非机密（阈值不构成秘密），密钥本就只在创建时出现一次、库里只存哈希。真正的残余风险是「推断本平台检索策略」，属可接受的信息泄露 |
| R4 | 若某天要「场景由调用方自选」（①的诉求），③ 需要一次破坏性变更 | **成立但代价可控**：§5.4 真值表已预留「凭证未绑 + 请求带 scenario」这一行，即 ① 的能力可以**在同一份实现里**逐步放开，不需重写 |

### 12.2 对「场景三段切（DNA / Policy / Binding）」的反例

| # | 反例 | 判定 |
|---|---|---|
| R5 | **DNA / Policy 的边界会漂移**：今天 `chunk_overlap` 算 DNA（改了要重建），明天有人论证「重叠只影响边界，老数据仍可比」→ 慢慢全变 Policy，重建纪律失效 | **成立，是本设计最真实的风险**。缓解：边界不由人决定，由 §4.5 真值表决定 ——「旧数据是否仍可检」是**可执行断言**（指纹匹配测试），不是判断题。改边界必须先改测试 |
| R6 | **三段切增加概念数**，产品经理看不懂「DNA 是什么」 | **成立**。缓解：后台表单只暴露 Policy；DNA 只**只读展示** + 「换 DNA 需走运维流程」说明。概念复杂度留在代码与文档，不推给使用者 |
| R7 | `chunker_version` 既在 DNA 又「不硬过滤」（`index_profile.py` 原文：只作建议重切提示）→ 名为 DNA 实为 Policy，自相矛盾 | **成立，是既有设计的已知张力**。判定：`chunker_version` 属「**软 DNA**」—— 不匹配不拒绝检索（向量仍可比），但必须在 `needs_reindex` 视图里显式暴露。本设计**保留**该行为，并在 §6 第 3 条写明「值可配、派生与盖章不可配」 |
| R8 | 场景表会重演「配置债」：配置比代码大、评审比代码松（Sculley 2015） | **成立**。缓解三道闸（全部来自研究简报 §六.2 的一手出处）：草稿→发布两态、`checksum` 乐观并发、schema + 版本校验。**闸门只降低概率，不消除** → 写进 §15 |

### 12.3 对「演进 7 步」的反例

| # | 反例 | 判定 |
|---|---|---|
| R9 | Step 3 要给 `retrieve()` 加参数注入 → 与 `decisions.py` 的纪律「MUST 通过 `decisions.X` 读取常量，不得把值拷进命名空间」冲突：一旦参数化，单测就无法用 monkeypatch 锁口径 | **成立，且是本方案最大的工程风险**（§15 U3）。缓解：注入的是**不可变快照对象**（`frozen dataclass`）而非散装参数；默认场景的快照值 = 常量值，因此 monkeypatch 常量仍能影响默认场景（单测兼容）。**这条必须在 Step 3 第一天用一条垂直切片验证，不能等做完** |
| R10 | Step 4 的「多 DNA」会让 `needs_reindex` 视图成为永久债务（没人看 → 覆盖率虚高 → 运维学会无视） | **成立且本项目踩过同类坑**：`capabilities.py` 注释记录「曾用『全部未删除文档』当分母，结果一篇失败文档让就绪度永远停在 20/21 —— 闸门永远红，运维很快就学会无视它」。缓解：分母口径必须与「补建脚本的选取条件」同一批文档 |
| R11 | 5 步实际可能变成 5 个半成品（每步"够用就行"，最后没有一步真正收口） | **部分成立**。缓解：每步给**硬验收信号**（可跑的命令 / 可断言的测试），不达标不进下一步。Step 3 的 217 条 A/B 是**唯一一道能拦住"看起来对"的门**（本项目三轮实测证明这道门真的会拦：开态漏答率 0.00% → 0.90% → 1.80%，「不劣化」不成立） |

### 12.4 对「不可配置清单」的反例

| # | 反例 | 判定 |
|---|---|---|
| R12 | 把 `RRF_K` / 阈值锁死 → 不同领域最优值本就不同（法务文档 vs 产品手册）→ 锁死等于放弃质量 | **部分成立**。区分：阈值**数值**已允下沉 L2（区间 `[0.40,0.70]`）；`RRF_K=60` 锁死是因为它只影响「排名融合的相对权重」，且改动会让 217 条基线不可比。**若未来有证据表明不同领域 RRF_K 最优值差异显著，可升级为 Policy（带区间）**，但必须先有 A/B 证据 |
| R13 | 「尝试配置应报错」会让运维难受（想试试能不能改 embedding） | **可接受**：报错信息里给「怎么做才对」（改 `.env` + 重建流程文档）。**静默忽略的代价远高于报错**（研究简报 §二.2：「静默忽略是最坏的一种：调用方以为生效了」） |

### 12.5 对「数据层隔离」（§3A）的反例

| # | 反例（攻击） | 判定 |
|---|---|---|
| R14 | **分库是为了隔离，但「一场景一库」会让平台的横向能力失效**：跨场景的质量对比、全局坏例回流、A/B 都变成「跑 N 次」 | **部分成立且已部分支付**：评测按场景各有基线（§3A.9 / §13 第 6 项），跨场景数字本就不可比（即便同库也不同策略）。代价是**评测成本 × N**（U4 已记）。缓解：`eval_runs` 留控制库 + `caliber` 带场景键，使「跨场景汇总」在**指标层**仍可做（不做内容层合并） |
| R15 | **分库会让「一个场景的故障变成局部不可用」变成「运维要逐个库查」** | **成立**：N 个库 = N 个故障点。缓解：① `db_routing` 统一健康检查与启动自检（库不可达即 fail-closed 报错，见 §3A.6.2 判定点 7）；② 审计统一写控制库（I-8），所以「哪个库出问题」一条 SQL 可查；③ 分级策略把多数场景压在**同一个** database 实例上（温档），故障面并未真的乘 N |
| R16 | **§3A.4.3 的内存公式用了 300MB/场景的假设值**，若真实值是 1GB，10 个场景就是 10GB，16GB 直接不可交付 —— 结论会翻转 | **成立，是本方案最需要实测的数字**（U10）。缓解：① 公式与假设值分离，替换实测值即可复算；② 分级策略让「乘 N 的只有热场景」，温/冷不乘；③ 若实测偏大，默认档位可从「温」进一步收到「热场景例外制」。**这条反例成立恰恰说明不能把 300MB 当结论**，故 §3A.4.3 已标「示例假设」 |
| R17 | **控制库会变成新的单点与瓶颈**：所有场景的鉴权、配额、审计都打同一个库 | **成立**。缓解：① 控制库只存元数据不存正文（§3A.2.2 纪律 2），体量可控；② 鉴权读可缓存（现有 Redis 已在用）；③ 审计是追加写，可后续分表/归档。**但要承认**：分库把「一库爆炸」换成了「控制库热 + N 个场景库冷」，不是消灭单点 |
| R18 | **分库之后 I-9（分库不替代授权）容易被当成「已经安全了」而放松 ACL** | **这是最危险的一条，必须靠机制而非自觉**。缓解：① 四闸门 SQL 是**唯一真源**（`PUSHDOWN_WHERE_SQL` 一个字符串，图/wiki 复用），分库不改它；② 越权用例（跨 kb / 高密级 / deny 邻居）在分库形态下必须**仍为零命中**（§3A.12 I-9 的断言）；③ 端到端测试必须在**分库形态**跑一遍，不能只在单库跑 |

| # | 必答项 | 结论 |
|---|---|---|
| **1** | **执行环境**：工具在哪跑？凭证是否进执行环境？ | 工具在 **api 容器内**执行（MCP 适配层只做 header 映射 + 转发，不实现任何检索 / 问答 / 权限逻辑）。**凭证不进执行环境**：应用密钥明文只在创建响应出现一次，库里存 SHA-256；MCP 层把入站 header 映射为双认证头，不落日志、不入库。**场景化禁止把密钥或端点下沉到场景配置**；**分库后新增一条同款禁令：连接串（host/port/db/user/password）属 L1 部署期，绝不下沉到场景 Binding**（场景只持库位逻辑键，I-7）。写操作影响半径：`ask` / `search` 只写 `conversations` / `messages` / `audit` / `integration_conversations`，**不写知识库内容** → 单向只读能力，这是本平台作为 tool provider 的安全底色。**分库后影响半径的一处变化**：MCP 契约仍是只读，但**运维/迁移脚本**的影响半径从「一个库」变成「N 个库」→ 脚本必须显式声明目标库（I-11） |
| **2** | **错误回喂**：失败如何作为观察回到上下文？如何分类恢复？ | MCP 层：缺身份头 → `ToolError`（调用方 agent 看到可读错误文本）；HTTP 非 2xx → `raise_for_status` 抛给调用方。**分类**：`400`（参数 / 场景越界，**不可重试**，调用方要改请求）、`401/403`（凭证或授权，不可重试，需运维）、`429`（限流，可退避重试）、`503`（知识库暂不可用，可重试）、超时（适配层 `httpx` 120s；可重试但需幂等键，§8 Q9）。**禁止吞异常**：主 API 侧检索异常 → `503` + `logger.exception`，**不返回空结果冒充「没找到内容」**（空结果 = 拒答语义，会被调用方误读为「知识库没这内容」） |
| **3** | **打转检测与熔断**：如何识别原地打转？如何打断？ | **N/A（本层）**：RAG 平台无自主循环，调用方的循环是它的 E 层职责，平台不感知。**等效替代**：① 请求级配额（`daily_token_limit` / `daily_message_limit` / `rate_limit_per_minute`，已实现）；② 内部防重复：`GENERATION_REFUSAL_RETRY_ENABLED` 最多重试 **1 次**且带分数门槛（防「重试到满意为止」）；`CHAIN_MAX_SUBQUESTIONS=3`；每个 LLM 调用都有超时；③ **需补**：同一调用方对同一 `(场景, query)` 的高频重复应能在 `/metrics` 看出（防知识库被逐条抽取 —— `production-checklist.md` 横切关注点） |
| **4** | **记忆治理**：可信度、归属、失效条件 | 已实现且较完整：三级记忆（`short` / `long` / `permanent`）；长期记忆**只读「偏好」类**（`MEMORY_LONG_TERM_KINDS = {"preference"}`）；写入过滤器 `BLOCKED_MEMORY_PATTERNS`（引用编号痕迹、拒答文案、密级标识、内部权限字段名）；`MEMORY_SOURCE_TRACE_REQUIRED=True`（权限变更时按文档反查清除的唯一依据）；**长期记忆 MUST NOT 含文档内容**（那是权限副本，会绕过实时判定）。**场景化新增约束**：场景切换**不应清空**用户长期偏好（偏好与知识集合无关），但**场景快照变化必须写审计**（否则「为什么这个 agent 今天答得不一样」无从追溯）。**未验证推测不得升级为事实**：`MEMORY_WRITE_CONFIDENCE_THRESHOLD=0.6`，低于它只写短期 |
| **5** | **外部副作用幂等** | 平台副作用 4 类：① `messages` 落库（每次 `ask` 一条，**非幂等**）→ §8 Q9 建议 `request_id` + 去重窗口；② `audit` 记录（只追加，天然幂等）；③ `integration_conversations`（按 `conversation_id` 唯一，幂等）；④ 知识库写入（**当前 MCP 契约不提供**，故无风险）。**关键判断**：「会话恢复 ≠ 外部行动恢复」—— RAG 侧无外部行动（不调第三方写接口），本项风险低；**唯一例外是 LLM 调用计费**：重试 = 重复付费，这是 `request_id` 幂等的真实价值 |
| **6** | **证据版本绑定**：验证结论如何绑定版本？版本变更后如何失效？ | 本设计的**核心机制**，四层绑定：① **向量**：chunk 行盖 `embedding_model` / `embedding_dim` / `embedding_text_version`，检索 SQL 按当前 `index_fingerprint` 过滤（fail-closed）；② **分块**：`chunker_version` 盖章，只作「建议重切」提示（软 DNA）；③ **图**：`graph_entity_mentions` / `graph_relations` / `documents` 盖 `extractor_model` + `prompt_version`，检索侧 `WHERE` 双列匹配；④ **wiki**：`wiki_pages` 盖 `generator_model` + `prompt_version`，`caliber_mismatch` 进能力横幅。**评估结论的版本绑定**：`eval_runs` 存 `case_fingerprint` + `caliber.config_fingerprint`；两次跑只有在 `case_fingerprint` 一致时才可比（`latest_eval_run` 已实现，且必须显式传 `--baseline-id`，否则开态轮会盖掉关态基线 —— 本项目踩过）。**场景化新增**：`caliber` 需增「场景键 + 场景版本」，否则跨场景 A/B 数字会被误认为同一口径 |
| **7** | **生成者与评估者分离** | 三处分离，全部已实现：① **引用校验**：`citations` 由**程序**从可追溯来源绑定（chunk_id + 文件 + 页号），双向校验（答案里的编号必须存在于 citations，citations 必须被答案引用），生成方无法伪造；② **治理四维审查**：独立 LLM 调用 + 独立 `prompt`（锁定区含「仅依据给定文档内容判定 / MUST NOT 臆造 / MUST NOT 改写原文」三类约束 + 启动自检强制校验）；③ **拒答判定**：由代码按阈值 + 接地结果判定（`GROUNDING_CHECK_ENABLED` 剥离无归因句子，空则降级拒答），**不由模型自评**。**评估者档位 vs 生成者**：可与生成同档，因为独立性靠「独立上下文 + 不看生成推理链 + 显式标准」保证，不靠换模型。**推理链不外泄**由 `COT_REASONING_EXPOSED=False` 强制（启动自检拦） |
| **8** | **前缀稳定与缓存命中** | **稳定区**：`qa_system` 锁定区（拒答文案、冲突披露要求等，启动自检强制存在）+ 工具披露序列（MCP 工具**常驻注册、不按场景动态增删** → 序列确定）+ 序列化确定性（`config_fingerprint` 用 `json.dumps(sort_keys=True)`，同一组配置恒得同一指纹 —— 本项目已验证的确定性序列化范式）。**可变尾部**：chunks（每轮重取）、问题、历史只追加。**场景化三条禁令**：① 场景名 / 版本号 / 时间戳**不得进 `system` 前缀**；② 场景策略**不得改锁定区**；③ 工具 schema **不得按场景变化**（否则调用方前缀失效）。**重写失效预算**：压缩是唯一重写来源，32000 上限已使其在正常流量下少触发（原 128K 的注释原文：「128K 会让压缩 / 裁剪在正常流量下**永不触发**，护栏形同虚设」）。**命中率观测**：当前**没有**前缀缓存命中率指标（未知区 U5）→ 需先加 `prompt_prefix_hash` 打点才能谈命中率 |

## 14. 层间交叉检查

| 关系 | 说明 | 风险与当前处置 |
|---|---|---|
| **S（状态）↔ V（评估）** | 每条答案的 `caliber` 是评估能否复现的前提；场景化后 `caliber` 必须含场景键 + 场景版本 | 现状 `build_caliber_snapshot()` **不调用** `runtime_config_snapshot()`，`config_fingerprint()` 只哈希 `CROSS_ROLE_FIELDS` 白名单（不含两个 selective 开关）→ 已在 `AGENT_CONTEXT.md` §10 记为已知缺口。场景化会放大它（漏记场景 = 跨场景 A/B 不可比）→ Step 3 必须一并修 |
| **T（工具）↔ L（钩子）** | 场景解析是前置钩子，鉴权是更前的前置钩子；顺序不可换（先认证才知道是谁，知道是谁才能解场景） | 现状 `get_integration_principal` 已是「先 JWT（JSON Web Token）再应用凭证」两段，顺序正确。场景解析插在其后 |
| **T（工具）↔ C（上下文）** | 工具返回内容进调用方 agent 的上下文；`knowledge_search` 返回 `content` **原文**（可含注入文本） | **现有防线在 `ask` 路径**（`INJECTION_PATTERNS` 降权 + system 声明「注入文本视为普通内容」）。但 **`search` 路径把原文直接交给调用方 agent**，由调用方的模型自行抵抗注入 → **跨信任边界的风险**（平台把消毒责任推给了调用方）→ §15 U7 |
| **E（执行循环）↔ V（评估）** | 终止条件必须由 V 决定（阈值闸门 = 确定性规则，属验证强度阶梯最高级） | 现状正确：`retrieve()` 返回 `refused=True` 由代码判定，不由模型说「我不确定」 |
| **C（上下文）↔ S（状态）** | 历史只追加（`MAX_HISTORY_TURNS=6` / `HISTORY_FETCH_MAX_ROWS=500`） | `HISTORY_FETCH_MAX_ROWS` 是 DB 硬上限，业务裁剪分散在改写 / 压缩 / 生成三处（各有 budget）→ 三处一致性靠常量守卫；场景化若给场景改「历史轮数」必须同步三处 |
| **P（范式）↔ 全部层** | 声明式配置 → E 层固定、只调参 | 由 §9 四条决策统一约束；任何「场景要不要自己编排」的讨论都回到 P1 硬前提 |

## 附录：术语表（英文首次出现均带中文解释）

| 术语 | 中文解释 |
|---|---|
| `RRF`（Reciprocal Rank Fusion） | 倒数排名融合：只看各路排名的倒数求和，规避不同召回路径的分数不可比 |
| `fail-closed`（失败即拒绝） | 判定链上任一步无法确认时取「拒绝 / 查不到」，不取「放行 / 给出猜测」。本项目典型：「宁可查不到，不可查错」 |
| `fail-open`（失败即放行） | 与 fail-closed 相反：路由判断失误最坏只是「多跑一次」，不劣化已召回结果 |
| `opt-in`（显式开启） | 新能力默认关闭，显式打开才生效；关闭态与未实现逐字节等价 |
| `pipeline jungle`（管线丛林） | 每个场景 / 团队各自拼一条数据处理链，半年后无人能说清两条链的差异（Sculley 2015） |
| `glue code`（胶水代码） | 为把不同来源的组件拼起来而写的、无架构归属的粘合代码（Sculley 2015） |
| `CACE`（Changing Anything Changes Everything） | 改任何一处都会影响全部输出（Sculley 2015） |
| `DNA`（本设计借用） | 决定派生数据物理同构性的不可变身份集合，改了就要求重建 |
| `Policy`（可调策略） | 改了只影响后续请求、不要求重建的参数集 |
| `Binding`（绑定资源） | 知识集合与凭证的逻辑引用；改错是越权而非「效果差」 |
| `provenance`（来源归属） | 记录每个生效配置值来自哪一层（平台 / 租户 / 场景 / 请求），用于回答「这个值是谁定的」 |
| `caliber`（口径快照） | 本项目概念：每条答案落库的「这次是按什么口径跑的」审计快照 |
| `tsquery` | PostgreSQL 全文检索的查询语法 |
| `GIN`（Generalized Inverted Index） | PostgreSQL 广义倒排索引，用于 `tsvector` 与数组的加速匹配 |
| `ILIKE` | PostgreSQL 大小写不敏感模糊匹配（本项目用 `~*` 正则实现子串匹配） |
| `SSE`（Server-Sent Events） | 服务端推送事件，本项目的流式回答通道（`meta → stage → citations → delta → done / refused`） |
| `MCP`（Model Context Protocol） | 模型上下文协议，把能力以「工具」形式暴露给调用方 agent 的标准 |
| `RLS`（Row Level Security） | PostgreSQL 行级安全策略，引擎级默认拒绝 |
| `PII`（Personally Identifiable Information） | 个人可识别信息（手机号 / 身份证 / 银行卡等） |
| `OWASP` | 开放 Web 应用安全项目，其 fail-safe defaults 是本项目守门开关不可配的业界依据 |
| `HNSW`（Hierarchical Navigable Small World） | pgvector 常用的近似最近邻索引；其过滤发生在索引扫描之后，是多租户共享索引的召回陷阱来源 |
| `LLM`（Large Language Model） | 大语言模型 |
| `instance`（实例） | 一个 PostgreSQL 服务进程 + 一份数据目录（本项目对应一个容器） |
| `database`（库） | 同一实例内由 `CREATE DATABASE` 建立的独立库，各有独立 catalog，**互不可跨库 JOIN** |
| `schema`（同一数据库内的命名空间） | 同一库内的表命名空间；可跨 schema JOIN，靠 `search_path` 定位 |
| `shared_buffers` | PostgreSQL 的共享缓冲池（默认 128MB），实例内存开销的主要部分 |
| `RPO` / `RTO` | Recovery Point Objective（恢复点目标，能容忍丢多少数据）/ Recovery Time Objective（恢复时间目标，能容忍停多久） |
| `federated aggregation`（联邦聚合） | 跨多个数据源分别查询后在中间层合并排序，再统一返回 |
| `pg_dump -d` | PostgreSQL 按库导出（database 级备份），是「一场景一库」能实现独立备份的依据 |
| `postgres_fdw` / `dblink` | PostgreSQL 的跨库/跨实例访问扩展；本章用它说明「跨库查询可行但有代价」，不作为方案 |
| `fail-closed`（失败即拒绝） | 见上（本附录首条）；本章新增用法：库不存在/连不上时**报错**，不得降级为「返回空」 |
