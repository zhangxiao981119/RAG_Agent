### 1.3 两条红线（违反即回滚整个方案）

**红线 A：图与 wiki 只用于召回与导航；进 prompt 的证据与引用永远回到 chunk 原文。**
实体、关系、wiki 摘要都是 LLM 产物，**不得作为引用来源**。本方案在结构上（而非靠注释）保证这一点：

- 图召回只产出 `chunk_id`，最终取的是 `chunks` 表里的**原文行**；图数据本身没有任何进入 `current_chunks` 的代码路径。
- wiki 只产出「额外检索词元」（进 `build_ilike_terms` / `build_fts_query` 的词元集合）与「人工导航页」；**不存在**任何把 wiki 文本拼进 prompt 的函数。结构上不存在这条数据通路 = 红线不可被后人误踩。

**红线 B：图扩展必须先过四闸门；邻居 chunk 绕过 kb/密级/deny/acl 就是越权漏洞；禁止「关了图就跳过权限检查」这种语义。**
落地方式：图扩展的取片 SQL 里直接嵌入 `_WHERE_BASE`（含 `c.is_latest = true`），与向量路 / 关键词路 / 章节补全路**逐字一致**。**不新增、不减少、不重排**任何一个条件 —— 图路径看到的 chunk 集合必须恰好等于向量路可能看到的集合。

## 2. 架构范式 P

> P（范式）是开放的、多维的架构决策集，不是四选一。下表逐子维度给决策与理由，关键取舍附量化依据。

| 子维度 | 决策 | 理由 |
|---|---|---|
| **扩展方式** | **端口-适配器（Ports & Adapters）**：定义 `GraphStore` 端口（4 个方法），`PostgresGraphStore` 是**唯一**实现；`Neo4jGraphStore` 只留一句 `raise NotImplementedError` 的位与文档，**不写实现**。 | 第一性原理：图的存储形态是**可替换的实现细节**，而「四闸门下推 + 口径过滤」是**不可替换的契约**。把契约钉在端口上，实现可换、契约不可绕。不引入 Neo4j 的量化理由：①多一个常驻容器 = 多一份内存占用（生产机 4 核 8GB 起，Neo4j 起步 1~2GB）与多一份排障面；②图规模量级估算：1000 篇文档 × 平均 60 chunk × 每 chunk 8 实体（去重后约 3~5 个新实体）≈ 20~30 万 mention、5~10 万边 —— 这个量级在 PostgreSQL 上走 `(kb_id, src_entity_id)` B-tree + 2 跳自连接是**毫秒级**，Neo4j 的遍历优势要到千万级边才显现；③私有化交付「少一个运行时组件」是可审计性与可运维性的直接收益。 |
| **配置方式** | **部署期声明式**：环境变量 → `Settings`（pydantic）→ 启动自检（fail-closed）→ 能力快照（进启动日志 / `/api/system/capabilities` / `caliber`）。零数据库开关、零运行时开关、零请求级开关。 | 已由管家节点确认（不可推翻）。设计层补充：**这不是"少做一个功能"，而是把"能力存在性"从可变状态降为不可变事实**。运行时开关的价值是「快速回滚 + 渐进放量」，代价是「同一份数据在不同配置下语义不同，且出现问题时不知道当时是哪种配置」。私有化交付里回滚靠镜像与 `.env`，不需要运行时开关。**关闭能力 = 改一个环境变量 + 重启两个容器**，这是可接受的操作成本。 |
| **部署拓扑** | **进程内共库**：api 只读图（在线召回），worker 只写图（离线抽取），共享同一个 PostgreSQL；无新增服务、无跨进程缓存。 | 复用既有 api/worker 双进程模型与既有连接池口径。**代价明确**：api 与 worker 必须读到**同一份**能力配置，否则出现「api 开图召回、worker 不抽取」的静默不一致 —— 这有前车之鉴（只重建 api 镜像导致 worker 跑旧代码，任务照常返回成功）。对策见 §7.4「配置一致性机制」：能力快照 + `config_fingerprint` 双端打印 + 启动日志可比对。 |
| **编排模式** | **固定管线**（不是 agent 循环）：`retrieve()` 内部追加「实体链接 → 图扩展 → 取片」三步串行的确定性步骤。 | 本系统的检索是确定性管线，把图召回包装成「给 LLM 动态调用的工具」是过度设计（会引入工具注册表、描述质量、误调用等一整套问题，而没有任何收益）。 |
| **失败语义（三档分离，本方案最重要的范式决策）** | ① **启动 fail-closed**：配置项开了但依赖缺失 → 拒绝启动；② **在线 fail-open 到 0 路**：图召回超时/异常 → 返回空，问答主链路继续（打点 + 告警）；③ **离线 fail-visible**：单篇文档抽取失败 → 文档照常可检索、`graph_status='failed'` 可见 + 指标 + 上线验收门禁卡住。 | 三档必须分开，否则会出现两类错误：把「单篇抽取失败」升级成「不让服务启动」（脆弱），或把「依赖缺失」降级成「静默不生效」（这正是团队点名要堵的前车之鉴）。**判别标准**：`依赖缺失`（配了却没有）= 启动失败；`数据未就绪`（表在、服务在，只是还没抽取）= 允许启动 + 明确告警 + 可补建；`单条任务失败`（运行时错误）= 可见 + 可重试 + 不阻断其他文档。 |
| **版本口径** | **写入侧盖章 + 读取侧过滤**：图行带 `extractor_model + prompt_version`，检索按当前口径 SQL 过滤，不同口径物理隔离（宁可查不到，不可混查）。 | 与既有 `IndexProfile`（索引口径单一真源）同构。理由同 `index_profile.py` 的原文：混算等于「静默劣化」——不报错，只是答不准。 |
| **在线是否并行** | **串行**（团队判断「与三路并行」被推翻，见 §2.1）。 | 见下。 |

### 2.1 推翻团队判断①：图召回**不能**与三路并行，必须串行

团队判断原文：「图召回作为第 4 路，与三路并行、硬超时（建议 800ms）、失败降级为 0 路」。

**结论：保留「第 4 路 / 硬超时 / 降级为 0 路」三点，但"并行"必须改为"串行"。** 三条独立理由：

1. **`AsyncSession` 非并发安全（硬约束，不是偏好）。** `retrieve()` 全程复用 API 层传入的同一个 `AsyncSession`，代码里已有明确注释：「多轮 MUST **串行**复用同一 session（AsyncSession 非并发安全）—— 同 session 并发会让连接被多协程交叉使用（await 点交错），结果不可预期」。在同 session 上 `asyncio.gather` 两条 SQL，是把已知不可并发的东西并发。
2. **事务 abort 会连锁污染（本项目已踩过）。** README §13.4 有一条 P1：「关键词召回静默崩溃……异常被吞但事务已 abort，同一次检索后续查询连锁失败」。图召回是四条 SQL 里**最可能超时**的一条（递归 CTE），一旦它在共享 session 上超时被 `wait_for` 取消，事务状态不可控 → 后面的 gate / 回捞 / 补全查询全部连锁失败。串行 + 事后 `rollback` 是唯一可控的处置（§9.3 时序）。
3. **连接池容量会跌破基线。** 现状：一个在途问答请求长期占用 1 条连接（`get_db` 的 yield 覆盖整条 SSE 流），检索期再瞬时开 1 条 → 约 2 条/请求。容量换算（`settings.py` 的压测注释口径）：可用连接数 ≈ `db_pool_size(20) + db_max_overflow(20) = 40`，按每在途请求 2 条 → **支持约 20 并发**（该注释记录的反例：池 10+10 时 c=20 并发 76 请求失败 36 个 = 47%，即 20 恰好卡在临界点）。若图召回再并发开**第三条**连接，容量变成 40/3 ≈ 13 并发，**直接跌破已标定的 20 并发基线**。

**串行的量化代价**：图召回 = 1 次实体链接（B-tree + GIN，百微秒~毫秒级）+ 1 次图扩展取片（2 跳自连接 + 四闸门 JOIN，目标 p95 ≤ 80ms）。相对现有检索耗时（embed 往返 + 三路 SQL + rerank）属可接受增量。**并且放在 L1 闸门之后执行** → 拒答路径完全不为图召回付费（217 条里 106 条不可答，即约一半请求零成本）。

### 2.2 推翻团队判断②：图召回**不进入 RRF**，走 side channel

团队判断原文：「图召回作为第 4 路……沿用既有不变量『RRF 分只作排序键，绝不参与阈值判定』」。

保留不变量，但**推翻"进 RRF"这个做法**。理由是一条硬算术：

- 图独有的 chunk 没有可比分数。它没被向量路召回 → 没有 `vector_score`；`rerank_enabled` 默认 **false**（本机 CPU 实测 50 条重排 66s，远超 3s 超时）→ 没有 `rerank_score`。`_build_chunk()` 会给出 `final_score = 0.0 + weight*0.001 ≈ 0`。
- 若把它塞进 `chunks`：① 它排序垫底，`TOP_K_RERANK=8` 截断后**根本进不了上下文**（白算）；② 更糟的是它可能进入 `retrieved[0]` 的候选池参与「top1 是否过阈值」的语义（一旦三路全空而它非空，`if not all_chunks` 的提前拒答被绕过，然后 top1=0 仍拒答 —— 行为不变但多花一次计算）；③ 若为了让它能过阈值而给它换一套分数口径，**0.50 阈值与 217 条基线同时失效**（这就是链式检索 `merge_rounds` 明令禁止的「把 RRF 分写回 final_score」同类错误）。
- 若给它一个「图路专属分数」并参与排序，等于新增第二套打分口径，需要重新标定阈值 —— 直接违反「阈值必须绑定度量空间」的检查项。

**替代方案（已采纳）**：图召回 = **第 4 个上下文来源**，与「表格回捞片」「章节补全片」完全同构 —— 独立字段、分数恒 0、不进排序/阈值/RRF、由 chat 层追加到上下文尾部。这带来三个直接好处：① 阈值/排序/RRF 代码**一行不改**，217 条基线风险为零；② 上线零风险（关开关 = 代码路径不执行 = 与今天逐字节等价）；③ 语义诚实：图召回的定位本来就是「补充上下文」，不是「更相关」。

**由此产生的口径微调（v1.2 已按实测定稿）**：`graph_unique` 的统计口径 = **「最终进入上下文的图召回片数」**（`== len(graph_recall_chunks)`），`graph_covered` = 「≤10 个邻居中已存在于最终命中片的条数」。两个参照系都必须是**交付上下文**，不能是任一「候选池」：图召回片不在 top-K（在 side channel），用 top-K 当参照会恒为 0；用三路粗召回池（可达 150 个 id）当参照**同样**会恒为 0（v1.1 的实现口径，真库实测证伪，见 §9.8 裁决 1 / §9.9）。判据与分母见 §14.6。

### 2.3 推翻团队判断③：抽取 prompt 版本**不进环境变量**，是代码常量

团队要求「配置项清单至少覆盖：……抽取 prompt 版本」。

**结论：`GRAPH_PROMPT_VERSION` 必须是 `decisions.py` 里的 `Final` 常量，不能是环境变量。** 理由与 `EMBEDDING_TEXT_VERSION` 完全同构（见 `index_profile.py` 模块说明）：版本号是**代码里那段 prompt 正文的指纹**，二者必须同源。若允许部署侧改版本号，就会出现「版本号写 v2、实际跑 v1 的 prompt 正文」—— 落库的数据全部被贴上错误的版本标签，口径过滤形同虚设，而这**不会报任何错**。审批 prompt 变更的正确姿势是改代码 + 改常量 + 重抽，走代码评审。

同结论适用于 `WIKI_PROMPT_VERSION`。其余「非 prompt 正文相关」的项（模型名、开关、后端、超时）进 `settings`，判断标准见 §9.5。

## 4. 六层设计

### 4.1 E 执行循环

**设计决策**

- **形态**：本系统不是自主 agent 循环，而是「固定管线 + 一次带超时的子步骤」。**不引入循环、不引入终止条件判定、不引入打转检测**（打转是自主循环的病，管线没有这个概念）。E 层在本方案里的唯一职责是**调度与失败分类**。
- **墙钟预算**：L1 闸门通过后串行追加 `graph_recall` 一步，硬上限 `settings.graph_retrieve_timeout_ms = 800`（兜底），目标 p95 ≤ 80ms（§14.6 门禁）。
- **并行度上限**：**1**（串行）。理由见 §2.1（三条硬约束）。
- **失败分类与恢复**（必须分类，禁止吞异常）：
  | 类别 | 触发 | 处置 | 打点 |
  |---|---|---|---|
  | 超时 | `asyncio.TimeoutError` | 放弃本步，`rollback()` 后继续主链路（结果 = 0 路） | `rag.graph.degraded{reason=timeout}` |
  | 永久 | 口径/后端配置错（启动期已拦，理论上不出现） | 记录 error，返回 0 路 | `rag.graph.degraded{reason=config}` |
  | 瞬时 | 数据库连接抖动 | 不重试（在线路径不重试，宁快勿等），返回 0 路 | `rag.graph.degraded{reason=error}` |
  | 空结果 | 无种子实体 / 无邻居 | 正常态（不是失败） | `rag.graph.empty{stage=link\|expand}` |
- **离线侧重置**：抽取任务重试上限复用 `settings.arq_max_attempts = 3`；每次重试前**先按 `document_id` 清派生数据**（幂等，见下）。
- **可中断**：不改变既有 SSE（服务端推送）中断点。图召回发生在首个 SSE 事件之前，超时即放弃，用户感知是「检索略慢」或「不慢」。

**落地规格**

- 文件：`app/services/graph/recall.py`
- 关键函数：`async def recall_by_graph(session, *, query, pushdown, timeout_ms, ...) -> GraphRecallResult`；内部 `asyncio.wait_for(asyncio.shield(...))` **不加 shield**（要能取消），超时后由调用方 `await session.rollback()`。
- 调用点：`app/services/retrieve/__init__.py::RetrievalService.retrieve()`，位置在「L1 阈值闸门通过之后、章节补全之前」（时序见 §9.3 的 8 步）。
- 失败处理：`recall_by_graph` **自身不抛异常**（内部 try/except 全覆盖，返回 `GraphRecallResult(chunks=[], degraded_reason=...)`），并在超时/异常分支执行 `await session.rollback()` —— 这一步**不可省**，否则重演「事务 abort 导致后续查询连锁失败」的 P1 缺陷。

### 4.2 T 工具注册

**设计决策**

- **是"固定管线"还是"动态 function-calling"**：**固定管线**。`GraphStore` 是**依赖注入的组件端口**，不是给模型调用的工具表。不存在「注册 - 披露 - 授权」三分离问题（没有模型发起的调用）。
- **执行环境**：抽取在 **worker 容器**内跑（无外网出口要求，只访问内部 LLM 网关与 PostgreSQL）；在线召回在 **api 容器**内跑（只读图，无写权限需求）。
- **凭证是否进执行环境**：**进，且必须有。** 抽取依赖 LLM 凭据；worker 需要 `LLM_BASE_URL` / `LLM_API_KEY` / `LLM_MODEL`。这里有一个**必须在本方案中一并修复的生产缺口**（见 §7.4）：`docker-compose.prod.yml` 的 `worker` 段**当前没有注入任何 `LLM_*`**（只有 `api` 段有，第 158-160 行）；dev compose 两段都有。若不补，图抽取在 prod 下会因缺凭据而必然失败 —— 与 README §13.4 记录过的 P0「生产 compose 漏同步开关」完全同类。
- **写操作影响半径**：抽取只写 `graph_entities / graph_entity_mentions / graph_relations / documents.graph_* / wiki_pages` 五处，**不触碰** `chunks` / `documents` 的业务字段、不触碰 S3 对象、不触碰审计与配额。半径限定在「派生数据」范围内。

**落地规格**

- 端口：`app/services/graph/base.py::GraphStore`（`typing.Protocol`），4 个方法（签名见 §9.1）：`upsert_subgraph` / `neighbors` / `delete_by_document` / `health`。
- 实现：`app/services/graph/postgres_store.py::PostgresGraphStore`；选择器 `get_graph_store() -> GraphStore`，只认 `settings.graph_store_backend == "postgres"`，其余值在**启动期**已 fail-closed 拦下。
- Neo4j 位：`app/services/graph/neo4j_store.py` **不创建**该文件（避免留一个"看起来能用"的空实现）；位置记录在本设计与 `base.py` 的模块 docstring 里，附「实现时必须满足的四条契约」（四闸门下推 / 口径过滤 / 幂等 upsert / 按文档级联删）。
- 失败处理：`upsert_subgraph` 在**单个事务**内完成三表写入；失败整篇回滚并置 `documents.graph_status='failed'`，不留半成品。

### 4.3 C 上下文管理

**设计决策**

- **预算分配**（单请求 32K，`CONTEXT_WINDOW_LIMIT_TOKENS`，预留输出 4K）：

  | 来源 | 预算 | 说明 |
  |---|---|---|
  | system（含锁定区） | ≈1.5K | 不变 |
  | 长期画像 | ≤0.5K | 不变 |
  | 短期历史（6 条） | 3~6K | 不变 |
  | **命中片（`chunks`）** | ≤6.4K（8 × 800） | 不变 |
  | 表格回捞片 | ≤2K（`TABLE_RECALL_TOKEN_BUDGET=2048`） | 不变 |
  | 章节补全片 | ≤1.2K（`SECTION_RECALL_TOKEN_BUDGET=1200`） | 不变 |
  | **图召回片（新增）** | **≤1.2K（`GRAPH_RECALL_TOKEN_BUDGET=1200`）** | 新增，最低优先级 |
  | 当前问题 | ≈0.3K | 不变 |

  合计上限 ≈ 22K < 28K（32K − 4K 输出预留），仍有 6K 余量给长历史 —— 增量不会让压缩阈值提前触发到不可接受的程度。
- **组装顺序（即裁剪优先级，尾部先被裁）**：`chunks` → `table_recall_chunks` → `section_recall_chunks` → **`graph_recall_chunks`**。图召回放最后：它是最新、最未经验证的能力，让它在超限时**第一个被裁掉**，符合「不确定的东西先让位」。
- **外部内容消毒**：图召回片是 **chunk 原文**，走既有注入检测（`guard/injection.py` 降权 + 打点）、既有 PII 脱敏、既有引用编号机制 —— **零特殊分支**。
- **前缀布局（稳定区/可变区）**：**本方案对前缀缓存的影响 = 0**。system prompt 字节不变；wiki 与图数据都不进 prompt；检索结果只改变尾部（chunk 段）内容。新增的 `WIKI_*` / `GRAPH_*` 配置**不进 prompt 文本**（只在 `caliber` 里落库）。
- **序列化确定性**：图召回片的排序键必须是**全序**且不含随机量：`(hop ASC, edge_weight_sum DESC, chunk_id ASC)`。第三键用 `chunk_id` 而非 `created_at`，避免同一语义出现两种字节顺序。wiki 的 `key_terms` 落库前 `sorted()` + 去重，保证两次生成同样内容时字节一致。
- **重写失效预算与结果复用**：
  - 抽取是**离线昂贵产物** → 必须复用：同一 `(document_id, extractor_model, prompt_version)` 若 `graph_status='done'` 则**跳过重抽**（幂等键见 §9.4）。
  - 失效条件**先于**缓存实现定义（见 §7.3 矩阵）：`chunk` 行被删除重建 / 口径变更 / 文档重解析。写操作与非幂等操作不进缓存。
  - wiki 页用 `content_hash`（输入 chunk 文本 + prompt 版本 + 模型名的 sha1）判定是否需要重建，避免全库无意义重建。

**落地规格**

- `app/api/chat.py` 的三元组追加改为四元组（**唯一一处必须改的既有文件**）：
  ```python
  current_chunks = (
      list(result.chunks)
      + list(result.table_recall_chunks)
      + list(result.section_recall_chunks)
      + list(result.graph_recall_chunks)      # 新增；位置即裁剪优先级
  )
  ```
- 图召回片的 token 预算在 `retrieve` 内按 `chunk.token_count` 累计，超预算即停（与章节补全同款），**不在 chat 层再算**。

### 4.4 S 状态存储

**设计决策**

- **结构**：三张图表 + 一张 wiki 表 + `documents` 三列（详见 §8）。图数据按 **KB 聚合实体、按 chunk 记录提及**：实体在 KB 内合一（跨文档合并是图的全部意义），提及与关系按文档/分片记账（可级联删除、可回算证据）。
- **备份/回滚**：图与 wiki 全是**可再生派生数据** → 不进备份策略（`DEPLOY.md` §5 的备份只覆盖业务表）；重建成本 = worker 重跑。这是选的：派生数据备份是浪费，重跑是幂等操作。
- **治理**：图数据无「可信度分级」需求，但必须有**口径章**（`extractor_model` / `prompt_version`）与**就绪度**（`documents.graph_status`）。理由：没有章就无法回答「这条回答用的图是按什么口径抽的」；没有就绪度就无法回答「图召回为什么对这篇文档不生效」。
- **记忆可信度与失效**：图不是记忆（不跨会话、不代表用户偏好、不参与权限判定），故**不适用** `MEMORY_LONG_TERM_KINDS` 那套白名单。但继承一条原则：**LLM 产出的东西不得因"被写进库"而升级为事实** —— 所以图只作召回线索，不做证据（红线 A）。
- **外部副作用幂等**：抽取会**覆盖写三表**，幂等键 = `(document_id, extractor_model, prompt_version)`。重复执行先 `delete_by_document()` 再 `upsert_subgraph()`，结果为终态一致（不依赖「上次跑到哪」）。

**落地规格**

- 写入方：`app/workers/graph_job.py`（新增 arq 任务）+ `app/services/graph/extract.py`（LLM 调用与结果校验）+ `PostgresGraphStore.upsert_subgraph()`。
- **重索引必须先清派生数据**（关键不变量，见 §8.5）：`chunks` 在重解析时被 `delete(Chunk).where(document_id == ...)` 再 INSERT（`parse_job.py::_index_document`），新 chunk 是**新 uuid**。因此 `graph_entity_mentions.chunk_id` 的 `ON DELETE CASCADE` 会静默删掉旧提及，留下孤儿实体与指向死 chunk 的 wiki 页。**必须**在写入新 chunks 的同一事务里先调 `purge_derived(session, document_id)`（删图数据 + 删 wiki 页 + 置 `graph_status='pending'`）。
- 并发写：`graph_entities(kb_id, name_key)` 唯一约束 + `INSERT ... ON CONFLICT (kb_id, name_key) DO UPDATE` 解决并发 upsert 竞态（`doc_freq` 用 `+1` 增量而非覆盖）。

### 4.5 L 生命周期钩子

**设计决策**

- **拦截点（真实存在，不虚构 API）**：
  | 钩子 | 挂载点 | 作用 |
  |---|---|---|
  | 启动自检 | `app/main.py::lifespan`（已调 `decisions.self_check()` 与 `check_llm_budget`） | 新增 `check_capabilities()`，fail-closed |
  | 能力横幅 | `lifespan` 内、自检查通过之后 | 打印人可读横幅 + 结构化 `capability` 日志，api 与 worker **各打一条** |
  | 索引后置 | `parse_job.py::_index_document` / `run_parse_finalize` 写库事务**提交后** | `enqueue("run_graph_extract", document_id)` / `enqueue("run_wiki_build", document_id)`（仅在对应开关开启时） |
  | 索引前置 | 同上，写新 chunks 的**同一事务内、DELETE 之前** | `purge_derived(session, document_id)` |
- **人在回路四档**：本能力**无高危外部动作**（不删业务数据、不外发、不改权限）。四档落位：
  - 自动执行：抽取、wiki 生成、图召回（离线/只读，可逆）。
  - 执行后告知：能力快照写日志 + 管理端可查（部署方随时知道现在是哪一档）。
  - 执行前确认：**变更能力配置**（改 `.env` + 重启）本身就是人工动作，无需系统再加一道。
  - 直接阻断：启动自检（依赖缺失即拒启）—— 这是唯一的「阻断」档位。
- **纵深防御**：图召回的权限不能只靠「端口实现自觉」。三道叠加：① `neighbors()` 契约内嵌 `_WHERE_BASE`；② 单测用**真实 SQL 解析**断言 SQL 文本包含四个闸门条件（防以后有人「优化」掉某个条件）；③ 端到端越权测试集（构造高密级邻居，断言零命中）。

**落地规格**

- `app/config/capabilities.py`（新增）：`capability_snapshot() -> dict`（**唯一真源**，供横幅 / 管理端 / caliber 三处共用，禁止各拼一份）；`render_banner() -> str`。
- `app/config/self_check_ext.py`（新增，或直接在 `decisions.py` 内加 `check_capabilities()`）：见 §7.2 规则表。**放独立函数**的理由：`decisions.self_check()` 是「冻结口径」的校验，能力校验需要**查库**（表是否存在），混进去会让 `python -m app.config.decisions` 这个纯静态自检变成需要 DB —— 破坏现有的「口径即代码，可离线自检」性质。

### 4.6 V 评估接口

**设计决策**

- **验证方式**：按「验证强度阶梯」取最高可行级 —— 本方案有确定性规则可用，**不走模型裁判**：① 217 条既有评测集（可答/不可答判定是确定性的：拒答与否 + 期望文档命中）；② `graph_unique` 计数（确定性）；③ 越权反例集（零命中是二元判定）。
- **独立读路径**：`scripts/run_eval.py` 已走「评测脚本进程内直调检索/生成」，不经 api HTTP 层 → 天然是独立读路径（CQRS 的读侧）。**不新增**评测端点。
- **生成者与评估者分离**：本方案的「生成者」是离线抽取 prompt；「评估者」是评测集的门禁指标（refusal / miss / hit）—— 评估者**不看**抽取的推理过程，只看最终产物（哪些 chunk 进了上下文、答案是否拒答）。评估者不引入 LLM 自评。
- **核对权威系统状态**：`graph_status='done'` 不等于「图真的可用」→ 验收必须核 `graph_entities / graph_relations` 的实际行数与 `neighbors()` 的真实返回（工具回执 ≠ 业务事实）。
- **可复现**：能力快照进 `eval_runs.caliber`（含 `config_fingerprint`），同一 `case_fingerprint` 下的两次运行可直接对比「开了图 vs 没开图」。

**落地规格**：见 §14。

## 5. 模型组合与任务分派

**形态判定**：**A 类 —— 单智能体 + 单模型（在线），离线侧复用同一档模型。**
显式质疑记录：
- 为什么不是 **B（循环内多档模型）**？因为在线检索链路**没有 LLM 调用**（实体链接是 SQL）。要在循环内分档，前提是循环内有多次模型调用 —— 这里没有。离线抽取虽然可以分档（flash 抽 + pro 抽查），但离线不在循环内、且没人盯着延迟，多档只增加配置面，收益是「更贵」。
- 为什么不是 **C（多智能体）**？见 §6。

**任务-模型分派表**

| 步骤 | 档位 | 理由 | 成本/延迟预算 |
|---|---|---|---|
| 查询 → 实体链接 | 确定性代码（SQL） | 词元级匹配足够；LLM 链接会 +3~10s TTFT | ≤ 10ms |
| 图扩展（1~2 跳） | 确定性代码（递归 CTE） | 纯图遍历，无模型参与 | p95 ≤ 80ms |
| 图召回取片 + 预算裁剪 | 确定性代码 | 与章节补全同款 | ≤ 5ms |
| 实体/关系抽取 | 快速低价 LLM（`llm_model`） | 结构化抄写任务；每批 4 chunk | 离线：单文档 ≈ 60 chunk → 15 次调用；按 15 token/s 上游实测，单次约 8~20s → 单文档 2~5 分钟（**估算，须实测**） |
| 抽取结果校验（JSON 结构 / 长度 / 类型枚举） | 确定性代码 | 校验必须是规则，不能靠模型自评 | 0 |
| wiki 页生成 | 快速低价 LLM | 摘要 + 术语 + 小节导航 | 离线：单文档 1 次调用（输入截断到 `WIKI_INPUT_MAX_CHARS`） |
| 评测门禁 | 确定性规则（拒答 / 命中 / 计数） | 禁止模型自评 | 0 |

- **token 预算按档位分配**：在线 0 token（全部确定性代码）；离线 100% 走快速档。**没有把预算分给强力档**，因为默认不启用。
- **缓存与重算账**：抽取结果 = 缓存本体（落库）；失效触发点只有三个（口径变更 / chunk 重建 / 文档删除），重抽一次代价 = 该文档 chunk 数 / 4 × 单次调用 token（约 60/4 × 1.5K ≈ 22K token/文档）。wiki 重建 = 1 次调用 ≈ 4K token/文档。
- **级联升级条件**：不设在线级联（在线无 LLM）。离线侧：抽取 JSON 解析连续 2 次失败 → 不做模型升级，直接置 `failed` 并告警（升级到 pro 不会让模型更会输出合法 JSON，只会更贵更慢）。
- **降级链**：图召回失败 → 0 路（三路照常）；wiki 导航无数据 → 不扩展词元（等价于今天）；抽取失败 → 该文档无图（可检索性不变）。
- **评估者档位与生成者档位关系**：评估者是**确定性代码**（比任何模型都便宜且独立），不需要独立性妥协。

## 7. 核心：配置项契约

> 本节是设计的重心。**判断标准**：一个配置项值不值得存在，取决于它是否满足「部署方确实需要在不同环境取不同值」与「取值错误会导致什么后果可被立刻发现」两条。凡是「改错了不报错、只是答不准」的项，一律不给环境变量（详见 §9.5）。

### 7.2 启动自检规则（fail-closed 的完整定义）

**放在新函数 `app/config/self_check_ext.py::check_capabilities()`**，由 `main.py::lifespan` 在 `decisions.self_check()` 之后调用；worker 在 `app/workers/parse_job.py::WorkerSettings` 里**新增** `on_startup` 协程调**同一个函数**（注意：`WorkerSettings` 当前**没有** `on_startup`，本项目 arq 配置里只用了 `functions` / `cron_jobs` / `job_timeout` 等，该钩子需新增；arq 的 `on_startup` 抛异常会让 worker 启动失败，正是我们要的 fail-closed 语义，须在编码时验证一次「故意配错 → worker 进程退出且日志含 §12.4 文案」）。

| # | 条件 | 判定 | 失败后果 |
|---|---|---|---|
| C1 | `GRAPH_ENABLED=true` → `GRAPH_STORE_BACKEND` 必须是已实现的后端 | 值 ∉ {`postgres`} → RuntimeError | 拒绝启动 |
| C2 | `GRAPH_ENABLED=true` → `settings.llm_api_key` 非空 | 空 → RuntimeError | 拒绝启动 |
| C3 | `GRAPH_ENABLED=true` → 图三表存在 | `SELECT to_regclass('graph_entities') IS NOT NULL AND ...` 任一为 NULL → RuntimeError（附迁移命令） | 拒绝启动 |
| C4 | `GRAPH_ENABLED=true` → 图存储可达 | `GraphStore.health()` 返回 False 或抛异常 → RuntimeError | 拒绝启动 |
| C5 | `WIKI_ENABLED=true` → `llm_api_key` 非空 + `wiki_pages` 表存在 | 同 C2/C3 | 拒绝启动 |
| C6 | `WIKI_ENABLED=true` → `WIKI_SCOPE == "doc"` | 其它值 → RuntimeError | 拒绝启动 |
| C7 | `GRAPH_ENABLED=true` → 图数据就绪度**只告警不阻断** | 统计 `documents WHERE is_latest AND graph_status NOT IN ('done')`，>0 时 `logger.warning` + 指标 `graph.data.not_ready` | 允许启动（数据未就绪 ≠ 依赖缺失） |
| C8 | `GRAPH_ENABLED=false` | 不做任何图相关检查（连 DB 都不查） | 允许启动 |

**C4 的一个细节（bool 而非抛异常）**：`GraphStore.health()` 契约返回 `bool`，内部自行捕获异常 —— 端口不向外抛存储层异常，调用方（启动自检 / 在线召回 / 管理端）统一按 bool 处置。这样在线侧 `except` 分支只剩「超时」一种真实异常。

**为什么自检要查库（C3/C4）而既有启动检查（索引口径 / schema 版本）只告警**：既有检查的对象是「**数据是否过期**」（旧 chunk 仍然可用，服务应继续跑）；本自检的对象是「**能力是否真的可用**」。开关声称「图召回已启用」，而表不存在 → 每一次提问都会静默走 0 路且没人知道 —— 这就是团队要堵的静默降级。两者的判别标准已在 §2「失败语义」写清。

### 7.3 配置项 × 变更后果矩阵（本设计的核心交付物之一）

> 判断依据（先说，再看表）：**实体抽取的输入是已落库的 `chunks.content` + `heading_path`。只要 chunk **行**不变（`chunks.id` 不变），就不需要重新解析与嵌入。**
>
> **这个判断在本项目中成立，但有一个必须显式指出的边界**：
> - `scripts/reindex_embeddings.py` 是 `UPDATE chunks SET embedding=...`（原地更新，`chunk_id` 不变）→ **换嵌入口径不需要重抽图**（这是「改嵌入不用重抽」成立的唯一依据）。
> - `parse_job.py::_index_document` 与 `run_parse_finalize` 是 **`DELETE chunks` + `INSERT`**（新 `uuid4`）→ **任何重解析都会换掉 chunk 行**，`graph_entity_mentions.chunk_id` 的级联删除会静默抹掉全部提及。所以「重解析」必然要求重抽图与重建 wiki，这不是保守，是数据的物理事实。
> - 结论：矩阵里「换分块器 / 嵌入口径 → 全链重跑」中的**分块器**部分触发重解析（→ 必须重抽），**嵌入**部分若是原地重算（→ 不必重抽）。团队原判断把两者合为一行，我拆开更准确（见第 4、5 行）。

| # | 变更 | 要重跑什么 | 不用重跑什么 | 依据 / 机制 |
|---|---|---|---|---|
| 1 | **开图**（`GRAPH_ENABLED false→true`） | **补建实体抽取**：`python -m scripts.backfill_graph --all`（或 `--kb-id` 限库） | 解析、分块、嵌入、wiki（与图无关） | 抽取输入是已落库 chunk；补建是幂等任务（先 `delete_by_document` 再 `upsert`） |
| 2 | **关图**（`true→false`） | **什么都不用重跑**。图数据保留（不删）—— 重新开启时若口径未变，`graph_status='done'` 直接复用 | 全部 | 关闭 = 代码路径不执行；数据留库便于快速回滚（开回来立即生效）。真要清空：`scripts/purge_graph.py`（本版不写，标注为运维手动 SQL） |
| 3 | **换抽取模型或 prompt 版本**（`GRAPH_EXTRACTOR_MODEL` 变更 / 代码里 bump `GRAPH_PROMPT_VERSION`） | **重抽**：`scripts/backfill_graph.py --recaliber`（只抽口径不匹配的文档） | 解析、分块、嵌入 | **旧口径的行不是被"覆盖"，而是被检索直接排除**（`WHERE extractor_model=:m AND prompt_version=:pv`）→ 重抽完成前，图路对这些文档静默无结果（fail-closed，宁可查不到） |
| 4 | **换 wiki 生成模型 / wiki prompt 版本** | **重建 wiki 页**：`scripts/rebuild_wiki.py --recaliber` | 解析、分块、嵌入、**图抽取** | wiki 输入是 chunk 文本；两能力彼此独立（图不依赖 wiki，wiki 不依赖图） |
| 5 | **换分块器**（`CHUNK_*` 常量变更 → `chunker_version` 变） | **全链重跑**：解析 → 分块 → 嵌入 → **图抽取** → **wiki 重建** | — | 重解析 `DELETE+INSERT` 换掉 chunk 行 → 图提及被级联删除、wiki 页指向死 chunk。必须先 `purge_derived()` 再重抽 |
| 6 | **换嵌入口径**（`EMBEDDING_MODEL` / `EMBEDDING_TEXT_VERSION` 变更，**分块器不变**） | 重算向量：`scripts/reindex_embeddings.py`（原地 UPDATE）；**若同时改了分块器则按第 5 行** | **图抽取**、**wiki**、解析（`parse_segments` 未变） | `chunk_id` 不变 → 图提及与 wiki 证据仍有效 |
| 7 | **开 wiki**（`WIKI_ENABLED false→true`） | **重建 wiki 页**：`scripts/rebuild_wiki.py --all` | 解析、分块、嵌入、图抽取 | 生成输入 = 已落库 chunk |
| 8 | **关 wiki**（`true→false`） | 什么都不用重跑；页留库（接口 404，检索不扩展词元） | 全部 | 同第 2 行 |
| 9 | **调 `GRAPH_RETRIEVE_TIMEOUT_MS` / `GRAPH_RECALL_*`** | 什么都不用重跑（只影响在线行为） | 全部 | 纯在线参数 |
| 10 | **api / worker 只重建一侧** | **必须两侧同时重建**（同一 tag） | — | 双镜像一致性要求（README §13.4 的 P0 前车之鉴）。配置一致性由 §7.4 的指纹比对兜底 |

**上线验收口径差异（容易漏）**：第 1/3/7 行做完后，**必须重跑 217 条评测**并把 `caliber` 里的能力快照一起落库，否则「开图之后变好」这句话没有可比证据（§14）。

### 7.4 配置一致性机制（api ↔ worker）

问题：抽取在 worker、召回在 api。两者如果读到不同的 `GRAPH_ENABLED`，会出现「api 开着图但库里没数据」（用户无感变慢）或「worker 一直抽但 api 不查」（白烧算力）。**运行时没有任何机制能发现这个不一致**（它们不通信）。

三道机制，全部复用既有设施：

1. **启动能力横幅 + 结构化日志**（§12.1）：api 与 worker **各打一条**，人可读横幅 + 一条 JSON 日志含 `config_fingerprint`（由 `config/config_profile.config_fingerprint()` 计算，能力字段已进 `runtime_config_snapshot()` 故指纹自动变）。
2. **`/api/system/capabilities`**（§9.2）：管理端随时能看 api 侧的能力与**数据就绪度**；若 worker 侧没在抽，`documents_pending` 会持续不降 —— 这是可观测的间接证据。
3. **部署文档硬性要求**（§12.3）：`DEPLOY.md` 明确写「改这两个开关必须同时重建 api 与 worker 并比对两条启动横幅的 `config_fingerprint`」。

**必须一并修复的既有缺口**：`docker-compose.prod.yml` 的 `worker.environment` **缺 `LLM_BASE_URL` / `LLM_API_KEY` / `LLM_MODEL`**（只有 `api` 段有，第 158-160 行；dev compose 的 worker 段有）。图抽取依赖 LLM，不补则 prod 下抽取必然失败。本方案把「prod worker 段补齐 LLM_*」列为**第 1 步的必做项**，并由 C2 自检在 worker 侧兜底（缺凭据 → 拒绝启动而不是跑起来后静默失败）。

### 7.5 为什么 `WIKI_SCOPE=kb` 必须拒绝启动（而不是先支持着）

KB 级 wiki 页要把**多篇不同密级的文档**摘要合成一个对象，而可见性的表达单位是**文档**（chunk 继承 doc 的 `acl_tags` / `level_rank`）。两种实现都是坏的：
- 按「生成者的权限」生成 → 高密级内容进了低密级用户可见的页面 = **越权**；
- 按「读者的权限」动态裁剪 → 同一页面每次请求都要重建（且缓存键要带用户主体集合）→ 成本与实现复杂度都远超本阶段目标。

所以本版**只做 doc 级**（一文档一页，可见性 = 该文档存在至少一条通过四闸门的 chunk，与文档级 ACL 完全同构）。`kb` 作为保留值存在，配了就在启动时**明确拒绝**，而不是"悄悄按 doc 处理"。

### 8.4 ACL 字段怎么带：**不冗余存，一律 JOIN 回 `chunks`**

团队问的是「冗余存还是 join 回 chunks」。**判断：不冗余存任何 ACL 字段。**

理由三条，按重要性排序：
1. **不产生权限副本。** 冗余存 `acl_tags` / `level_rank` 到图表，等于给权限数据造了第二份拷贝。文档权限一旦变更（改密级、加 deny、移出 kb），副本不会自动跟着变 —— 这正是 `decisions.py` 里「长期记忆 MUST NOT 含文档内容，那是**权限副本**」的同一个病。JOIN 回 `chunks` 天然零同步成本。
2. **四闸门保持单一真源。** `_WHERE_BASE` 是既有唯一真源。图召回的取片 SQL 直接内联它 → 与向量路逐字一致。若冗余存，就必须在图表上**再写一份** WHERE（`ge.acl_tags && :user_subjects AND ge.level_rank <= :clearance ...`），两份必然漂移，而漂移的表现是**越权或漏召回**，都不会报错。
3. **JOIN 成本可忽略。** 图扩展先收缩到几十个候选 chunk_id，再 `JOIN chunks` 时 `chunks` 主键做索引扫描；`idx_chunk_filter` / `idx_chunk_acl` / `idx_chunk_deny` 全部可用。实测预期在毫秒级（§14.6 有门禁：p95 ≤ 80ms）。

**代价（诚实）**：① 每次图召回多一次 JOIN（已论证可忽略）；② 换图存储到 Neo4j 时，Neo4j 侧**没有** `chunks` 表 → 实现者必须把四闸门条件翻译成 Neo4j 的查询语义，或者在 Neo4j 里冗余一张权限投影表。这是端口契约的一部分（`neighbors()` 必须在存储层内完成权限过滤），已在 §9.1 写进实现者须知 —— **这是换存储的真实成本，不是可以省掉的设计细节**。

### 8.5 删除与版本语义

| 事件 | `documents` | `chunks` | 图数据 | wiki |
|---|---|---|---|---|
| **重索引同一文档**（重新解析） | 不变（同一行） | **DELETE + INSERT（新 uuid）** | **必须在同事务内 `purge_derived()`**：删 mention / relation / 无引用实体，置 `graph_status='pending'` | 同事务内 DELETE 页（否则 `source_chunk_ids` 变死 id） |
| **上传新版本**（`version+1`） | 新行，旧行 `is_latest=false` | 新文档的 chunk 是新行 | 新文档正常抽取；旧版本图数据留着（检索按 `c.is_latest` 天然排除） | 同上 |
| **软删文档**（`documents.deleted_at`） | `deleted_at` 置值 + `is_latest=false`（`documents.py` 现状） | 该文档 chunk 置 `is_latest=false`（现状，不物理删） | **不删**（保留历史回答的引用可读性）；检索因 `c.is_latest=true` 天然排除 | **不删**；读接口返回 404（因为无可见 chunk） |
| **硬删文档**（物理 DELETE） | 行消失 | `ON DELETE CASCADE` | `ON DELETE CASCADE` 自动清三表 | `ON DELETE CASCADE` 自动清页 |
| **硬删 chunk**（当前代码的重索引路径） | — | 行消失 | mention 级联删除；**遗留孤儿实体**（`doc_freq` 需重算） | 不自动清 → 必须靠 `purge_derived()` |
| **删除 kb** | 级联 | 级联 | `kb_id` 外键级联 | 级联 |

**孤儿实体清理**：`delete_by_document()` 在同一个事务里，删除本 doc 的 mention/relation 后执行
```sql
DELETE FROM graph_entities e
WHERE e.kb_id = :kb_id
  AND NOT EXISTS (SELECT 1 FROM graph_entity_mentions m WHERE m.entity_id = e.id);
```
并把受影响实体的 `doc_freq` 按剩余 mention 的 `count(DISTINCT document_id)` 重算（**不做 -1 增量** —— 增量在多文档共享实体时必然算错）。

**版本口径语义（fail-closed）**：检索 SQL 固定带 `extractor_model = :gm AND prompt_version = :pv`（`gm/pv` 来自 `current_graph_profile()`）。**不带兜底分支、不做 "OR prompt_version IS NULL"**。旧口径 = 查不到 = 这条能力对这篇文档暂时不生效 —— 这正是 `index_profile` 里「宁可查不到，不可查错」的同一条纪律。

### 9.1 数据源接口：`GraphStore` 端口（4 个方法）

```python
# app/services/graph/base.py
from __future__ import annotations
import uuid
from dataclasses import dataclass, field
from typing import Protocol

@dataclass(frozen=True)
class ExtractedEntity:
    name: str                 # 归一前的展示名（≤ GRAPH_ENTITY_NAME_MAX_CHARS）
    name_key: str             # 归一化键（同一 KB 内唯一键）
    entity_type: str          # 必须 ∈ decisions.GRAPH_ENTITY_TYPES
    aliases: tuple[str, ...] = ()

@dataclass(frozen=True)
class ExtractedMention:
    chunk_id: uuid.UUID
    entity_key: str           # 指向 ExtractedEntity.name_key
    surface: str              # 原文写法
    confidence: float | None = None

@dataclass(frozen=True)
class ExtractedRelation:
    src_key: str              # ExtractedEntity.name_key
    dst_key: str
    relation: str             # 归一后 ≤ 20 字
    document_id: uuid.UUID

@dataclass(frozen=True)
class ExtractionResult:
    entities: list[ExtractedEntity] = field(default_factory=list)
    mentions: list[ExtractedMention] = field(default_factory=list)
    relations: list[ExtractedRelation] = field(default_factory=list)
    extractor_model: str = ""
    prompt_version: str = ""
    chunks_processed: int = 0
    llm_calls: int = 0

@dataclass(frozen=True)
class GraphNeighbor:
    chunk_id: uuid.UUID
    hop: int                  # 1 = 种子实体的直接提及片；2 = 一跳邻居的提及片
    weight: int               # 路径支撑强度（沿途边 support_count 之和）

@dataclass(frozen=True)
class GraphRecallResult:
    neighbors: list[GraphNeighbor] = field(default_factory=list)
    seed_entity_count: int = 0
    expanded_entity_count: int = 0
    degraded_reason: str = ""    # "" = 正常；"timeout" / "error" / "no_entities" / "no_neighbors"
    elapsed_ms: int = 0


class GraphStore(Protocol):
    """图存储端口。**实现者必须满足四条契约**（缺一条即视为实现不合规）：

    契约 1（权限）：`neighbors()` 必须在存储层内完成四闸门过滤，逐字等价于
        app/services/retrieve/__init__.py 的 _WHERE_BASE。端口**不提供**任何
        「不过滤」的取数方法 —— 否则调用方一定会有人用错。
    契约 2（口径）：**口径的载体是"有证据的行"（mention / relation），不是实体节点。**
        实体是 KB 内按 (kb_id, name_key) 合一的**共享节点**，表上无口径列（0024 实测）；
        因此本契约的落点是两条，缺一不可：
          2a（证据读）：`neighbors()` 必须在关系遍历与提及 JOIN 两处都带
              `extractor_model = :em AND prompt_version = :pv`。无兜底分支
              （不许写 `OR prompt_version IS NULL`）。
          2b（节点读）：任何读 `graph_entities` 的查询 MUST 附带
              `EXISTS (SELECT 1 FROM graph_entity_mentions m
                       WHERE m.entity_id = e.id AND m.extractor_model = :em
                         AND m.prompt_version = :pv)`。
              漏了 2b 不会报错，只会让旧口径实体占满种子名额（GRAPH_LINK_MAX_ENTITIES=8），
              而 neighbors() 已按口径把它们的边滤干净 → 结果恒 0 邻居，
              且看不出是「名额被旧数据吃掉」—— 这是本端口最容易埋的静默失效。
        写入必须落这两个字段（mention / relation 两处）。
    契约 3（幂等）：`upsert_subgraph()` 对同一 (document_id, 口径) 重复执行结果一致
        （先删后写，或 ON CONFLICT 合并，二者择一但必须确定）。
    契约 4（级联）：`delete_by_document()` 清本档 mention/relation，并清理无引用实体、
        重算受影响实体的 doc_freq。
    """

    async def upsert_subgraph(
        self,
        session: "AsyncSession",
        *,
        tenant_id: uuid.UUID,
        kb_id: uuid.UUID,
        document_id: uuid.UUID,
        result: ExtractionResult,
    ) -> int:
        """写入一篇文档的抽取结果（单事务）。返回写入的关系行数。"""

    async def neighbors(
        self,
        session: "AsyncSession",
        *,
        pushdown: dict,                 # tenant_id / clearance / authorized_kb_ids / user_subjects
        seed_entity_ids: list[uuid.UUID],
        extractor_model: str,
        prompt_version: str,
        max_hops: int,                  # ≤ decisions.GRAPH_MAX_HOPS
        limit: int,                     # ≤ decisions.GRAPH_RETRIEVE_TOP_K
    ) -> list[GraphNeighbor]:
        """从种子实体出发扩 max_hops 跳，返回**已过四闸门**的候选 chunk（按 hop/weight 升序去重）。"""

    async def delete_by_document(self, session: "AsyncSession", *, document_id: uuid.UUID) -> int:
        """清一篇文档的图数据 + 孤儿实体。返回删除的关系行数。"""

    async def health(self) -> bool:
        """存储可用性。内部吞异常，只回 bool（端口不向调用方抛存储层异常）。"""
```

**为什么是这 4 个方法而不是更多**：`upsert_subgraph` 是三表写入的**事务边界**（拆成 upsert_entities / upsert_relations 会让调用方负责事务，必然有人忘）；`neighbors` 是唯一读路径；`delete_by_document` 是唯一的按档清理入口；`health` 被启动自检与管理端共用。**没有 `get_entity()` / `count()` 之类的"顺手"方法** —— 每多一个读方法就多一处可能忘加权限过滤的地方。

### 9.3 与 `RetrievalResult` 的对接：**新增独立字段（复用 `section_recall_chunks` 模式）**

```python
# app/services/retrieve/base.py 增量
@dataclass
class RetrievedChunk:
    ...
    # 图召回片：由实体图扩展而来的邻居 chunk。
    # 与 table/section 回捞同款 —— 仅补上下文，MUST NOT 参与排序 / 阈值 / RRF / 路径贡献统计；
    # 分数一律 0 / None，单独放在 RetrievalResult.graph_recall_chunks。
    is_graph_recall: bool = False

@dataclass
class RetrievalResult:
    ...
    graph_recall_chunks: list[RetrievedChunk] = field(default_factory=list)
    # 图召回的降级原因（"" = 正常）："timeout" / "error" / "no_entities" / "no_neighbors"。
    # ★ 必须是**顶层 str 字段**而不是塞进 path_stats（三选一的理由，见 §9.7 裁决 A）：
    #   ① path_stats 的键语义是 `{path}_{measure}` 且 merge_rounds 对它是**按轮求和**，
    #      原因不可加（"timeout" + "no_entities" 无意义）；
    #   ② 既有同形先例：refuse_reason / score_source / chain_mode 都是「单请求状态 str」；
    #   ③ 单请求审计需要它：metrics 是聚合值，日志需反查，而审计行里要能直接看到根因。
    # merge_rounds 的合并规则：**取首个非空**（各轮同口径，原因不需要拼接）。
    graph_degraded_reason: str = ""
    # path_stats 新增两个键。★ 两者**不是**一个集合的划分，各自基数不同（见下表）：
    #   graph_covered = ≤GRAPH_RETRIEVE_TOP_K 个邻居中、**已存在于最终命中片**的条数（量化重复工作量）
    #   graph_unique  = **最终进入上下文**的图召回片条数（= len(graph_recall_chunks)，存废判据）
    #   ★ MUST NOT 相加、MUST NOT 算比率（基数不同 → 相加无意义、比率会误导）
```

**`path_stats` 的口径不对称（必须写进文档，否则读者会误解）**：

| 键 | 基数 | 回答的问题 | 为什么是这个基数 |
|---|---|---|---|
| `{vector,tsquery,ilike}_covered` | **最终 top-K**（`retrieved`） | 该路有多少片进了最终结果 | 三路参与排序，只有进了 top-K 才算「被用上」 |
| `{vector,tsquery,ilike}_unique` | **最终 top-K** | 该路独有、别的路给不了的片数 | 同上 |
| `graph_covered` | **≤10 个邻居**（预算裁剪**前**） | 图路有多少探索是重复劳动（邻居已在命中片里） | 图**不参与排序**，没有「进 top-K」这回事；能在邻居层量化重复度，才有优化价值 |
| `graph_unique` | **交付片**（`graph_recall_chunks`） | 图路给上下文补进了几片**新的**原文（存废判据） | 这才是「图有没有用」的直接度量：补进上下文的片数 |

**为什么不能用「三路候选池」当参照（v1.1 的实现口径，已判定失效）**：三路候选池是**粗召回池**（每路 `TOP_K_RECALL=50`，合计可达 150 个 id），远大于最终 top-K（8）。图召回扩展出的邻居绝大多数本来就落在这个池子里 —— 只是没进最终 8 条。于是会出现「图明明补了 2 片进上下文，`graph_unique` 仍为 0」（真库实测，见 §9.9）。
**后果不是数字难看，而是判据结构上永不成立**：任何实现都无法让这个指标 > 0，验收者试几次之后就会学会无视它 —— 这与「就绪度闸门永远红」属同一类错误（设了一个不可能满足的判据）。

**两条必须成立的等式（实现与测试都要钉）**：

```
① graph_unique  ==  len(result.graph_recall_chunks)        ← 交付片数，可直接复算
② graph_covered ==  len(邻居 ∩ {c.chunk_id for c in result.chunks})   ← 判据裁剪前统计
```

**预算必须「先排重、后裁剪」（否则 `graph_unique` 会被系统性压低）**：

现状（v1.1 实现）：`recall_by_graph` 不知道命中片是哪 8 条，预算按「邻居排序后的前 3 个」裁剪，回到 `retrieve()` 后才剔除与命中片重复者。后果：**重复的邻居先吃掉 3 个名额**，真正新增的片被裁掉 —— 而邻居是按 `(hop, weight)` 排序的，权重最高的一跳邻居恰恰最可能已在 top-K，因此重复片会**系统性聚集在队首**。这不是边角情形，是让 `graph_unique` 再次结构性偏 0 的原因（与 §9.9 记录的是同一类失效）。

**整改（契约要求，不是优化项）**：`recall_by_graph` 增加入参 `exclude_chunk_ids`（= 最终命中片的 id 集合，`retrieve()` 在第 5 步已知），预算裁剪时**先跳过 exclude 集合**，并在跳过前统计 `duplicate_count` 作为 `graph_covered`（这就是等式 ②）。

- 语义边界：`exclude_chunk_ids` 只用于「不重复占预算 + 统计重复度」，**MUST NOT** 参与任何排序或打分；
- 该集合**不得**包含 `table_recall_chunks` / `section_recall_chunks`（它们在图召回之后才产生，此时未知；且它们之间的互斥已由 `final_id_set` 在更后面统一处理）。

关闭图能力时**不写**这两个键（`path_stats` 与未实现图召回时逐键相同，保证基线可字节比对）。

**理由（为什么复用 `section_recall_chunks` 模式，而不是给 `chunks` 加字段或加分数）**：
1. 既有两个先例（表格回捞 / 章节补全）已经把「上下文补充片」的语义、预算、编号、引用、裁剪优先级全部定义好 —— 复用即零新增语义；
2. **阈值口径一行不改** → 217 条基线风险为零（§2.2 的算术）；
3. 上线风险可控：关闭开关时 `graph_recall_chunks` 恒空，`current_chunks` 四元组的第四项是空列表，行为与今天逐字节等价；
4. 若塞进 `chunks`：`final_score≈0` 的片会参与排序与 `retrieved[0]` 的阈值语义，且 `TOP_K_RERANK=8` 截断后根本进不了上下文（白算）。

**必须同步改的第二处（易漏）**：`app/services/retrieve/chain.py::merge_rounds()` 的合并逻辑要加一段 —— 否则**链式多轮检索会静默丢掉图召回片**（多轮时 `retrieve_chain` 走 `merge_rounds`，它只合并 `chunks` / `table_recall_chunks` / `section_recall_chunks`）：

```python
graph_recall: dict[uuid.UUID, RetrievedChunk] = {}
for chunk in result.graph_recall_chunks:
    if chunk.chunk_id in merged or chunk.chunk_id in recall or chunk.chunk_id in section_recall:
        continue                       # 与命中片/表格/章节互斥，避免同片进上下文两次
    graph_recall.setdefault(chunk.chunk_id, chunk)
```
并把 `path_stats` 的 `graph_*` 键按轮累加（既有 `for key, val in result.path_stats.items()` 循环已自动覆盖，无需改）。

> **口径注意（链式多轮唯一一处「求和 ≠ 交付」）**：`path_stats` 是**按轮求和**，因此多轮请求的 `graph_unique` 合计可能**大于**最终去重后的交付片数 —— 同一片在两轮都被图召回、且两轮都没进命中片时，它计 2 而交付 1。**评测统计 MUST 以逐请求的 `len(graph_recall_chunks)` 求总和为准**（评测走单趟 `retrieve()`，结构上不触发该差异）；生产审计行里是累加值，用于看趋势、不是精确交付量。两者不可混用（同「基数」列的口径纪律）。

**拒答分支也必须带回原因（第 2 步验证 P2-4 · §9.8 裁决 2）**：`merge_rounds()` 有两处 `refused` 早返回（`merged` 为空 / 合并集低于阈值），当前两处都不带 `graph_degraded_reason` —— 实测：只有图召回片的单轮合并 → `refused=True, degraded=''`，原值 `'timeout'` 被丢。契约要求按「元信息 / 证据」两类分开处理：

| 字段 | 拒答分支 | 理由 |
|---|---|---|
| `graph_degraded_reason` | **MUST 带回**（规则同为「取首个非空」） | 恰恰是拒答时运维最需要知道「图那一路是不是也没跑通」。`refused + degraded=''` 的审计行无法区分「图正常但没邻居（调链接/抽取）」与「图超时了（调预算/查库）」—— 这两种处置完全不同 |
| `graph_recall_chunks` / `table_recall_chunks` / `section_recall_chunks` | **MUST NOT 带回**（保持现状，不是遗漏） | 拒答的语义是「本次没有可用证据」。带上补充片会造出「`refused=True` 且上下文非空」这个未定义状态：审计行自相矛盾；且将来若有人把 `chat.py` 改成「拒答也读 `current_chunks`」，就会变成「模型看到证据却回答『抱歉没找到』」 |

实现写法（两处早返回各加一个关键字参数，不改动任何既有字段）：

```python
return RetrievalResult(
    refused=True, refuse_reason="NO_RELEVANT_CONTENT",
    stage_ms=stage_ms, score_source=score_source, use_rerank=use_rerank,
    graph_degraded_reason=graph_degraded,      # ← 新增，两处早返回都要加
)
```

**验收**：单轮只含图召回片、`graph_degraded_reason='timeout'` → 返回 `refused=True` 且 `graph_degraded_reason='timeout'`；**两处早返回各一条用例**（只测一条会漏掉阈值那处）。

**`retrieve()` 内的 8 步时序（关键改动点，逐条对应既有行号区间）**：

| 步 | 内容 | 与现状的关系 |
|---|---|---|
| 1 | 三路召回（vector / tsquery / ILIKE） | 不变 |
| 2 | RRF 融合、取 top50 候选 | 不变 |
| 3 | rerank（默认关） | 不变 |
| 4 | 构造 `RetrievedChunk`、**L1 阈值闸门** | 不变 |
| 5 | **【新增】图召回**（闸门之后） | 新增：`recall_by_graph()` → `graph_recall_chunks`。**整块由 `if settings.graph_enabled` 包住，且图代码延迟 import** —— 关图时不发一条 SQL、不加载图模块（「关闭 = 代码路径不执行」成为可证事实，而非口头约定） |
| 6 | 表格分片回捞 | 不变（`final_id_set` 需先并入图召回片，避免重复） |
| 7 | 章节补全 | 不变（同上） |
| 8 | 路径贡献打点（含 `graph_covered` / `graph_unique`） | 扩展两个键 |

**为什么图召回在闸门之后、回捞之前**：
- 之后 → 拒答路径不为图召回付费（约一半请求）；
- 之前（相对回捞/补全）→ 让图召回片先占 `final_id_set`，表格/章节回捞据此排除重复（顺序反了会出现同一片进上下文两次）；
- 若图召回超时并 `rollback()`，后续只有表格/章节两条 SQL 受影响，且都已 `try` 包住的范围外 —— 因此 `rollback()` 必须在离开 `recall_by_graph` 前完成（§9.2 已写进契约）。

### 9.5 决策契约增量（`decisions.py`）：哪些 `Final`、哪些 `settings`

**判断标准（本设计的口径，写清以便后人复用）**：

> - 进 `decisions.py` 的 `Final`：影响**判定语义或口径**的值（阈值、排序依据、条数/预算上限、可见性、版本号），或**改动后会让评测基线失去可比性**的值，或**必须与代码里的文本/常量同源**的值（prompt 版本 ↔ prompt 正文）。
> - 进 `settings`（环境变量）：**随部署环境取不同值是正常且预期**的值（开关、模型名、端点、超时、批量、并发、资源护栏）。
> - **两者都不进**：同一个值在两处都有 —— 那是「两个真源」，比一个都没有更危险（见 `decisions.py` 里 `ALLOWED_EXT` / `OCR_ENABLED` 的注释）。

**新增 `Final` 常量（12 项，附注释要点）**

| 常量 | 类型 | 默认值 | 注释要点 |
|---|---|---|---|
| `GRAPH_MAX_HOPS` | `Final[int]` | `2` | 图扩展跳数上限。**与 `TOP_K_RECALL` 同类：改它=评测基线不可比**。>2 会增加噪声邻居与递归深度（1 跳=直接共现实体，2 跳=跨概念桥接；3 跳起噪声超过信号） |
| `GRAPH_MAX_HOPS_HARD_LIMIT` | `Final[int]` | `2` | `self_check` 用：`GRAPH_MAX_HOPS` MUST ≤ 本值（防有人为了「多跳更好」调到 5 把查询打成秒级） |
| `GRAPH_LINK_MAX_ENTITIES` | `Final[int]` | `8` | 单次查询最多取几个种子实体。太多→噪声种子引入无关子图；与 `ILIKE_MAX_TERMS=3` 同量级思路（宁可少而准） |
| `GRAPH_LINK_MAX_TERMS` | `Final[int]` | `3` | 实体链接用的词元上限（复用 `build_fts_query` 后截断） |
| `GRAPH_RETRIEVE_TOP_K` | `Final[int]` | `10` | 图扩展返回的候选 chunk 上限（去重后）。**不是最终上下文条数**，后者由 `GRAPH_RECALL_MAX_CHUNKS` 与 token 预算共同约束 |
| `GRAPH_RECALL_MAX_CHUNKS` | `Final[int]` | `3` | 进入上下文的图召回片上限。与 `TABLE_RECALL_MAX_CHUNKS` / `SECTION_RECALL_MAX_CHUNKS` 取同值（3），保持三类补全片的量级一致 |
| `GRAPH_RECALL_TOKEN_BUDGET` | `Final[int]` | `1_200` | 图召回片总 token 预算（按 `chunks.token_count` 累计）。与 `SECTION_RECALL_TOKEN_BUDGET` 同值：两者都是「锦上添花的上下文」，不该比它更贵 |
| `GRAPH_EXTRACT_BATCH_CHUNKS` | `Final[int]` | `4` | 单次 LLM 调用送几个 chunk。太少→调用次数爆炸；太多→单次超时且实体跨段错配。4 ≈ 2K token 输入，稳落在 120s 超时内 |
| `GRAPH_EXTRACT_MAX_CHUNKS_PER_DOC` | `Final[int]` | `200` | 单文档抽取分片上限（资源护栏，同 `EMBEDDED_IMAGE_MAX_PER_DOC` 的思路）。超限 → `graph_status='skipped'` + 日志（不静默） |
| `GRAPH_ENTITY_NAME_MAX_CHARS` | `Final[int]` | `40` | 实体名长度上限，超长丢弃（LLM 会把整句当实体名输出） |
| `GRAPH_MAX_ENTITIES_PER_CHUNK` / `GRAPH_MAX_RELATIONS_PER_CHUNK` | `Final[int]` | `12` / `12` | 单 chunk 抽取量上限。超限截断（防一篇 prompt 里塞进 200 个实体把落库打成风暴） |
| `GRAPH_ENTITY_TYPES` | `Final[tuple[str, ...]]` | `("PERSON","ORG","PRODUCT","TERM","POLICY","PROCESS","SYSTEM","OTHER")` | 类型闭集，与 DDL 的 CHECK 一一对应（`self_check` 校验两处一致 —— 这是本项目既有做法：`GOVERNANCE_DIM_WEIGHTS` 也校验键集） |
| `GRAPH_PROMPT_VERSION` | `Final[str]` | `"gprompt-v1"` | 抽取 prompt 正文版本（见 §2.3）。放在 `config/graph_profile.py` 而非 `decisions.py`（与 `EMBEDDING_TEXT_VERSION` 同位，保持「口径模块」自洽） |

### 9.7 实现偏离记录（第 2 步 · commit `02efb8d` 审核结论）

> 审核范围：coder 报回的 3 处实现偏离 + 2 项自行裁量。**结论分三类**：采纳（写进契约）/ 采纳但需整改（有验收标准）/ 否定（不可接受）。
> 表内「触发条件」必须是**真库事实或可复现证据**，不接受「我觉得这样更好」。

#### 偏离 1 · `link_entities()` 多收 `extractor_model` / `prompt_version`

| 项 | 内容 |
|---|---|
| **偏离内容** | 设计 §9.2 原签名无口径参数；实现增加两参数，并在三层 SQL 的 `_SCOPE_WHERE` 里加 `EXISTS (… m.extractor_model = :em AND m.prompt_version = :pv)` |
| **触发条件（证据）** | `0024_add_graph_tables.py` 实测：`graph_entities` 只有 `name / name_key / name_fts / name_vec / entity_type / aliases / doc_freq`，**没有口径列**；口径落在 `graph_entity_mentions` 与 `graph_relations` 上。这是 §8.1 的设计原样（实体是 KB 内合一的共享节点）。因此「实体读取按口径过滤」在设计给出的表结构上**根本无法按实体列实现** |
| **采纳结论** | **采纳。** 且这不是迁就实现，而是原契约写错了：契约 2 说「所有读取必须按口径过滤」，隐含「被读的行有口径列」；对实体节点这个前提不成立 |
| **对契约的影响** | §9.1 契约 2 已改写为 2a（证据读：mention / relation 带口径）+ 2b（节点读：MUST 附带「当前口径至少一条提及」的 EXISTS）。**2b 是新增的硬要求**，理由是可复现的静默失效：漏了 2b → 旧口径实体占满 8 个种子名额 → `neighbors()` 已按口径滤净它们的边 → 恒 0 邻居，且现象与「这个库真没有相关实体」完全一样 |
| **是否会出现「种子 v2、边 v1」的混合口径** | **不会。** 逐条核过 `neighbors()` 的 SQL：① `walk` 递归只在 `graph_relations` 上展开，`JOIN ... WHERE r.extractor_model=:em AND r.prompt_version=:pv`；② 末端 `JOIN graph_entity_mentions m ON m.entity_id=a.entity_id AND m.extractor_model=:em AND m.prompt_version=:pv`；③ 实体节点本身无口径列，因此不存在「实体自带 v1/v2」这回事。结论：**所有参与结果计算的证据行（边 + 提及）都是当前口径** |
| **验收标准（已满足，留作回归）** | `tests/graph/test_linking.py` 存在「旧口径实体不进种子」用例；`tests/graph/test_graph_recall_sql_contract.py` 断言两层口径过滤均在 SQL 文本内 |

#### 偏离 2 · `SET LOCAL` → `SELECT set_config('statement_timeout', :ms, true)`

| 项 | 内容 |
|---|---|
| **偏离内容** | 设计 §9.2 第 1 步原文为 `SET LOCAL statement_timeout = :timeout_ms`；实现改为 `SELECT set_config('statement_timeout', :ms, true)`（`ms` 传 `str(int(...))`） |
| **触发条件（证据）** | `SET` 是**工具语句（utility statement）**，其右侧不接受绑定参数；asyncpg 走扩展查询协议会发 `$1` → PG 报 `syntax error at or near "$1"`。`set_config(name, value, is_local)` 是普通函数，参数可绑定，`is_local=true` 即 `SET LOCAL` 语义（事务结束自动复原） |
| **语义等价性判定** | **等价，且实现选的这条路是唯一可走的路。** 逐条核对：① SQLAlchemy 2.x `AsyncSession` 是 autobegin 语义 —— 进入 `retrieve()` 后前面的三条召回 SQL 已开启事务，`set_config(...,true)` 落在这个已开启的事务内，**不存在「事务没开 → 设置立即失效」的窗口**；② `is_local=true` 的作用域到事务结束，与本步骤「只约束本次检索」的意图一致；③ 值以字符串传入（`'800'`）符合 `statement_timeout` 的单位约定（无单位默认毫秒） |
| **采纳结论** | **采纳。** 设计原文的 `SET LOCAL … = :param` 是一句**写不出来的 SQL**（照抄即报错），属设计笔误 |
| **但附带一条整改要求（P2，必须做）** | `set_config(...,true)` 的作用域是**整个事务**，而 `recall_by_graph` 返回后，同一事务里还要跑「表格回捞」「章节补全」两条 SQL（见 §9.3 第 6/7 步）。**于是 800ms 的 statement_timeout 会溢出到这两条 SQL 上**：原本「慢但能成功」的回捞，现在会变成 `QueryCanceled` 异常（章节补全块没有 try 包裹 → 直接冒泡成 `VECTOR_STORE_DOWN`）。这是一处**未声明的行为变更**，且方向是「把可成功的请求变成失败」。<br>**整改**：在 `recall_by_graph` 成功路径的最后一条 SQL 之后、返回前，补一次 `SELECT set_config('statement_timeout', '0', true)`（降级路径已 `rollback`，事务级设置随事务消失，无需重置）。<br>**验收**：① 单测断言成功路径的最后一条 SQL 是这次重置；② 集成断言：`recall_by_graph` 返回后，同 session 执行 `SELECT current_setting('statement_timeout')` 为 `0`；③ 在重置 SQL 的注释里写清「为什么必须重置」（溢出到回捞/补全） |

#### 偏离 3 · 第三层子串兜底用 `name_key ~* :pattern`（正则）而不是 `LIKE '%key%'`

| 项 | 内容 |
|---|---|
| **偏离内容** | 设计只写了「子串兜底」，未定实现；实现复用 `keyword_text.build_ilike_pattern(keys)` 产出 POSIX 正则，用 `e.name_key ~* :pattern` |
| **触发条件（证据）** | `name_key` 里含 `_`（如 `get_retrieval` 归一后仍带下划线）。SQL `LIKE` 中 `_` 是**单字符通配符** → `LIKE '%get_retrieval%'` 会命中 `getXretrieval`；`%` 同理会命中任意串。这是**正确性缺陷**，不是风格问题。`build_ilike_pattern` 对非型号词元做 `re.escape`、对型号词元展开 `[-_ ]?`，正好一次解决「通配注入」与「型号三种写法」两件事 |
| **性能判定（这是本节的重点，不是风格）** | **正则并没有让索引"更加"失效 —— 它和设计原意（`LIKE '%x%'`）一样都用不上 B-tree。** 事实拆解：<br>① 可用索引只有 `uq_graph_entities_kb_key (kb_id, name_key)`（B-tree）与 `idx_graph_entities_kb (tenant_id, kb_id)`；<br>② **未锚定**的 `~*` 或未锚定的 `LIKE '%x%'` 都**无法**走 `name_key` 的 B-tree（前缀不可提取）；<br>③ 真正起作用的过滤是 `WHERE e.tenant_id = :t AND e.kb_id = ANY(:kb)` → 命中 `idx_graph_entities_kb`，把扫描范围**收敛到单个 KB 的实体集**；<br>④ 因此成本 = **O(该 KB 的实体数)**，与正则/LIKE 无关。按 `name_key` 长度（≤40 字符）估算：10k 实体 ≈ 3~8ms；100k ≈ 30~80ms；500k ≈ 200~400ms（**估算，未实测**）；<br>⑤ 触发频率不低：第三层只在第 1/2 层合计 < 8 个种子时才跑 —— 而「这句话没提到库里任何实体」恰恰是最常见的情形，也就是**否定路径（最该快的路径）付最贵的账** |
| **采纳结论** | **采纳正则（正确性不可让）。** 但必须补一个**规模护栏**，否则本设计的「图召回 p95 ≤ 80ms」在大库上不可证 |
| **整改要求（P2，可随本步或下一 hotfix 落地）** | 新增 `decisions.GRAPH_LINK_SUBSTR_MAX_ENTITIES: Final[int] = 20_000`；在第三层 SQL 之前做一次 `SELECT count(*) FROM graph_entities WHERE tenant_id=:t AND kb_id = ANY(:kb)`（走 `idx_graph_entities_kb`，index-only），超过阈值则**跳过第三层**并 `metrics.incr("rag.graph_link.substr_skipped", reason="too_many")`。<br>理由：兜底层的**价值**随实体数下降（大库里子串噪声更大、准确率更低），**成本**随实体数线性上升 → 存在交叉点，过了就该停。<br>**验收**：① monkeypatch count 超阈值 → 第三层 SQL 不发出且指标 +1；② 在 `--dry-run` 或压测里贴一次 `EXPLAIN` 记录，证明计划是「`idx_graph_entities_kb` 索引扫描 + Filter」，而不是全表扫 |
| **未来可选解（不在本步）** | `pg_trgm` 的 `gin_trgm_ops` 索引可支持 `~*` 走索引，但需要 `CREATE EXTENSION pg_trgm`（私有化交付里是**一次部署变更**，且部分托管 PG 需超级用户）。登记为 §20-U9 |

**附带观察（不阻塞，P3）**：`_FTS_SQL` 的排序是 `ORDER BY e.name_key, e.id` 而非 `ts_rank`。当某 KB 里命中 tsquery 的实体超过 `limit*4` 个时，进种子的那一批是**按名字字典序**取的前 32 个，与相关性无关 —— 名字靠后的实体可能永远进不了种子。`name_vec` 是存储列，`ts_rank(name_vec, to_tsquery(...))` 可用且不触发逐行重算（与 README 记录的「读存储列 1.9ms vs 重算 142ms」同一个知识点）。建议后续改成按 `ts_rank` 排序，本次不强制。

#### 裁决 A · 新增字段 `RetrievalResult.graph_degraded_reason`

**结论：收进契约（已写入 §9.3 字段清单），不删。** 三条理由：

1. **它与 `path_stats` 语义不同类，不能合并**：`path_stats` 的键是 `{path}_{measure}` 且 `merge_rounds` 对它是**按轮求和**；原因不可加（"timeout" + "no_entities" 相加没有意义，取并集也没有意义）。把原因塞进计数容器，会让「求和」这条既有合并规则出现例外分支 —— 为了省一个字段给所有 `path_stats` 读者埋一个特例，不划算。
2. **既有同形先例三个**：`refuse_reason`、`score_source`、`chain_mode` 都是「单请求状态 str，空串为默认」，且都被审计/日志消费。新增一个同类字段不引入新模式。
3. **失败可见性的必要性**：`rag.graph_recall.degraded{reason}` 是**聚合指标**（只知道总量），日志是可查的**离散记录**（需要反查）。而 `chat.py` 把 `stage_ms` / `path_stats` 写进审计行 —— 有了这个字段，「这条回答当时图为什么没结果」可以直接从审计行读到，不用去捞日志。这正是设计 §4.1「失败必须分类且可见」的落点。

**要求补一条**：`merge_rounds` 的合并规则必须在 docstring 写明「取首个非空」（已实现为此，写进契约即可，防以后有人改成拼接或覆盖）。

#### 裁决 B · 评测口径断层（**最需要结论的一条**）

**事实核对（比 coder 报的更严重）**：`app/services/eval_service.py` 直调 `retrieval.retrieve()` 后，只把 `result.chunks` 传给 `generation.generate()`；`table_recall_chunks` / `section_recall_chunks` / `graph_recall_chunks` **三类补充片都没进评测上下文**。这意味着：

- 这不是「图没法测」的新问题，而是**既有断层**：当前 217 条基线（可答 100% / 漏答 0% / 拒答正确率 100% / 命中 100%）是在**比生产更少上下文**的口径下测出来的。生产 `chat.py` 拼四类，评测只拼一类。
- 另外 `eval_service` 调的是 `retrieve()` 而不是 `retrieve_chain()` → **链式检索在评测里从未被执行**。这是同一类断层的第二个实例。
- 直接后果：`GRAPH_ENABLED` 开/关两轮评测的分数会**逐字相同**（图片根本进不了评测的生成上下文），§14.6 的判据不可测。

**裁决**：

| 走法 | 结论 |
|---|---|
| **② 只聚合 `graph_covered/graph_unique/degraded_reason` 进评测报告** | **本步采纳（现在就能做，零风险）。** 它能回答「图是否补了东西」，是存废判据（§14.6 第 1 问）。但它**不能**回答「图是否让回答更好」——**禁止**用它宣称质量提升。报告里必须显式标注：「本次评测未将图召回片注入生成上下文，故本报告不覆盖图对答案质量的影响」 |
| **① 评测侧也拼四类补充片（与 chat 一致）** | **技术上我推荐，但必须由管家节点拍板 —— 它是「改判据」级别，不是实现细节。** 理由：① 代码成本近乎为零（`generation.generate(...)` 的实参从 `result.chunks` 改成一个四元组，与 `chat.py` 逐字同形），② 它同时修掉 table/section 的既有断层，让「评测通过」重新等于「生产行为通过」，③ 代价是一次性基线重标（`case_fingerprint` 不变，`_compare_baseline` 与**最近一次同用例集**比对，跑一次即成为新基线）。<br>**风险是单向的**：现基线四个指标已顶到 100%/0%/100%/100%，重标只可能**持平或下降**。若下降，说明生产口径确实比评测口径差 —— 那是**必须知道**的信息，但会即刻挡住当前发布门禁，故不能由实现方自行决定 |

**我的建议路径（供上报）**：
1. 本步按 ② 落地，报告加免责标注；
2. 把 ① 作为独立事项上报管家节点，附一个更小的替代选项 ①-b：**保留现有「纯三路」基线不动**，另加一个 `--with-recall-chunks` 开关跑「生产等价」口径，两套口径各自维护基线 —— 代价是双基线，好处是历史基线不废、可做「口径差异」的定量对比（这本身是有价值的观测：补充片到底贡献了多少）；
3. 链式检索缺失（`retrieve()` vs `retrieve_chain()`）与 ① 同批上报，不要单独改 —— 它同样动基线。

**为什么我不直接判 ① 必须做**：它会改变「什么算合格」这件事本身。设计文档可以主张「评测应当等于生产」，但不能替项目决定「用新基线还是双基线」——这是拿到管家节点桌面上的选择题，不是我在文档里能单方面定的。

### 9.8 契约层三条裁决（第 2 步独立验证 · `04-test/测试报告-第2步.md`）

> 裁决范围：**只裁契约层面三条**（P2-5 / P2-4 / P2-3）。报告里其余 P2（还原 SQL 无墙钟上限、取片 10 片全文再裁、`_COUNT_SQL` 注释与实测计划不符）属实现优化，已分派 coder，本节不涉及。

| # | 报告条 | 问题一句话 | 裁决 | 落到本文哪节 |
|---|---|---|---|---|
| 1 | P2-5 | `graph_unique` 以「三路候选池」为分母，实测恒为 0 | **推翻原口径，改锚「最终上下文」** | §9.3 字段口径 + §14.6 判据 1 |
| 2 | P2-4 | `merge_rounds` 两处拒答早返回丢掉 `graph_degraded_reason` | **违背契约意图，必须修** —— 但只补「原因」，不补「片」 | §9.3 合并规则 |
| 3 | P2-3 | 种子层不做 ACL（`seeds=7` 而 `chunks=0`） | **接受为残余风险**，登记且写明失效条件 | §10.1-R1 |

#### 裁决 1 · `graph_unique` 必须改锚「最终上下文」（推翻 v1.1 口径）

**结论：推翻我自己的口径，不是实现写错了。** v1.1 的实现严格按 v1.1 的文档写的；错在文档：原表把参照系写成「三路候选池」——那是 150 个 id 的**粗召回池**，而交付上下文只有 8 条。图扩展出的邻居绝大多数本来就落在粗池里（只是没进 top-8），于是这个指标**在结构上**不可能大于 0。实测三行数据（§9.9）证实：`Next.js` 那句真补了 2 片进上下文，`graph_unique` 仍是 0。

**为什么这不是「数字难看」而是必须改**：一个结构上永远为 0 的指标，会让验收者试几次之后学会无视它 —— 与「就绪度闸门永远红」属同一类错误（设了一个不可能满足的判据，等于没有判据）。而它的读者是**存废决策者**（§14.6 判据 1），错的方向是「把有用判成无用」。

**精确整改要求（三处，缺一不可）**：

| 改哪 | 改成什么 |
|---|---|
| `recall_by_graph()` 的**入参** | 增 `exclude_chunk_ids: Collection[uuid.UUID]` = 最终命中片 id 集合（`retrieve()` 第 5 步已知）。**只用于「不重复占预算 + 统计重复度」，MUST NOT 进排序或打分** |
| 预算裁剪的**顺序** | **先排重、后裁剪**：先跳过 `exclude_chunk_ids` 中的邻居并累计 `duplicate_count`，再按 `(hop, weight)` 取前 N 片。否则重复邻居（权重最高的一跳）系统性占满预算名额 |
| `graph_covered` / `graph_unique` 的**定义** | `graph_covered` = 被跳过的重复邻居数（裁剪前统计）；`graph_unique` = `len(result.graph_recall_chunks)`（交付片数）。两者基数不同，**MUST NOT 相加或算比率** |

**验收断言（§14.6 三条真库用例，逐条必须能红能绿）**：`Next.js App Router vs Pages` → `graph_unique ≥ 1`（旧口径下恒 0，是这次改动的直接证据）；`AX3000/AX6000 价格` → `graph_unique = 0` 且 `graph_covered = 3`（证明「重复」没被算成「有用」）；重算等式 `graph_unique == len(graph_recall_chunks)` 必须成立（可直接复算，不依赖任何内部变量）。

#### 裁决 2 · 拒答分支丢 `graph_degraded_reason`：违背契约意图（部分）

**结论：违背，必须修 —— 但只修原因字段。** 判据是「这个字段的读者在拒答时还需不需要它」：`refused=True` 且 `degraded=''` 的审计行，无法区分「图正常但没邻居」（该调链接/抽取）与「图超时了」（该调预算/查库）—— 而**拒答恰恰是最需要这个区分的时候**（一批请求持续 0 召回，第一件事就是看图那一路是不是也没跑通）。

**同时必须守住另一半**：`graph_recall_chunks` / `table_recall_chunks` / `section_recall_chunks` **不得**跟着回填。它们是「证据」，拒答的语义是「本次没有可用证据」；回填会造出 `refused=True` 且上下文非空的未定义状态。契约要求与实现写法见 §9.3。

#### 裁决 3 · 种子层不做 ACL：接受为残余风险（登记，不是「以后再说」）

**结论：接受，但必须登记成一条带失效条件的残余风险，而不是留成一句「已知问题」。** 依据：内容不泄漏（取片层四闸门是唯一出口）、实体名不外泄（只出计数）、可泄漏的只有「某名字的实体在该 KB 存在」这一位信息，且该信息对有读权限者本就可由命中排序/拒答率推断 —— 不新增泄漏类别。**这里的关键不是「风险很小」，而是「写清什么条件下它不再可接受」**（多密级同库的合规要求出现时，必须加 `EXISTS` 可见提及）。完整论证、影响面边界与三条失效条件见 §10.1-R1。

### 9.9 真库实测记录（第 2 步验证，`04-test/测试报告-第2步.md` §7）

> 环境：dev 单机、真实 PostgreSQL；图数据 432 实体 / 182 关系；口径 `gpt-4o-mini` + `gprompt-v1`。这一节只记**事实与它否证了什么**，不记推断。

| 问句 | 交付片（`chunks`） | 图召回片（进上下文） | `graph_covered` | `graph_unique`（旧口径） | 它否证了什么 |
|---|---|---|---|---|---|
| `AX3000/AX6000 价格` | 8 | 0 | 3 | 0 | 「`covered > 0` 就说明图有用」不成立：3 个邻居全在命中片里，是纯重复 |
| `Next.js App Router vs Pages` | 8 | **2** | 2 | **0** | **旧口径失效的直接证据**：真补了 2 片，指标仍是 0 |
| `差旅费报销凭证` | 8 | 0 | 0（`no_entities`） | 0 | 「两者都 0 = 图太稀」是错的归因：这次是**链接不到实体**，不是图稀 |

**三条结论**：

1. **旧口径的失效是结构性的，不是采样偶然** —— 表中第二行是最小反例：只要分母是三路候选池（可达 150 个 id）而交付只有 8 条，`graph_unique` 就只能在「图召回的邻居一个都不在粗池里」时才非 0，而那正是图**最没用**的情形（连粗召回都碰不到的片，多半离题）。判据与信号是反相的。
2. **「0 值」至少有三种成因**，必须分类（§14.6 归因表）：纯重复（第一行）、口径错（第二行）、链接失败（第三行）。旧文档把三者合并成「图太稀」一条，会把「链接召回不足」误诊成「实体抽取不足」，处置方向完全相反。
3. **这三行同时就是回归锚点**：改完 `exclude_chunk_ids` 与「先排重后裁剪」之后，第二行必须变成 `graph_unique = 2`（数值上等于它进上下文的片数），第一行必须保持 `0/3` 不变 —— 若第一行也跟着变成非 0，说明「排重」被实现成了「去重后重复计数」，那是把 bug 从一边翻到另一边。

### 10.1 已评估并接受的残余风险（登记项，不是待办）

> 这一节登记「知道它不完美、评估过、决定接受」的项。每条必须给三样东西：① **影响面的精确边界**（不是「应该没事」）；② **为什么接受的量化理由**；③ **什么条件下这条接受失效**。一条没有失效条件的「已接受」等于永久免责，那不叫评估。

#### R1 · 种子层不做 ACL 过滤（第 2 步验证 P2-3 实测）

**事实**：`public-only` 主体调用 `recall_by_graph`，种子层返回 `seeds=7` —— 因为种子层只按 `tenant_id / kb_id / 口径` 过滤（`graph_entity_mentions` 没有 `acl_tags` 列，见 §8.4「ACL 不冗余存」），挡人的是**取片层**的四闸门，结果是 `chunks=0`。

**影响面边界（逐项划清，不含糊）**：

| 维度 | 会不会泄漏 | 依据 |
|---|---|---|
| 文档内容 | **不会** | 取片层是唯一出口，带 `_WHERE_BASE`；§14.5 越权测试集四类反例全绿 |
| 实体名本身 | **不会** | 种子实体只用于内部扩展，不出现在响应体、审计行或日志文本里；`path_stats` 只带计数 |
| 「某名字的实体在该 KB 存在」这一位信息 | **会（弱侧信道）** | 可观测两个量：`graph_seed_count`（计数）与图召回耗时（毫秒级差异），二者与「库内有无该实体」相关 |
| 算力 | **白付一跳** | 实测 `seeds=7 → neighbors=0 → chunks=0`：链接与递归扩展白跑，量级 1~10ms |

**为什么接受（三条，按分量排序）**：① **不增加新的泄漏类别** —— 有该 kb 读权限的用户本就能检索其全部内容，「这个主题库里有」这层信息可由既有检索的命中排序与拒答率推断；侧信道只是多了一条**更省采样**的路，不是一条**新**的路。② **成本与收益不成比例** —— 修它要在递归展开**之前**多一次 JOIN 回 `chunks` 并跑 `_WHERE_BASE`，把权限判定成本从「0 次」提到「每次检索 1 次」，而收益是省掉一次注定 0 片的扩展 + 消除 1 bit 级侧信道。③ **正确的最小处置不是加 ACL** —— 若在意白付一跳，零成本短路是「种子数为 0 不进扩展」，与 ACL 无关；两者被混为一谈会让这条风险看起来只能靠加 JOIN 解决。

**失效条件（任一出现 → 本条不再可接受，必须做种子层 `EXISTS (可见提及)`）**：① 客户提出「同一 kb 内多密级文档，低密级用户不得知道高密级主题存在」的合规要求 —— 这是唯一真正需要它的场景；② 证明 `graph_seed_count` 可被批量探测（例如按常见词表扫一遍即可反推库内实体清单）；③ 权限判定成本降到可忽略（如 `_WHERE_BASE` 被物化），此时「加 JOIN」不再是代价。

#### R2 · `graph_unique` 在生产审计行里是**按轮累加值**

**事实**：`path_stats` 在 `merge_rounds` 里按轮求和，而交付片按 `chunk_id` 去重 → 同一片在两轮都被图召回时，计数 2、交付 1（§9.3 口径注意）。
**为什么接受**：审计行要回答的是「这次请求在各路花了多少」，求和是对的；精确交付量由评测（单趟 `retrieve()`）回答，二者分工清晰。
**失效条件**：任何人要拿审计行做「图贡献了多少上下文」的报表 → 必须改成逐请求 `len(graph_recall_chunks)` 求和，不能沿用 `path_stats`。

#### R3 · 图扩展的**来源**是 LLM 抽取结果，抽取错了图就会召回噪声邻居

**事实**：实体/关系由快速低价档 LLM 抽取，可能抽错（把无关片判为共现）。图扩展据此召回邻居 → 噪声上下文。
**为什么接受**：**红线 A 让错误停在「多召回了几片原文」** —— 引用永远回 `chunks` 原文，图不产出任何被当作事实的文本；噪声片的实际代价是被 L4 预算裁掉或被生成侧忽略，不会变成「模型被告知了一个假事实」。
**失效条件**：判据 1 的辅助判据 `graph_unique / graph_covered < 0.25`（说明扩展结果以重复/噪声为主）→ 直接砍第 2 步，不靠调参硬撑（与 §14.6 归因表第二行同一处置）。

### 12.3 部署文档警告段落（`code/docs/DEPLOY.md` 新增 §3.5 全文）

```markdown
### 3.5 能力开关与重跑口径（图召回 / LLM wiki 导航）

> **这一节必须在部署前读完。** 图召回（GraphRAG）与 LLM wiki 导航是**部署期能力**：
> 只由环境变量决定，运行期不可切换、没有请求级开关、不按用户或部门放量。
> 私有化交付要的是「少一个运行时组件、少一份排障面、可审计」——
> 代价就是**能力档位在部署那一刻就定下来了**。

#### 3.5.1 开关清单

| 变量 | 默认 | 作用 | 开启后的额外要求 |
|---|---|---|---|
| `GRAPH_ENABLED` | `false` | 实体图召回（在线召回 + 离线抽取，同一开关） | 需要 LLM 凭据；需要迁移到 0025；开启后必须补建抽取 |
| `GRAPH_STORE_BACKEND` | `postgres` | 图存储后端 | 当前仅支持 `postgres`；填其它值服务**拒绝启动** |
| `GRAPH_EXTRACTOR_MODEL` | 空（跟随 `LLM_MODEL`） | 抽取模型 | 留空即用主模型；换它 = 口径变更，需重抽 |
| `GRAPH_RETRIEVE_TIMEOUT_MS` | `800` | 在线图召回硬超时 | 取值须在 50~5000 |
| `WIKI_ENABLED` | `false` | LLM wiki 导航（生成 + 术语扩展 + 导航页） | 需要 LLM 凭据；需要迁移到 0026；开启后必须重建 wiki 页 |
| `WIKI_SCOPE` | `doc` | 生成范围 | 本版仅 `doc`；填 `kb` 服务**拒绝启动**（详见 §7.5 的可见性论证） |

#### 3.5.2 三条硬规则

1. **部署前定好。** 这两项能力决定「数据要不要重跑」。上线后再改，等于对一笔已经在产的
   知识库做一次数据迁移 —— 请在部署评审时就定下来，写进交付单。
2. **fail-closed：开了但没有依赖 → 服务直接起不来，不会静默降级。**
   - 开了图但没配 `LLM_API_KEY` → 拒绝启动
   - 开了图但没跑迁移（表不存在）→ 拒绝启动
   - 开了图但 `GRAPH_STORE_BACKEND` 填了未实现的后端 → 拒绝启动
   这是刻意的：**「配了却不生效」比「起不来」危险得多**。本项目曾经吃过一次「只重建 api 镜像，
   worker 静默跑旧代码，任务照常返回成功」的亏。
3. **api 与 worker 必须同时重建、读到同一份能力配置。**
   抽取在 worker、召回在 api。只重建一侧会导致「一侧开、一侧关」，而它们在运行期不通信，
   **不会互相报错**。校验方法：比对两个容器的启动日志里「启动能力快照」的
   `config_fingerprint` 字段，必须相同；管理端「系统能力」页页脚也显示同一个指纹。

#### 3.5.3 变更后果矩阵（要重跑什么 / 不用重跑什么）

| 变更 | 要重跑 | 不用重跑 |
|---|---|---|
| 开图 `GRAPH_ENABLED true` | 补建抽取：`python -m scripts.backfill_graph --all` | 解析、分块、嵌入、wiki |
| 关图 `GRAPH_ENABLED false` | 不用重跑任何东西（已抽取的数据保留，便于快速回滚） | 全部 |
| 换抽取模型 / 抽取 prompt 版本 | 重抽：`python -m scripts.backfill_graph --recaliber` | 解析、分块、嵌入 |
| 开 wiki `WIKI_ENABLED true` | 重建页面：`python -m scripts.rebuild_wiki --all` | 解析、分块、嵌入、图抽取 |
| 关 wiki `WIKI_ENABLED false` | 不用重跑（页面保留，读接口返回 404） | 全部 |
| 换 wiki 生成模型 / prompt 版本 | 重建页面：`python -m scripts.rebuild_wiki --recaliber` | 解析、分块、嵌入、图抽取 |
| 换分块器（`CHUNK_*` 变动） | **全链重跑**：解析 → 分块 → 嵌入 → 抽取 → wiki | —— |
| 换嵌入口径（模型 / 向量文本公式） | 只重算向量：`python -m scripts.reindex_embeddings` | 图抽取、wiki、解析 |

**为什么「换分块器」必须全链重跑**：重解析会 `DELETE chunks` 再 INSERT（分片是新 uuid）。
图数据与 wiki 页的证据都挂在 `chunk_id` 上 —— 分片一换，旧证据全部失效（数据库会级联删提及，
但会留下孤儿实体与指向死分片 id 的页面）。系统在重解析的同一事务里主动清理派生数据，
但**清理不等于重建**：抽取与生成仍需重跑。

**为什么「换嵌入口径」不用重抽图**：`scripts/reindex_embeddings.py` 是 `UPDATE chunks SET embedding=...`
（原地更新，`chunk_id` 不变），分片文本没变 → 实体与关系仍然有效。

#### 3.5.4 开启图能力后的上线验收（缺一不可）

1. `docker compose logs api | grep capability.banner` 与 `logs worker | grep capability.banner`
   → 两条的 `config_fingerprint` **相同**且 `graph.enabled=true`
2. `python -m scripts.backfill_graph --dry-run` → 输出待补建文档数，与预期一致
3. 补建完成后：管理端「系统能力」页 `documents_pending = 0` 且 `documents_failed = 0`
4. 越权回归：`pytest tests/graph/test_store_acl.py -v` 全绿（四类邻居零命中）
5. 评测门禁：`python -m scripts.run_eval --baseline`
   → 可答通过率 / 漏答率 / 拒答正确率 / 命中率 四项**不劣化**，且 `metrics.graph_unique_total > 0`
6. 若第 5 步 `graph_unique_total == 0`，**先按设计文档 §14.6 的归因表分类**：
   纯重复（`graph_covered > 0`）/ 链路级失败（降级占绝大多数）/ 链接召回不足
   （`no_entities` 为主）/ 图太稀（`no_neighbors` 为主）—— 四种处置方向完全不同，
   不要一律当作「图太稀」去重跑抽取。归因为「纯重复」时**不要上线这条路径**，回到设计评审。
```

### 12.4 启动自检失败文案（fail-closed 的错误原文）

这些文案会出现在容器启动日志里并 `exit 1`。要求：说清「哪里错、为什么不允许静默回落、怎么修」。

[GRAPH_STORE_BACKEND] GRAPH_ENABLED=true 但 GRAPH_STORE_BACKEND='neo4j'：
  本版本未提供 Neo4j 适配实现（端口已留位，实现未写）。
  请置 GRAPH_STORE_BACKEND=postgres；若暂时不用图能力，置 GRAPH_ENABLED=false。
  ★ 拒绝启动 —— 静默回落到 postgres 会让你以为在跑 Neo4j，而数据实际在 PG 里。

  ★ 拒绝启动 —— 表缺失时每次问答都会静默走 0 路图召回，没有任何人会知道。

[GRAPH_HEALTH] GRAPH_ENABLED=true 但图存储健康检查失败：{具体异常类型}
  请检查 PostgreSQL 可达性与 migrations 版本（当前 DB revision={rev}，代码 head={head}）。
  ★ 拒绝启动 —— 配了却验证不了，等价于没配。

  KB 级页面会把多篇不同密级的文档摘要合成一个对象，无法用文档级四闸门表达可见性

  请置 WIKI_SCOPE=doc，或置 WIKI_ENABLED=false。
  ★ 拒绝启动 —— 「悄悄按 doc 处理」会让你以为开的是 KB 级导航。

## 14. 评测与观测

### 14.1 配置指纹怎么进 `eval_runs`

现状：`run_eval.py` → `snapshot_for_message(tenant_id)` → `EvalRun.caliber`（JSONB）。本方案改两处，都在**既有数据结构内**，不新增列：

1. `config_profile.runtime_config_snapshot()` 增 10 个能力字段 + 4 个口径版本 → `config_fingerprint` **自动**随能力开关变化（`config_profile` 的 `sort_keys` + sha1 保证同名配置同指纹）。
2. `caliber.build_caliber_snapshot()` 增：
   ```python
   "capabilities": capability_snapshot(),      # 与启动横幅/管理端同源（capabilities.py 唯一真源）
   "graph_caliber": {"extractor_model": ..., "prompt_version": ...},   # 关闭时为 "off"
   "wiki_caliber": {"generator_model": ..., "prompt_version": ..., "scope": ...},
   ```
   理由：指纹只能判「两次是否同配置」，**不能告诉你差在哪**。口径字段是给人看的。

**注意（避免误伤基线）**：`_compare_baseline()` 只比对 `refusal_rate` / `hit_rate` / `miss_rate` 三个键（硬编码方向表），基线检索用 `case_fingerprint`。所以**新增 caliber 字段与新增 metrics 键都不会改变门禁行为**，历史 `eval_runs` 也不失效。这一点必须在编码时保持 —— 新的 `graph_*` 指标**只记录、不进方向表**（它们的波动不代表质量回退）。

### 14.2 指标清单（`app/infra/metrics.py` 的 `incr` / `observe_ms`）

### 14.6 如何证明「开了图之后变好」，而不是「感觉变好」

**A/B 方法（同一部署、同一语料、同一用例集，只变一个变量）**：

```bash
# 关图基线
GRAPH_ENABLED=false python -m scripts.run_eval --note "graph-off" --baseline
# 开图（图数据已补建完成）
GRAPH_ENABLED=true  python -m scripts.run_eval --note "graph-on"  --baseline
```
`run_eval.py` 是**进程内**直调检索/生成（不走 HTTP），`get_settings()` 是按进程缓存的 → 两次调用可用不同环境变量，**无需重启服务、无需两次部署**。这是本项目脚本化评测的直接便利，也是本方案能在 A/B 上给出硬证据的前提。

**判定四问（全部能答「是」才算变好，缺一即不上线）**：

| # | 问题 | 判据 | 不达标的处置 |
|---|---|---|---|
| 1 | 图路**真的给上下文补了新原文**吗？ | **主判据**：`graph_unique_total ≥ 11`，且落在**可答类**；**分母是 111 条可答类，不是 217**（理由见下）。**辅助判据（防「补了但全是噪声」）**：`graph_covered_total > 0` 时要求 `graph_unique_total / graph_covered_total ≥ 0.25`（探索过的邻居里至少 1/4 是新增）；`graph_covered_total = 0` 时该比值**无定义、不适用**，改看 `graph_unique_total > 0` | 按下方「归因表」处置；**不允许**用一句「图太稀」概括所有 0 值 |
| 2 | 质量**没有变差**吗？ | 四项指标（可答通过率/漏答率/拒答正确率/命中率）逐项不劣化；且 `graph_degraded_cases ≤ 1`。**必须在 `with_recall_chunks=true` 的同一口径下比两轮**（`GRAPH_ENABLED` 开/关）—— 用默认口径比是循环论证：两轮生成输入完全相同，分数必然相等 | 有劣化即回滚（`GRAPH_ENABLED=false`），并归因到「挤占上下文」还是「噪声邻居」 |
| 3 | 体感**没有变差**吗？ | 图召回 p95 ≤ 80ms；端到端 P95 增幅 ≤ 3%（用 `scripts/loadtest_chat.py` + stub LLM 隔离上游，对比 retrieve / TTFT / total 三个时间点） | 超了先查 `hop` 与图规模；仍超则把 `GRAPH_RETRIEVE_TOP_K` 或 `max_hops` 往回收（走代码评审，不改环境变量） |
| 4 | 成本**可接受**吗？ | 离线一次性：`graph_extract_llm_calls × 平均 token` 折算成金额，与「知识库总文档数」线性关系；单文档增量成本记录在验收单里 | 超预算 → 降 `GRAPH_EXTRACT_BATCH_CHUNKS` 无效（调用数不变），正确做法是**缩小抽取范围**（只抽 `heading_path` 非空的小节首片，或按 kb 分批开图） |

**判据 1 的分母为什么改成 111（这一步不能省，否则门槛被悄悄抬高 1 倍）**：图召回在 L1 阈值闸门**之后**（§9.3 第 5 步）——106 条不可答用例必然在闸门处 `refused` 提前返回，**永不执行图召回**，其 `graph_unique` 结构上恒为 0。所以「217 的 5%」实为「111 的 9.9%」，而文档写的是 5%，读者会按字面把门槛理解成一半。改成显式分母后：`11 / 111 ≈ 10%`，含义是「**十个可答问题里有一个**被图补进了新原文」，这是一个可以被人反驳、也可以被人接受的下限。

**归因表（五态，0 值必须先分类再处置；旧版把三种不同故障合并成「图太稀」）**：

| 观测组合 | 归因 | 处置 |
|---|---|---|
| `unique ≥ 11` 且 `unique/covered ≥ 0.25` | 图在补新原文，方向正确 | 进第 2 问（质量不劣化） |
| `unique = 0` 且 `covered > 0` | **纯重复劳动**：图扩展的邻居全在命中片里 | **砍掉第 2 步**，保留离线图（留给第 5 步的查询扩展）；台账记「一拍即知，不必再调参」 |
| `unique = 0` 且 `covered = 0` 且 `degraded_cases / 217 > 0.9` | **链路级失败**（缺依赖 / 口径不符 / 超时），不是图的问题 | 先修链路：C1~C8 启动自检 + 口径核对（`extractor_model`/`prompt_version` 与 `graph_profile` 是否一致） |
| `unique = 0` 且 `covered = 0` 且降级原因以 `no_entities` 为主 | **实体链接召回不足**（§20-U2） | 调 `GRAPH_LINK_MAX_ENTITIES` / 补 `aliases` / 接受词元级召回率上限（这是一个能力边界，不是 bug） |
| `unique = 0` 且 `covered = 0` 且降级原因以 `no_neighbors` 为主 | **图太稀**（抽取覆盖不足） | 看 `documents.graph_status` 分布与 `graph_status='failed'` 比例，修抽取 |

**口径回归的三条真库用例（验收 MUST 断言，值取自当前 dev 库实测）**：

| 用例 | 断言 | 它守的是什么 |
|---|---|---|
| `Next.js App Router vs Pages` | `graph_unique ≥ 1` 且 `graph_covered ≥ 1` | 旧口径下恒 0 的正例；真补了 2 片就必须记 2（旧的候选池口径记 0） |
| `AX3000/AX6000 价格` | `graph_unique = 0` 且 `graph_covered = 3` | 纯重复的正例：**不许把重复算成有用**，也不许把有用算成 0 |
| `差旅费报销凭证` | `graph_degraded_reason = "no_entities"` 且 `graph_unique = 0` | 降级必须带可读原因，不能是「0 片 + 空原因」 |

> ⚠ 前两条断言依赖库内图数据现状（换了库要重标期望值）；第三条只依赖「问句里没有库内实体」，是稳定的回归锚点。三条都应写进 `tests/graph/`，且**用 `path_stats` 而不是日志文本**断言。

**「变好」的最小可接受证据链**（写进验收单）：
`eval_runs` 两条同 `case_fingerprint` 的记录 + `caliber.config_fingerprint` 不同 + `caliber.capabilities.graph.enabled` 不同 + `caliber.context_caliber` **相同且为 `with_recall_chunks`** + `metrics.graph_unique_total > 0` + 四项门禁指标不劣化 + 越权测试全绿 + 压测 P95 增幅 ≤ 3%。

> **口径断层已按 ①-b 落地（commit `7b2252c`），本节的限制条件随之更新**：`EvalService.run_eval` 现有 `with_recall_chunks` 开关（默认 `false` = 旧基线逐字节可比），开启后走 `retrieve_chain()` 且四类上下文用唯一的 `assemble_context_chunks()` 拼装（与 `chat.py` 同源）。因此：
> - **第 1 问**（图补了东西）→ 两种口径都能答（`graph_unique_total` 与开关无关，始终聚合）；
> - **第 2 问**（答案不更差）→ **必须在 `with_recall_chunks=true` 下答**。默认口径下开/关两轮的生成输入完全相同，分数相等是构造使然，**不是证据**（这是循环论证，MUST NOT 写进验收单）；
> - **还差的一处（写着，不要假装没有）**：评测不做 query 改写（`rewrite_score=None` 使内部按信号不足降级单趟），因此「四类上下文 + 链式多轮」在评测里并不完整等价于生产 —— 生产若命中改写，轮次结构不同。验收单 MUST 写明「本证据覆盖上下文口径，不覆盖改写策略」；
> - **两条链路的口径不得混比**：`scripts/run_eval.py` 走 `/api/chat/ask` 生产链路（本来就是四类 + `retrieve_chain`，**没有请求级开关**，因此该脚本刻意不提供 `--with-recall-chunks` —— 提供它就是给一个骗人的空开关）；admin 门禁 `POST /api/admin/eval/run` 才有开关。报告与 `eval_runs.caliber` 都已带 `context_caliber`，比对基线前先核这一列，否则是拿两种口径互相判优劣。

## 15. 层间交叉检查

| 关系 | 说明 |
|---|---|
| C（上下文）↔ E（执行循环） | 图召回在闸门之后执行 → 拒答路径零成本；超时 800ms 是 E 层预算，1.2K token 是 C 层预算，两者独立但同源（`GRAPH_RECALL_*`）。若只调其中一个会出现「召回很快但上下文被挤爆」或「预算够但永远等超时」 |
| C ↔ S（状态） | 图召回片追加在上下文**最尾部**（裁剪优先级最低），且其内容来自 `chunks` 原文 → 前缀（system）字节不变 → 缓存命中率不受影响。**本方案对前缀缓存的影响 = 0**，这是它比「把图摘要塞进 system」更优的关键点 |
| T（工具/组件）↔ L（钩子） | `GraphStore` 的 `neighbors()` 契约内含四闸门 —— 这是「组件自带权限」，不是「调用方记得加权限」。L 层的纵深防御（单测文本断言 + 越权测试集）兜住「实现者写漏」这一层 |
| S ↔ V（评估） | 口径章（`extractor_model` / `prompt_version`）既是检索过滤依据，也是「这条评测结果按什么口径得出」的追溯依据 —— 没有章就无法解释「为什么这次评测命中率掉了」 |
| E ↔ S | 抽取是幂等写（先删后写）；在线召回是纯读。二者共用同一个 PostgreSQL 但**不同进程**，不共享事务 —— 意味着「抽取进行到一半时被召回」会看到部分数据（`graph_status='running'`）。这是**可接受的**：部分图数据就是部分召回，不会错（口径一致），只可能少。**不用加锁**，因为加锁会让检索等抽取，代价远大于收益 |
| L ↔ 部署 | 能力横幅 + `config_fingerprint` 是「两侧配置一致」的唯一机器化证据；没有它，「只重建一侧镜像」这类事故只能靠人记住 |
| V ↔ 成本 | `graph_unique` 既是质量判据也是成本判据：全量 217 条跑一次就知道「这条路径值不值它的维护成本」；但**判据只看可答类 111 条**（不可答类结构上恒 0，见 §14.6 分母说明） |
| V ↔ S（口径） | 评测分数只能在同一 `context_caliber` + 同一 `config_fingerprint` 下互比；`caliber` 同时落能力快照与上下文口径，就是为了让「这次分数变了是因为图，还是因为拼装口径变了」可被机器判定，而不是靠人回忆 |

|---|---|---|---|
| **E 执行循环** | 固定管线追加一个串行子步骤（不并行、不循环、不引入打转检测）；闸门后执行；硬超时 800ms；失败分类四态；超时后必 `rollback()` | AsyncSession 非并发安全 + 连接池基线 + 事务 abort 连锁（三条硬约束，见 §2.1） | 默认假设（推翻团队「并行」判断） |

## 17. 生产级必答项

| # | 必答项 | 结论 |
|---|---|---|
| 1 | **执行环境**：工具在哪跑、凭证是否进执行环境 | 抽取在 **worker 容器**、召回在 **api 容器**、图存储在 **PostgreSQL**。凭证（`LLM_API_KEY`）**必须**进 worker 执行环境（抽取要调 LLM），但只经环境变量注入、不进日志（`self_check` 已校验 caption 快照不含密钥明文）。**必须一并修复**：`docker-compose.prod.yml` 的 worker 段当前缺 `LLM_BASE_URL` / `LLM_API_KEY` / `LLM_MODEL`（只有 api 段有），不补则 prod 抽取必然失败；由启动自检 C2 兜底（缺凭据 → 拒绝启动，而非跑起来后静默失败）。写操作影响半径限定在 5 处派生数据表/列，不触碰 `chunks`/`documents` 业务字段、S3、审计、配额 |
| 2 | **错误回喂**：失败如何作为观察回到上下文、如何分类恢复 | 本系统无自主循环、无「把错误回喂模型重试」的语义 → 在线侧**不回喂**，直接降级并打点。分类四态见 §4.1：超时（放弃 + rollback）/ 永久（记录 + 0 路）/ 瞬时（不重试，宁快勿等）/ 空结果（正常态）。**离线抽取**有回喂：JSON 非法 → 带纠正提示重 prompt 一次（仅一次），仍失败 → `graph_status='failed'` + 指标，**不静默跳过**（静默跳过 = 让「图对这个文档不生效」这个事实消失） |
| 3 | **打转检测与熔断** | **不适用**（无 agent 循环，不存在原地打转）。替代物：① 抽取按 `GRAPH_EXTRACT_MAX_CHUNKS_PER_DOC` 截断 + arq 重试上限 3 + 单次调用超时 120s（单文档最坏 15 × 120s 仍在 `parse_job_timeout=1800s` 内的独立任务里，且不占解析主任务）；② 在线侧 800ms 硬超时即熔断；③ 全局熔断不做（图召回失败只影响自己那一路，不影响问答） |
| 4 | **记忆治理**：可信度、归属、失效条件 | 图与 wiki **不是记忆**（不跨会话代表用户、不参与权限判定）→ `MEMORY_LONG_TERM_KINDS` 那套白名单**不适用**。但继承一条原则：**LLM 产出的东西不因"被写进库"而升级为事实** —— 图只作召回线索、wiki 只作导航，永不作为证据（红线 A 的结构性保证）。归属：图/ wiki 都属于 kb（`kb_id` 外键），随 kb 删除级联。失效：口径章 + `documents.graph_status` + `wiki_pages.content_hash` 三重判定，见 §7.3 |
| 5 | **外部副作用幂等**：幂等键 / 状态查询 / 恢复策略 | 幂等键 `(document_id, extractor_model, prompt_version)`（抽取）与 `(document_id, generator_model, prompt_version, content_hash)`（wiki）。恢复策略 = **先删后写**（`delete_by_document` + `upsert_subgraph`），不依赖「上次跑到哪」；状态查询 `documents.graph_status` + `wiki_pages.status`。arq 重试只重试抽取本身（不重解析文档）。无外部系统副作用（不写 S3、不发消息、不调第三方） |
| 6 | **证据版本绑定**：验证结论如何绑定版本、版本变更后如何失效 | 图行的每一行都带 `extractor_model` + `prompt_version`；检索按当前口径过滤（fail-closed），旧口径**排除**而非混算。`documents.graph_status='done'` 只对「当次口径 + 当次 chunk 行」有效：chunk 行被 `DELETE+INSERT` 后，`purge_derived()` 把状态打回 `pending`（证据版本绑定）。wiki 用 `content_hash` + `source_chunk_ids` 双向留痕，chunk 换 id 即失效（`purge_derived()` 删页） |
| 7 | **生成者与评估者分离**：独立上下文、不看推理、显式评分标准、迭代预算 | 本方案的「生成者」= 离线抽取/摘要 prompt；「评估者」= 217 条评测集的确定性门禁（拒答与否 + 期望文档命中 + `graph_unique` 计数）。评估者**不看**抽取的推理，只看产物与执行记录（哪些 chunk 进了上下文）。**无模型自评**、无迭代预算问题（门禁是单趟批处理）。评测走独立读路径（`run_eval.py` 进程内直调，不经 HTTP 生成链路） |
| 8 | **前缀稳定与缓存命中**：稳定区/可变区划分、序列化确定性、重写触发点、命中率观测 | **本方案对前缀缓存的破坏 = 0**：system prompt 字节不变；wiki 与图数据都不进 prompt；能力配置只在 `caliber` 落库、不进 prompt 文本。图召回片只改尾部（chunk 段），且排序键是全序 `(hop, weight, chunk_id)`（无时间戳、无随机量）。**重写触发点**：`purge_derived()`（重索引）与口径变更 —— 两者都会让图/ wiki 一次性失效，代价已在 §7.3 矩阵里逐行说明。命中率观测：本方案不新增观测（缓存收益在推理侧，不由本能力影响） |
| 9 | **模型组合**（跨层必答） | 见 §5：形态 A（单智能体 + 单模型），在线 0 LLM、离线全用快速低价档，强力档可选不默认。级联升级只在离线（且明确「升级不能修 JSON 非法」） |
| 10 | **成本核算** | 离线一次性成本 = `文档数 × (chunk 数/4) × 单次 token`（抽取）+ `文档数 × 1 × 4K`（wiki）。在线增量 token = 0~1200/次（仅图召回命中时）。**按档位分配**：在线 100% 确定性代码、离线 100% 快速档。单位任务成本核算进验收单（§14.6 判定四问第 4 条） |
| 11 | **可观测性** | 11 个新指标（§14.2）+ `path_stats` 扩展（自动进审计与日志）+ 启动横幅 + 管理端能力页。无新日志格式、无新追踪层 |
| 12 | **数据治理与合规** | 图/ wiki 是派生数据，不进备份；硬删文档/schema 级联清除。**注意**：wiki 摘要是 LLM 对原文的重述，可能引入原文没有的措辞 → 页面上必须带 `disclaimer`（§9.6），且**永不作为引用**。审计留痕：`graph_status` / `generated_at` / 口径章 |

## 19. 魔鬼代言人（反例 ≥3，逐条给缓解）

### 反例 1：「图召回片绕过了阈值闸门，等于给不可答问题开了后门」

**攻击**：闸门只判三路 top1。假设用户问一个知识库里毫无依据的问题，三路恰好捞到一条 0.52 的弱相关片（过闸门），而图路因为实体名撞词捞到 3 条话题相邻但完全不相关的片 → 上下文里混进噪声，模型可能照噪声作答。

**承认成立的部分**：这是真的，且与「表格回捞 / 章节补全」共享同一个已存在的风险面 —— 那两条路径同样绕过阈值。

**缓解（三层）**：
1. **量级受控**：≤3 片 / ≤1200 token，且优先选 `hop=1`（直接共现实体）而不是 `hop=2`；
2. **可观测**：`graph_unique` 高但 `hit_rate` 不涨 = 噪声 → §14.6 第 2 问直接判回滚；
3. **可关闭**：`GRAPH_ENABLED=false` 即完全消除该风险面，且不影响既有三路。

**残余风险（诚实）**：无法用确定性规则区分「有意义的补充」与「话题相邻的噪声」—— 这需要语义判定，属于未知区（§20-U3）。

### 反例 2：「fail-closed 会让一次配置错误变成一次服务不可用」

**攻击**：运维把 `GRAPH_STORE_BACKEND` 拼错（`postgress`），或者迁移忘了跑 → 服务直接起不来，而图召回本来只是个增强项。**为了让一个可选能力可用性达标，牺牲了核心问答的可用性。**

**承认成立的部分**：这是 fail-closed 的真实代价，且比"静默降级"更容易被投诉（起不来立刻会被发现，静默降级可能几周没人发现 —— 但那正是问题）。

**缓解**：
1. **判别标准已写死**（§2 失败语义）：只有「依赖缺失」才拒启，「数据未就绪」只告警。所以「忘了补建抽取」不会拒启，只有「表不存在 / 没密钥 / 后端未实现」会；
2. **文案必须给出可执行的修复命令**（§12.4 每条都带命令与路径）；
3. **默认关闭**：绝大多数部署不会触碰这些开关，风险面只为"主动开启"的部署存在；
4. **`.env.example` 与 compose 默认值一致**，避免"抄了个错的默认值"这类事故。

**残余风险**：无法消除「运维改配置时打错字」的概率，只能保证「打错字后 10 秒内被发现，而不是 3 周后」。

### 反例 3：「串行图召回会拖慢首字节，而 TTFT 已经 91% 耗在串行 LLM 调用上」

**攻击**：本设计的图召回是**串行**追加在闸门之后 → 直接进 TTFT。虽然只有 ~80ms，但用户感知的是绝对时间；而且它在闸门后，意味着**每次成功回答都要付**这笔钱（约一半请求）。

**承认成立的部分**：串行确实把这 80ms 全额加在关键路径上。

**缓解**：
1. **量级可接受**：80ms 相对 `llm_first_token_timeout_seconds=15`、实测改写 5.4~9.5s 的上游，占比 < 1%；
2. **有硬上限**：800ms 兜底，最坏情况可控（不会出现"图召回挂着不返回"）；
3. **零成本拒答路径**：闸门之后 → 106/217 不可答用例完全不付这笔钱；
4. **可优化但需证据**：真正能藏掉这 80ms 的方案是「与 embedding 调用并发、用独立连接」。本文不采用，理由是它要多占一条连接（容量 40/3 ≈ 13 并发 < 基线 20）—— **若后续压测证明 13 并发够用，这是优选方案**，已登记为未知区 U1，不作默认。

### 反例 4：「`purge_derived()` 放错位置会让图数据静默消失」

**攻击**：如果 `purge_derived()` 放在 commit 之后（而不是同一事务内），或放在 DELETE chunks 之后，那么「清派生数据」与「写新 chunks」之间会出现中间态；如果这中间进程被杀，会留下「chunk 已换新、图数据指向旧 chunk（已被级联删除）、`graph_status` 仍是 `done`」的状态 —— 检索时图路永远为空，但状态说"已完成"，无人去补建。

**承认成立的部分**：这是本设计里**最脆弱的实现细节**，一个位置错误就产生静默空图。

**缓解**：
1. 契约写死：`purge_derived()` MUST 在「删除旧 chunks / 写入新 chunks」的**同一事务内**，且**先于** chunk 写入执行；`graph_status` 在同一事务里置 `pending`（与 chunk 写入原子）；
2. `tests/graph/test_purge_derived.py` 钉住：模拟重索引 → 断言 `graph_status='pending'` 且旧 mention 为 0；
3. 启动自检 C7 的告警会暴露「`graph_status='done'` 但 mention 为 0」的文档（新增一条一致性检查 SQL，见 §20-U4 待定）；
4. 补建脚本的默认模式是「按 `graph_status != 'done'` 补」，`--force` 才重抽已 done 的 → 误判可修。

### 反例 5：「wiki 摘要是 LLM 产物，被人类当文档读，等于把幻觉洗成知识」

**攻击**：wiki 页在 UI 上展示 200~400 字摘要。管理员/用户会当真读。摘要是 LLM 重述，可能把两句话的前提合并、把"应当"写成"必须"。**虽然没进 prompt，但人脑就是 prompt。**

**承认成立的部分**：这是本方案里唯一一处"LLM 产物面向人展示"的地方，风险真实。

**缓解**：
1. 页面上必须带 `disclaimer`（§9.6 的文案：明确写"LLM 产物、不构成引用依据"）；
2. 每个 `sections[].chunk_ids` 提供到原文的回跳 → 人可一键核对；
3. 摘要 prompt 明确约束「只做索引式陈述，不得引入原文没有的判断词」；
4. 摘要不参与任何检索打分 → 即便错，也只影响"人点进去看什么"，不影响"系统答什么"。

**残余风险**：无法自动验证摘要的事实正确性（客观部分可抽查，主观判断不行）→ 标注为未知区（§20-U5）。

## 20. 遗留问题与未知区（诚实标注）

### U1 · 图召回能否与 embedding 调用并发（连接池容量待压测）

**未知**：若把图召回放在**独立 session** 上与 `embed_query()` 并发，可把这 ~80ms 完全藏进 embedding 往返（embedding 走本机 `bge-m3`，量级估算 50~200ms，**须实测**），TTFT 增量趋近 0。代价是在途请求峰值连接数从 2 变 3，容量从 20 并发降到约 13。
**需要什么才能决**：用 `scripts/loadtest_chat.py` + `stub_llm.py` 在 c=10/13/16/20 下测「检索 P95 / 失败率 / QueuePool 拒绝数」，确认 13 并发是否覆盖实际峰值。
**若不能决**：保持串行（本文默认），80ms 计入 TTFT。
**占位方案**：`recall_by_graph` 已按「可独立 session」设计（不依赖外部传入 session 之外的任何状态），改并发只需换一个 session 来源。

### U2 · 实体链接的召回率（词元级是否够用）

**未知**：词元级链接（`build_fts_query` + `name_vec`）依赖实体名的字面匹配。若用户问「那台设备怎么重置」而实体名是「XYZ-1000 控制器」，链接会失败（除非问题里出现实体名或别名）。
**影响**：`rag_graph_empty{stage=link}` 会偏高，`graph_unique` 偏低 → 按 §14.6 判据会判「图路没用」并砍掉 —— 但**真实原因可能是链接不准，而不是图没用**。这是一个会导致错误决策的判据漏洞。
**需要什么才能决**：构造「实体未在问题中出现」的用例集，测链接命中率；若 < 60%，考虑把 `graph_entities.aliases` 也进 `name_fts`（低成本改进）。
**占位方案**：本版**先把 aliases 一起写进 `name_fts`**（抽取产出 aliases 时），成本为零。

### U3 · 「有意义的图邻居」与「话题相邻的噪声」无法用确定性规则区分

**未知**：反例 1 的残余风险。图扩展能保证「实体真的共现」，不能保证「这段内容对这个问题有用」。
**本版处置**：靠 `max_hops=2` + `hop` 优先 + 3 片上限压住量，靠 `graph_unique`/`hit_rate` 做上线判定。
**若未来要解**：需要一次「邻居相关性判定」，那是模型裁判（且必须独立于生成者）—— 会引入新的一次 LLM 调用，与「在线 0 LLM」的设计冲突，须重新评估。

### U4 · 「`graph_status='done'` 但图实际为空」的一致性巡检

**未知**：反例 4 的兜底还没做机器化巡检。设想一条启动/定时检查：统计 `graph_status='done'` 且该文档 mention 数为 0 的文档，>0 则告警。
**为什么本版不做**：这是一个全库聚合查询（`GROUP BY document_id`），放在启动期会拖慢启动（大库上秒级）；放在 cron 又要新增调度。
**占位方案**：写进 `scripts/backfill_graph.py --check`（手动/验收时跑），不挂启动与 cron。

### U5 · wiki 摘要的事实正确性无法自动验证

**未知**：摘要是否引入了原文没有的判断（"应当" vs "可以"）、是否把两段话的因果关系接错。
**本版处置**：`disclaimer` + `chunk_ids` 回跳 + prompt 约束 + 人工抽查。
**诚实结论**：主观正确性没有 ground truth，评估只能覆盖客观部分（是否覆盖了该文档的主要小节 / 术语是否来自原文）。**不假装能自动评分**。

### U6 · 生产 compose worker 段缺 `LLM_*` 的影响面未完全核实

**未知**：已确认 `docker-compose.prod.yml` 的 worker 段缺 `LLM_BASE_URL`/`LLM_API_KEY`/`LLM_MODEL`（dev 段有）。但这意味着**现有的内嵌图视觉转录（`vision_extract`）与知识治理审查（`governance_review`）在 prod 下可能已经在失败** —— 它们是既有功能，不在本方案范围内，但同一根因。
**本方案处置**：把「prod worker 段补 `LLM_*`」写进第 1 步必做项；不擅自修改既有功能的判定逻辑。
**建议**：主理人考虑单开一个「prod worker LLM 凭据缺失」的排查项 —— 它可能已经在影响治理状态与内嵌图转录的成功率。

### U7 · 图规模上限未做容量标定

**未知**：本文用「1000 篇文档 → 5~10 万边」做量级论证，但没有实测。若客户语料是 5 万篇，边数到百万级，2 跳自连接的 p95 可能超过 80ms 门禁。
**需要什么才能决**：造 10 万 / 50 万 / 100 万边的合成数据，测 `neighbors()` 的 p95。
**占位方案**：`GRAPH_MAX_HOPS` 已是 Final 常量（调它走代码评审）；大规模的兜底是「按 kb 开图」（只给核心库开），无需改代码。

### U8 · 评测口径与生产口径的断层（第 2 步审核新增，**需管家节点裁决**）

**事实**：`eval_service` 只把 `result.chunks` 送进生成；`table_recall_chunks` / `section_recall_chunks` / `graph_recall_chunks` 都不拼。且它调 `retrieve()` 而非 `retrieve_chain()`。→ 评测测的是「纯三路单趟」，生产跑的是「四类拼装 + 可能的链式多轮」。
**影响**：现有 217 条基线是在**比生产更少上下文**的口径下得出的；「开图 vs 关图」两轮评测生成输入完全相同 → §14.6 第 2 问不可测。
**本步处置**：按 §9.7 裁决 B 的 ②（只聚合计数指标 + 报告免责标注）。
**待裁决**：① 评测对齐 chat（一次性重标基线）vs ①-b 双口径并存（`--with-recall-chunks` 开关，两套基线），**二选一需管家节点拍板**；`retrieve_chain` 的缺失同批处理。
**为什么不在本步自行决定**：它会改变「什么算合格」本身，属于改判据。

### U9 · 第三层子串兜底的索引（规模护栏之外的可选解）

**未知**：`name_key ~* pattern` 无索引，成本 O(该 KB 实体数)（§9.7 偏离 3）。已加 `GRAPH_LINK_SUBSTR_MAX_ENTITIES=20_000` 护栏（超阈值跳过第三层），但护栏是「放弃兜底」而不是「让兜底变快」。
**可选解**：`pg_trgm` 的 `gin_trgm_ops` 索引可让 `~*` 走索引（trigram）；代价是 `CREATE EXTENSION pg_trgm`（部署变更，部分托管 PG 需超级用户），与「私有化交付少一份排障面」的取向冲突。
**需要什么才能决**：是否有客户库的实体数会稳定超过 2 万 → 若有，先量 SQL 实测 p95，再决定「加扩展」还是「按 kb 分批开图」。

### U10 · 判据 1 的阈值（`graph_unique_total ≥ 11`）缺乏历史分布支撑

**未知**：11 = 可答类 111 条的 10% 是**先验判断**，不是标定值。当前项目没有任何一轮评测留下「图给上下文补了几片」的分布 —— 217 条基线是在没有图的情况下建立的。所以这个阈值回答不了「11 是偏松还是偏紧」。
**影响**：偏松 → 图几乎没用也能过判据（浪费后续维护成本）；偏紧 → 有用但被判无用（砍掉第 2 步）。两种错误都不是零成本。
**需要什么才能决**：`with_recall_chunks=true` 跑一轮开图评测（判据 1 只看计数，不需要质量门禁通过），拿到 `graph_unique` 在 111 条可答类上的**实际分布**（多少条为 0 / 1 / 2 / 3），再回来重设阈值。在此之前，11 是**待标定值**，验收单上必须标注「本阈值为先验值，首轮实测后重设」。**MUST NOT** 因为实测不达标就临时下调阈值 —— 那是把判据改成「只要不是 0 就算过」。
**占位方案**：首轮按 11 判；若实测 ≥ 11 则不必调（结论不受影响），若 < 11 则先看五态归因表，再谈阈值是否该改。

### U11 · 种子层加 ACL 的成本，以及 `graph_seed_count` 侧信道的可探测性

**未知**：§10.1-R1 接受「种子层不做 ACL」，依据之一是「加 `EXISTS` 可见提及会让每次检索多一次带权限判定的 JOIN，成本不成比例」—— 但**这个成本没有实测**（当前 `seeds=7 → neighbors=0 → chunks=0`，全流程 3~10ms，加 JOIN 后是多少不知道）。同时「`graph_seed_count` 是否可被批量探测」也只是推理（需要按常见词表扫一遍看计数的稳定性），没有攻击实验。
**影响**：这一条是 R1 的**唯一量化支柱**。若加 JOIN 的实际成本只有 0.5ms，那「不成比例」这个理由就不成立，应当是「直接加上更好」；若侧信道可探测，则 R1 的失效条件 ② 立即触发。
**需要什么才能决**：① 在 432 实体 / 10 万实体的合成数据上分别量「种子层带 `EXISTS` + `_WHERE_BASE`」相对当前版本的 p95 增量；② 写一个探测脚本：以 200 个常见中文词为探针，看 `graph_seed_count` 与拒答率的组合能否稳定区分「库内有该实体」—— 若能，R1 必须改。
**占位方案**：R1 维持「接受」，但把这两项测出来作为 R1 转正的准入条件，不要等客户提合规要求才动。

## 22. 给主理人的一句话结论

**这个方案能上线，但它的价值(命中率/漏答率)只可能体现在"补上下文"，不可能体现在"救回原本会被拒答的问题"(A9) —— 如果团队要的是后者，需要重开一次阈值口径设计，不是在本方案上修。**
