## 0. 一句话结论

图召回作为第 4 个上下文来源，**确实没有污染排序 / 阈值 / 拒答判定**——开图与关图时
`chunks` 的 8 条逐字段完全相同（含 `final_score`、`score_source`、`path_stats` 去 graph_* 后逐键相同），
连拒答判定在「图能补 3 片、但三路相关性低」的对抗用例上也**没有被图救回来**。
四闸门在**取片 SQL** 上逐条生效（23 组破坏实验），口径在**种子层 SQL 侧**用 EXISTS 过滤
（有「先取后过滤必然 0 结果」的区分实验），预算裁剪按「先条数、后 token、不跳片」精确执行。

唯一实质缺陷是 `statement_timeout` 的**事务级溢出**：`set_config(..., is_local=true)` 的作用域是
整个事务，图召回成功后不还原，同一事务里后续的表格回捞 / 章节补全全部继承图召回预算。
默认 800ms 基本无害，但**把 `GRAPH_RETRIEVE_TIMEOUT_MS` 调小就变成「图路把本来会成功的请求弄失败」**：
50ms 配置下，图召回之后一条 200ms 的 SQL 被 DB 侧打断。`e6b6a94` 已修（还原成调用前的值）并复核通过。

## 6. 附加 9：三处「实现偏离」实证

### 9a `set_config('statement_timeout', ms, true)` 是否真的生效 —— **生效；但 02efb8d 上会溢出**

```
  set_config 前='0' → 后='150ms'
  ✔ pg_sleep(0.6) 被 DB 侧打断: DBAPIError: canceling statement due to statement timeout
  rollback 后='0'（is_local=true 在事务结束时复原）
```

`is_local=true` 的作用域是**整个事务**，不是函数体。图召回成功后不还原 → 同一事务里
后续 SQL 全部继承图召回预算。同一探针、两个版本对照：

| 版本 | `recall_by_graph(50ms)` 之后 | 之后一条 200ms 查询 | 完整 `retrieve()` 之后 |
|---|---|---|---|
| `02efb8d` | `'50ms'`（800ms 配置下为 `'800ms'`） | **被掐断** `DBAPIError: canceling statement` | `'800ms'` |
| `e6b6a94` | `'0'` | 未被打断 | `'0'` |

`e6b6a94` 的还原是**三条成功路径统一一处**（`_steps()` 之后），逐条 SQL 验证：

```
  有片（Next.js）        set_config 位置=[1, 8]（倒数第 2 条是还原；最后一条是我自己的查询）→ '0'
  空种子（问句无库内实体）  set_config 位置=[1, 6] → '0'
  空邻居（clearance=0，seeds=1 neighbors=0） set_config 位置=[1, 7] → '0'
```

并且还原成「调用前的值」而不是硬编码 0：

```
  B. 还原成「调用前的值」而不是硬编码 0
    调用前='200ms' → 调用后='200ms'
    100ms 查询（<200ms）: 通过 ✔
    400ms 查询（>200ms）: 被掐断 ✔ ← 外层的 200ms 仍然生效（说明没被悄悄放宽）
```

再把 `GRAPH_RETRIEVE_TIMEOUT_MS` 调到 800/100/30/5 各跑 4 个真实问句：**16/16 全部正常**
（`chunks=8`，图召回自身 3–10ms），主链路不再受图预算影响。

### 9b `name_key ~* :pattern` 是否真的比 LIKE 安全 —— **是**（误匹配可量化）

```
  'getXretrieval' LIKE '%get_retrieval%' = True   ← LIKE 下 `_` 是单字符通配符
  'getXretrieval' ~* 'get_retrieval'     = False  ← POSIX 正则下 `_` 是普通字符
  'get_retrieval' ~* 'get_retrieval'     = True

  端到端：造实体 zzretr_alpha 与 zzretrXalpha
  link_entities('zzretr_alpha') → [('zzretr_alpha', 1.0)]   是否误召回 zzretrXalpha: False
  同条件 LIKE 计数=2 vs ~* 计数=1   ← 若改用 LIKE，会多召回 1 个假实体
```

### 9c 第三层 `~*` 兜底是否走全表扫 —— **是 seq scan，当前规模可接受**

```
    Limit  (cost=52.16..52.17 rows=5) (actual time=0.454..0.457 rows=4)
      ->  Hash Semi Join  (Hash Cond: e.id = m.entity_id)
            ->  Seq Scan on graph_entities e  (actual time=0.096..0.243 rows=5)
                  Filter: (kb_id = ANY(...)) AND (name_key ~* 'next') AND (tenant_id = ...)
                  Rows Removed by Filter: 427
            ->  Seq Scan on graph_entity_mentions m  (rows=466)  Filter: 口径两列
  graph_entities 行数 = 432；Execution Time: 0.526 ms
```

结论：`~*` 用不上 `name_key` 的 B-tree，确实全表扫；432 行 0.5ms，**当前规模无害**。
`e6b6a94` 新加的规模护栏把这条查询限制在「实体数 ≤ 20000」才发：

```
  默认阈值 20000: 4 个种子 ['Next.js','Next.js 13+','nextTick','前端性能优化终极手册…']
  阈值=1:        3 个种子（第三层被跳过）
    期间 SQL 3 条：exact / fts / count 护栏查询 —— 没有 LIKE 那条正则查询
    指标 rag_graph_link_substr_skipped_total{reason=too_many} = 1.0
```

### P1-1 `statement_timeout` 溢出到同一事务的回捞/补全 —— **在 `02efb8d` 上成立，`e6b6a94` 已修**

- 复现：`GRAPH_RETRIEVE_TIMEOUT_MS=50` → 跑一次 `retrieve()` → 同 session 执行 `SELECT pg_sleep(0.2)`
  → `DBAPIError: canceling statement due to statement timeout`。
- 状态：`e6b6a94` 已按要求修（还原成**调用前读到的值**，还原点唯一，三条成功路径都覆盖），
  我用同一探针复核通过（§6.9a）。**建议保留这条记录**：默认 800ms 下不暴露，
  是「dev 数据量小看不出来」的典型，未来别把 restore 挪进某个提前 return 分支。

### P2-1 还原 SQL 在 `asyncio.timeout` 窗口之外执行，没有墙钟上限

`recall.py` 中 `_restore_statement_timeout()` 在 `async with asyncio.timeout(...)` 之后调用。
若连接假死（网络分区但 socket 未断），这条 SQL 自身会等到 TCP 超时，而函数契约是「永不抛、
不拖慢主链路」。建议把还原也放进一层短超时（如 `asyncio.wait_for(..., 0.2)`）——
它的失败已被吞掉，包一层不会改变语义。

### P2-2 `_COUNT_SQL` 的注释说走 index-only scan，实测是 Seq Scan

`linking.py` 的 `_COUNT_SQL` 注释写「走 `idx_graph_entities_kb` 的 index-only scan，本身很便宜」，
实测计划是 `Seq Scan on graph_entities (rows=432, 0.123ms)`（planner 在小表上不选索引）。
当前无影响，但护栏的存在理由就是「实体数上量」；上量后这条 count 自己也会 O(n)。
建议注释按实测改写，或上量时改用 `pg_class.reltuples` 近似值。

### P2-3 种子层不做 ACL 过滤（无泄漏，但有侧信道 + 白付代价）

对 `public-only` 主体，`recall_by_graph` 仍返回 `seeds=7`（因为提及表没有 `acl_tags`，
种子层只按 tenant/kb/口径过滤），只是取片层被四闸门挡成 0 片。
无内容泄漏，但：① 种子数量/耗时与「库里有没有这个实体」相关，构成弱侧信道；
② 白跑一层链接与图扩展。若在意，可在种子层加「至少一条可见提及」的 EXISTS（成本是多一次 JOIN）。

### P2-4 拒答分支把 `graph_degraded_reason` 一起丢掉

`merge_rounds()` 的两处 `refused` 早返回（`merged` 为空 / 低于阈值）都不带
`graph_degraded_reason`、`table_recall_chunks`、`section_recall_chunks`、`graph_recall_chunks`。
实测：只有图召回片的单轮 → `refused=True, degraded=''`（原值 `'timeout'` 被丢）。
对「为什么这批请求一直 0 召回」的排障不利。建议拒答时仍带回 `graph_degraded_reason`。

### P2-5 `graph_unique` 以「三路候选集」为分母，实测恒 0，不能直接当存废判据

真实问句实测：

| 问句 | 交付片 | graph_chunks（进上下文） | graph_covered | graph_unique |
|---|---|---|---|---|
| AX3000/AX6000 价格 | 8 | 0 | 3 | 0 |
| Next.js App Router vs Pages | 8 | 2 | 2 | 0 |
| 差旅费报销凭证 | 8 | 0 | 0（no_entities） | 0 |

`Next.js` 那句图召回确实补了 2 片进上下文（三路 top-8 里没有它们），但 `graph_unique` 仍是 0
——因为分母是「三路**候选集**」而不是「交付集」。用 `graph_unique == 0` 判「图路没价值」会低估收益。
建议：把「交付层被图补上的片数」（`graph_chunks - graph_covered_in_delivered`）也打一个点。

### P2-6 预算裁剪在「取行之后」，10 片全文都取回再丢掉 7-8 片

`⑦` 用 `c.id = ANY(:chunk_ids)` 一次取回 ≤10 片**全文**（实测单片 404–783 tokens，合计约 6k tokens），
`⑧` 再按预算只留 2–3 片。可以先只取 `id/token_count` 预筛、再取需要的全文，省一次大传输。
属优化项（当前 graph 全流程 3–10ms，收益有限）。
