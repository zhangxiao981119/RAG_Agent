## 〇、检索范围与筛选决策（披露）

**本次聚焦**：「RAG 的可配置项如何分层 + 场景差异用什么机制表达 + 多租户隔离怎么取舍 + 过度配置化的反面教训」。
**未展开**：Agentic 六层（执行循环/工具注册/上下文管理/状态存储/生命周期钩子/评估接口）的学术前沿——本次是企业工程决策支撑，不是论文综述，故不按六层模板铺开。

**入选标准**：能直接支撑「分层 / 抽象机制 / 隔离 / 约束」四类决策之一，且有一手文档可溯源。
**淘汰**：无一手出处的中文二次转载、只讲"我这样做了"无机制的方案帖、只做 Demo 的框架介绍。检索到的微信公众号实战文仅作背景参考（第 5 节未引用为证据）。

**一个必须先说的发现**：本项目 `code/apps/api/app/config/` 下**已经存在**与本议题高度同构的设计——
`index_profile.py` 已有「embedding_model + embedding_dim + embedding_text_version」三要素 sha1 指纹并用于检索期过滤（注释原文："fail-closed：宁可查不到，不可查错"）；
`config_profile.py` 已有跨角色一致字段白名单 + 脱敏快照 + 指纹；
`decisions.py` 已把契约级常量冻结在代码里并带 `CONTRACT_VERSION`。
也就是说：**本次研究的主要价值不是"从零设计"，而是"用业界一手文档验证这套口径对不对、缺口在哪、哪一层还缺"。** 下文凡与本项目已有设计对得上的地方，都会明确标注「已验证」或「与业界口径偏离」。

## 一、一句话结论

**成立，但前提是把"可配置"限定在「向量空间之外」的一切。**

业界所有能查到的成熟系统，都把配置切成「声明式、可版本化、可分场景覆写」的部分，**同时**把少数几个决定"向量是否同构"的维度锁在代码或部署级——RAGFlow 用兼容性探针 + 失败回滚、Azure AI Search 用"vectorizer 必须指向建索引时同一个 embedding 模型"、Dify 用"高质量索引不可回退到经济索引"、Haystack 用反序列化白名单直接把不可信配置挡在加载前。**统一平台 + 场景化配置的正确形态是：平台提供一套「带指纹的场景配置行 + 一条固定的执行管线」，而不是「让场景自由拼装 pipeline」。** 一旦允许场景各自编排执行链，就退化成 Sculley 等人在 NeurIPS 2015 命名的 pipeline jungle，且无法回归测试。

## 二、配置分层表（可直接映射到 Pydantic Settings / DB 表）

### 2.1 分层总表

| 层 | 放什么 | 谁改 | 变更影响面 | 是否允许运行时改 |
|---|---|---|---|---|
| **L0 契约级**（代码常量） | 向量空间四要素里的语义部分、拒答/守门类不可关开关、RRF_K、阈值语义、提示词模板版本 | 只有发版（PR + review） | 全平台所有场景、所有租户；改一次等于换一代数据 | **禁止**。改了必须 bump `CONTRACT_VERSION` 并触发重算评估 |
| **L1 平台级**（部署 env / Pydantic Settings） | embedding 模型 + 维度 + 端点、LLM 端点与输出上限、rerank 端点与超时、上传白名单、审计保留期、限流与预算上限、pgvector 表名/索引名 | 运维 / SRE | 全平台；两侧角色必须一致，不一致即"数据不可解释" | **禁止热改**。改需重启 + 跑启动自检 + 打指纹横幅 |
| **L2 场景级**（DB 行，一场景一行） | 分块目标/上限/重叠、父子块策略、召回 top_k、是否开 rerank 及权重、相似度阈值、是否开混合检索/关键词扩展、是否开 graph/wiki 及其超时、场景默认模型（可选） | 产品/算法（后台表单，不是改文件） | 该场景的**新入库数据 + 后续请求**；不影响其它场景 | **允许**，但必须走「草稿→校验→发布版本」三步，且**不回溯**已有 chunk |
| **L3 租户级**（DB 行，一租户一行） | 场景启用清单、租户配额（日/月 token）、限流阈值、可见性策略、数据保留期、**引用哪一套场景配置的版本号** | 运营 / 租户管理员（受平台封顶约束） | 该租户全部请求 | **允许**，但只能**收紧**不能**放宽**（见 2.3 收敛原则） |
| **L4 请求级**（API 参数 / query param） | top_k（平台上限内）、相似度阈值（只在场景允许区间内微调）、是否流式、过滤器（文档集/时间/标签）、`debug` 开关 | 调用方（前端/集成方） | 单次调用 | **允许**，但必须**结构性受限于**上层：越界值不是"取默认"，而是**拒绝（fail-closed）** |

### 2.2 字段级建议（映射到本项目）

**L0 → 继续留在 `app/config/decisions.py`（现状正确，已验证）**

| 字段 | 判据 |
|---|---|
| `GROUNDING_CHECK_ENABLED` / `INJECTION_GUARD_ENABLED` / `MEMORY_SOURCE_TRACE_REQUIRED` | 这是"质量守门开关"。一旦做成场景可配，就等于把"允许静默劣化"写进配置项。业界同类：Azure 的 `dimensions` 不可改、Haystack 的危险 builtin 即使在白名单内也被 block——**安全相关默认值不可被配置绕过**（OWASP "secure-by-default / fail-safe"）。 |
| `RRF_K`、`RELEVANCE_THRESHOLD_*` 的**语义** | 阈值**数值**可以下沉到 L2，但"阈值是过滤还是加权""低于阈值是拒答还是低置信作答"这种**语义**必须留在 L0。否则场景 A 改成加权、场景 B 保持过滤，同一份评估集无法比较。 |
| `EMBEDDING_TEXT_VERSION` | 现状注释已写明"必须人工 bump"，正确。补充一条业界佐证：Elasticsearch 明确"除受支持的 mapping 参数外，**不能改已有字段的 mapping 或字段类型**，要改只能新建索引 + reindex"——即**派生数据的"生成公式"一旦作为不可变契约，就只能靠换索引代次迁移，不能原地改**。 |

**L1 → `app/config/settings.py`（现状基本正确，一处建议调整）**

| 字段 | 现状 | 建议 |
|---|---|---|
| `embedding_model` / `embedding_dim` / `embedding_base_url` | 在 Settings，且已进 `CROSS_ROLE_FIELDS` 白名单 | **保持**。这三者与 `embedding_text_version` 共同构成向量空间身份，**不可下沉到 L2/L3**。理由见第 4 节第 1 条。 |
| `llm_model` / `llm_base_url` / `llm_max_output_tokens` | 在 Settings，已进白名单 | **保持 L1，但建议把"场景默认模型"做成 L2 的 nullable 覆写**——Dify 的做法正是这一层：workspace 级设 `Embedding Model / Rerank Model / System Reasoning Model` 作为全空间默认，应用/节点不指定时回退到 workspace 默认（`docs.dify.ai/zh/use-dify/workspace/model-providers`）。即 **"平台默认 + 场景可空覆写 + 空则回退"**，而不是"每场景必填"。 |
| `rerank_*` / `graph_*_timeout` / `wiki_nav_timeout_ms` 等**单角色字段** | 明确排除在指纹白名单外 | **正确且业界少见，是本项目的一个亮点**。注释里记录的"假警比不做检查更糟"完全对得上工程共识（第 6 节第 5 条）。 |
| `multi_tenant: bool` + `tenant_code: str` | 全局单值 | **建议演进为 L1 开能力、L3 存租户行**。当前形态只能表达"单租户/多租户"，表达不了"多租户 + 每租户不同的配额与场景启用清单"。`default_tenant_daily_token_limit` 同理：现在是**全局默认值**，一旦有租户要单独谈额度，就只能加 env——这正是配置爆炸的起点。 |

**L2 → 新建 `scenario_profile` 表（本项目当前缺口）**

建议字段（每行 = 一个场景的一个已发布版本，`is_active` 唯一）：

```
id, scenario_key, version(int), status(draft|published|archived),
chunk_target_tokens, chunk_max_tokens, chunk_overlap_tokens,
chunk_strategy(enum: token|title|parent_child|qa),
retrieval_mode(enum: vector|fulltext|hybrid),
recall_top_k, rerank_top_k, rerank_enabled,
relevance_threshold_vector, relevance_threshold_rerank,
keyword_expansion_enabled, fts_max_terms,
graph_enabled, wiki_enabled,
*_model_override (nullable 三类),
index_fingerprint(text),       -- 冻结这一版依赖的向量空间身份
config_fingerprint(text),      -- 冻结这一版解析后的全部有效值
published_at, published_by,
checksum(text)                 -- 草稿写入时的乐观并发校验位
```

关键设计约束（每条都有出处，见第 6 节）：
- `version` 单调递增 + `published` 后不可改，只能发新版本（RAGFlow 的 `Save draft → Publish → 创建版本`，且**数据集保留它当时选的那个版本**，不会因为管线发新版就自动跟）。
- `checksum` 用于**导入/保存时的乐观并发**：Dify 的做法是"先读取草稿哈希值，再带上它导入；带了哈希后若期间有人改了草稿，导入被拒绝，不会覆盖对方改动"。
- `index_fingerprint` 必填：这一版场景配置**只能**用在匹配该指纹的数据上，不匹配就拒绝启动该场景的检索（fail-closed），而不是"警告后继续"。

**L3 → 新建 `tenant_setting` 表**

```
tenant_id, scenario_key, enabled(bool),
scenario_version_id(FK → scenario_profile.id),  -- 钉版本，不自动跟新版
daily_token_limit, monthly_token_limit,
rate_limit_rpm, visibility_policy(jsonb), retention_days,
allow_request_override(jsonb)                    -- 允许租户在请求级覆写哪些字段
```

**L4 → 请求参数，用 Pydantic 模型显式声明 + 区间校验**

- 可覆写集合由 `L3.allow_request_override` 决定，不在集合内的字段**收到即 400，不是静默忽略**。静默忽略是最坏的一种：调用方以为生效了。
- 区间上限由 L2 给出，越过上限按上限**截断要记 warning 并落 audit**（或直接拒绝，二者择一，不可两种混用）。

### 2.3 收敛原则（L3 / L4 只能收紧，不能放宽）

WeKnora 的实践值得抄（注：腾讯开源项目，此处作为**设计思路**参考，非证据）：其组织内"有效权限 = min(共享权限, 我的组织角色)"——共享只会让权限收敛，不会突破角色天花板。
映射到配置上：**租户级只能在平台/场景允许的范围内收紧**（比如场景允许 top_k ∈ [3,20]，租户可以设成 10，不能设成 50；场景允许开 rerank，租户可以关，不能开一个场景本来没开的能力）。
这条不是业界文档原文，是基于第 5 节"配置优先级/覆写隐藏"教训的推论，属**待核线索（设计建议，非事实）**。

## 三、抽象机制对照表

| 机制 | 代表系统 | 表达能力 | 学习成本 | 失败模式 |
|---|---|---|---|---|
| **声明式配置（YAML / DB 行）** | Dify DSL（`app.yaml` / `.ifpkg`）、Azure AI Search index JSON、Vespa `services.xml` + `query-profiles/*.xml` | **中**。只能表达"参数集合定值"，表达不了"步骤顺序"和"分支"。Vespa 的 query profile 就是"命名的一组默认查询参数"（mobile profile = 更少 hits + 更短超时），并可用 `maxHits` **强设一个调用方无法超过的上限**——这正是 L4 收敛的官方范式 | **低**。产品经理能读能改 | ① 引用断裂：Dify 导出**不含**关联知识库，跨 workspace 导入后"每个知识检索节点都会丢失关联的知识库"；Azure/Vespa 同类问题是要手工对齐索引名。② 无类型字符串：`"false"` 被当 true、ms 与 s 混用。③ 版本兼容：Dify 导入时校验 DSL 版本，低于当前平台只给 warning |
| **Pipeline / DAG 编排** | RAGFlow Ingestion Pipeline（Begin→Parser→Chunker→[Transformer]→[Compiler]→Indexer）、Dify Workflow/Chatflow、Haystack `Pipeline`（components + connections） | **高**。能表达顺序、分支、循环（Haystack 支持 branching/looping） | **高**。RAGFlow 明确规定"一个画布只能一个 Chunker、Parser/Transformer/Compiler/Indexer 各限一个实例"——约束本身就是学习成本的一部分 | ① **pipeline jungle**：每个场景自己画一条，半年后没人能说清两条链的差异（Sculley 2015 原词）。② 无法横向比较：评估集跑不出可比数字，因为链路不同。③ 校验负担外移给用户：RAGFlow 的 `Checklist` 就是补这个洞。④ 版本漂移：发新版后旧数据集仍跑旧版，"现有 chunk 不会自动重新生成" |
| **可插拔接口（面向对象抽象）** | LlamaIndex `Settings`（全局默认）+ `transformations=[...]`（per-index 覆写）、`IngestionPipeline(transformations=[...], vector_store=..., docstore=..., cache=...)`、`NodeParser` 家族（Sentence / SentenceWindow / Semantic / Markdown / Hierarchical / Code） | **最高**。新增一种切法 = 新增一个类，不动框架 | **最高**。需要写 Python、理解 `Node`/`Document` 关系链、`excluded_embed_metadata_keys` 这类细节 | ① 抽象泄漏：能力只存在于代码里，产品改不了 → 需求排队到研发。② 每加一个场景就多一个 `if scenario == "hr": parser = ...` → 回到 glue code。③ 缓存/去重口径分散：LlamaIndex 按"节点+转换"对做缓存，一旦场景自己换了转换器，缓存命中率骤降且难以解释 |
| **Profile 组合（声明式 + 插件注册表的折中）** | Azure AI Search 的 `vectorSearchProfile`（vectorizer + algorithm + compression 三者命名组合，每个 vector 字段只能用一个 profile、一个索引可以有很多 profile）、Vespa `rank-profile`（一个 schema 定义多个 rank profile，**查询时选**）、本项目现有 `index_profile / graph_profile / wiki_profile / config_profile` | **中高**。profile = 一组预设的"命名组合"，字段引用 profile 名而非直接展开全部参数；表达力强于纯 KV，弱于 DAG | **中**。概念少（只有"profile 名"和"字段指向它"两条），但要理解"profile 变了哪些字段会跟着变" | ① profile 漂移：改了 profile 定义，所有引用它的字段**同时变**，没有 diff 视图就是定时炸弹。② 组合爆炸：N 个 profile × M 个字段，最后没人知道哪个字段用了哪个 profile（Azure 的缓解手段是"每个 vector 字段只能一个 profile"，用基数约束压住组合）。③ 缺少"哪个 profile 是当前生效版"的显式指针 → 必须引入版本号 |

### 3.1 选型判断（给 P1 的直接结论）

**推荐：Profile 组合（L2 场景配置表） + 固定 DAG（L0 硬编码）+ 少量声明式参数（L1 env）**，**不要**做场景级可编排 DAG。

理由三条，都有出处：
1. **DAG 编排的价值在"探索期"，成本在"运维期"。** RAGFlow 自己都在给 DAG 加护栏（每类节点限一个、Checklist 校验、发布版本、测试用专用 Dataset）——这说明自由编排的代价已经大到必须用约束换回来。本项目已经有 13 个能力包 + 固定的执行链，场景差异集中在**参数**而非**拓扑**，用 DAG 是拿最高成本换用不上的表达力。
2. **Profile 组合有官方成功范式**：Vespa 的 `rank-profile` 就是"schema 定多个 profile、查询时按名选"，且 `query-profile` 还能给"调用方不可超过的上限"（`maxHits`）。这与"L2 定 profile、L4 按名选 + 上限"一一对应。
3. **本项目已有 profile 骨架**，演进成本最低；反过来把 profile 改成 DAG，等于重写。

## 四、不可配置清单（硬约束）

> 判定标准：**一旦做成配置项，两个不同取值的组合会产生"不报错的错误结果"**（静默劣化），而不是"报错的失败"。这是与"可配但会报错"的本质区别。

| # | 不可配维度 | 为什么一旦可配就静默劣化 | 一手出处 |
|---|---|---|---|
| 1 | **embedding 模型 / 维度 / 向量文本公式** | 不同模型的向量**不同构**，余弦相似度跨模型无意义。同维度也不行——`text-embedding-3-small` 与 `ada-002` 都是 1536 维，但互不可比。混用后**不抛错**，只是检索结果逐渐变得不相关，且常被误判为"rerank 不行"或"分块要重做" | RAGFlow：旧版文档明确"数据集一旦有 chunk 就不能换 embedding 模型，要换必须删掉全部 chunk"，理由是"必须保证同一数据集的文件用同一模型转成 embedding，**在同一向量空间内比较**"（`ragflow.cc/docs/configure_knowledge_base`）；新版演进为**兼容性探针**："选择不同模型将触发对抽样现有向量的兼容性检查，**向量维度必须匹配，且平均余弦相似度至少 0.9**，检查失败则恢复先前选择"（`ragflow.com.cn/docs/dataset_configuration`）。Azure AI Search："vectorizer 必须在查询时提供 embedding 转换，**它必须指向索引内容编码时使用的同一个 embedding 模型**"；`dimensions` "必须设成 embedding 模型实际生成的维数"（`learn.microsoft.com/en-us/azure/search/agentic-retrieval-how-to-create-index`、`docs.azure.cn/en-us/search/vector-store`）。Dify：**高质量索引建成后不可回退到经济索引**（`enterprise-docs.dify.ai/zh/3.7.x/.../setting-indexing-methods`） |
| 2 | **索引方式的"类别"（是否向量化）** | 经济模式（关键词倒排）与高质量模式（向量）产出的**索引结构不同**，不存在"部分向量 + 部分关键词"还能语义互搜的中间态。回退会让已有 chunk 的检索能力凭空消失 | Dify 同上（单向不可逆：经济→高质量可升级，高质量→经济不可回退） |
| 3 | **chunk 的"生成公式"标识（`embedding_text_version` / `chunker_version`）** | 公式变了但版本号没变，新旧向量会被判为同构而混检。代码无法自动感知语义变更（改了函数体输出也可能恰好相同），**必须人工 bump** | 本项目 `index_profile.py` 注释已按住此点（**已验证，且业界没有更优解**）；旁证：Elasticsearch"不能改已有字段的 mapping/type，要改只能新建索引 + reindex"（`elastic.co/docs/api/doc/elasticsearch/v8/operation/operation-indices-put-mapping-1`）——**派生数据的生成契约只能换代，不能原地改** |
| 4 | **多租户/可见性的"是否过滤"开关** | 过滤不是"优化项"而是"授权项"。做成可关的开关 = 一条配置就能让全租户数据互见，且**不报错**（返回的是别人的数据，看起来完全正常） | Qdrant："租户索引帮助存储与检索，**它不授权请求**。持有不受限凭据的客户端可以省略 filter 访问其它租户的点"；"租户身份必须**从已认证用户推导**，而不是接受请求里传来的不受限 tenant ID"（`qdrant.tech/documentation/deploy-and-scale/multitenant-search/`）。Azure AI Search："请求里的索引名**不是授权边界**……否则让请求走可信应用层，由该层**从已认证上下文推导**租户索引"（`learn.microsoft.com/en-us/azure/search/search-modeling-multitenant-saas-applications`）。pgvector RLS："若无策略适用，默认**拒绝**"（default-deny） |
| 5 | **质量守门类开关（grounding / 注入防护 / 溯源必填 / 拒答）** | 这类开关"关掉更省事、指标更好看"，一旦可配，第一个被关掉的就是它们；且关掉后系统仍然"能跑能答"，只是答案不可信 | OWASP：**fail-safe defaults**——"除非显式授权，否则默认拒绝"；"默认配置应尽可能安全，而不是尽可能好用"（`owasp.org/index.php/CLASP_Security_Principles`、`devguide.owasp.org/en/02-foundations/03-security-principles/`）。本项目 `GROUNDING_CHECK_ENABLED` 注释"MUST NOT 置 False"方向正确 |
| 6 | **执行链拓扑（步骤顺序 / 是否跳过 rerank 之外的结构性变更）** | 拓扑可变 → 两个场景的数据不可比、评估集不可复用、回归测试无法覆盖（N 场景 × M 拓扑） | Sculley et al., *Hidden Technical Debt in Machine Learning Systems*, NeurIPS 2015：**pipeline jungle**、**glue code**、**CACE（Changing Anything Changes Everything）**（`papers.nips.cc/paper/5656`）。注意 rerank **开关**属于 L2（可配），因为它不改变数据形态，只改变候选排序 |

**一句话**：可配的是「**怎么取**」（top_k、阈值、策略）、不可配的是「**算出来是什么**」（向量空间、派生公式、授权边界、质量守门）。

## 五、多租户隔离取舍表

| 方案 | 代表实现 | 隔离强度 | 成本 / 容量 | 召回与延迟影响 | 判定依据 |
|---|---|---|---|---|---|
| **一租户一库/一表** | pgvector 官方推荐做法之一（`PARTITION BY LIST(customer_id)` 或独立表）；Azure "Model 1: One index per tenant" | **最强**（物理隔离，合规最好讲） | 每个实例有基线成本；Qdrant Cloud **默认每集群最多 1000 个 collection**，一租户一 collection 很快撞顶 | **最好**（索引里只有本租户向量，ANN 遍历不被稀释） | 租户数少 × 单租户数据大 × 强合规（金融/政务）；且能接受"扩租户要扩实例" |
| **一租户一分片/一分区** | Weaviate multi-tenancy（`multiTenancyConfig.enabled=True`，**每租户独立 shard**）；Qdrant custom sharding（`shard_key_selector`） | **强**（物理隔离 + 共享基础设施） | 中等。Weaviate 的解法是把"长尾不活跃租户"降到 `INACTIVE`（仍在本地盘）/`OFFLOADED`（挪到对象存储），"让上千租户的总成本可承受" | 好 | 租户数多到"一租户一 collection 会配置爆炸"，但仍要物理隔离。Weaviate 原话：定义一次 collection，然后每客户加一个 tenant，"**你得到了隔离，但没有配置爆炸**" |
| **共享索引 + 元数据过滤** | Qdrant `is_tenant: true` 关键词索引；Azure "Model 4: One index for multiple tenants"；pgvector `WHERE tenant_id = ...` | **弱**（逻辑隔离，靠代码/DB 策略保证） | 最低 | **对 pgvector 是陷阱**：官方 README 原文"**With approximate indexes, filtering is applied after the index is scanned.** 若条件匹配 10% 行、HNSW 默认 `hnsw.ef_search=40`，平均只有 4 行会命中"——要 5 条却拿到 2 条，**不报错**。缓解：`hnsw.iterative_scan`（0.8.0+）、部分索引、分区 | 租户数很大 × 单租户数据小 × 无需物理隔离。pgvector README 对多租户直接给出结论："**For tenant isolation, use list partitioning or separate tables**"——即 pgvector 官方**不推荐**纯共享索引做租户隔离 |
| **RLS（DB 引擎级默认拒绝）** | PostgreSQL RLS：`ENABLE ROW LEVEL SECURITY` + `tenant_id = current_setting('app.tenant_id')` | **中**（在应用之外多一道闸） | 低 | **不解决召回问题**：RLS 是行可见性，**不是 ANN 遍历约束**——过滤仍在索引扫描之后发生 | 需要"应用代码写漏了也不会泄漏"的兜底。坑：**表 owner 与 BYPASSRLS 角色默认绕过策略**，需 `FORCE ROW LEVEL SECURITY`；且应用必须用单独角色连接 |

### 5.1 对本项目的判定（pgvector 已定，给出取舍结论）

**结论：短期"一租户一分区"、长期"分区 + RLS 双闸"，不要把纯 `WHERE tenant_id` 当隔离方案。**

依据链：
1. 物理约束先行——本项目向量列是 `vector(N)`，**维度和列类型由 DDL 固定**，所以"embedding 模型/维度"天然不可能按租户配（这反过来印证了第 4 节第 1 条）。
2. pgvector 官方 README 明确把「多租户」这一节写成"共享近似索引会让一个租户的向量影响另一个租户的**召回与速度**"，并直接推荐 LIST 分区或独立表（`github.com/pgvector/pgvector/blob/master/README.md`）。这条比任何二手博客都硬。
3. 若坚持共享表，必须同时做三件事：`tenant_id` B-tree/分区索引、`hnsw.iterative_scan = relaxed_order`（0.8.0+）、**默认拒绝**（权限上下文缺失时返回空，不降级为无过滤查询）。第三条与 Qdrant"从已认证用户推导租户身份"、Azure"由可信应用层推导租户索引"同源。
4. RLS 只作兜底，不作主隔离：它防"代码写漏"，不防"召回塌陷"，且 owner/BYPASSRLS 会绕过。

## 六、反面教训（每条含真实出处）

### 教训 1｜配置债：配置比代码大，评审比代码松

Sculley 等人在 NeurIPS 2015 就把 **configuration issues** 列为 ML 系统专属债之一，与 entanglement（CACE：改任何东西都改了全部）、hidden feedback loops、undeclared consumers、glue code、pipeline jungle 并列，并指出成熟系统里 ML 代码占比极小、绝大部分是周边基础设施与粘合代码。
**在 RAG 上的形态**：一个场景的"有效配置"= 分块参数 + 索引口径 + 检索参数 + 提示词 + 阈值 + 模型，**没有任何单元测试能覆盖它们的组合**；而提示词/阈值往往由不在 code review 流程里的人改。
**约束手段（有出处）**：配置**带 schema + 校验 + 版本号**（Haystack 的 pipeline YAML 声明 `dependencies: haystack-ai==2.14.0` 把版本钉死在配置里；Azure 的 index JSON 由服务端 schema 校验；Vespa 在**部署时**校验 application package 并把配置推给所有节点）。
> 出处：https://papers.nips.cc/paper/5656-hidden-technical-debt-in-machine-learning-systems ；https://docs.cloud.deepset.ai/docs/pipeline-yaml-format ；https://learn.vespa.ai/application-package-deployment/app-package

### 教训 2｜"UI 能改一切"= 影子部署系统（无版本、无评审、无回滚）

无边界后台配置的失败模式不是"改错"，是"改错了但没人知道改过"。
**业界给出的三道闸，本项目可照抄**：
1. **草稿→发布两态**：RAGFlow 明确"仅保存草稿不能作为解析方式被选中"，必须 `Publish` 生成版本（`ragflow.io/docs/v1.0.0/connect_the_pipeline_to_knowledge_base`）。
2. **乐观并发校验**：Dify 导入 DSL 时"先读草稿哈希值再带上导入；期间若有人改动草稿，**导入被拒绝**，不会覆盖对方改动"（`docs.dify.ai/zh/cli/create-and-update-apps-from-dsl-files`）——这就是本项目 `checksum` 字段的出处级依据。
3. **不可信配置直接拒绝加载**：Haystack 反序列化走 **trusted-module allowlist**，"引用白名单外模块的 pipeline 会**加载失败**，直到你显式扩展白名单"；即使 `builtins` 在白名单内，`eval/exec/compile/import/open/getattr` 也**被 block**；还会校验嵌套 `init_parameters` 的 key 是否属于父类构造签名，"把走私类塞进无用参数槽"会在 import 前被拒（`docs.haystack.deepset.ai/docs/serialization`）。
> 这就是"fail-closed"在配置加载层的标准实现：**能加载的一定是已声明过的，加载不了就是错，不是警告。**

### 教训 3｜发布新版本 ≠ 已生效 ≠ 已回溯（配置漂移的真实形态）

这是最容易骗过测试的一类：**你改了、也发布了、生产行为没变**。
RAGFlow 三处明确的"不自动"：
- 数据集**保留它当时选的那个管线版本**，"当发布另一个版本时，数据集保持其当前选择的版本"；要生效得手动重选 + 重新解析。
- "现有 chunk **不会**自动重新生成。"
- 自动元数据设置"**仅对后续新解析的文档生效**，不会自动更新已完成解析的文档"。
Dify 同样：改 CompilationTemplate 后"已完成的文档**不会**自动重编"。
**结论**：配置表必须有 `needs_reindex` 视图，把"配置版本 × 数据代次"的不匹配显式暴露成待办，而不是靠人记。本项目 `IndexProfile.chunker_version` 目前正是"只作提示不硬过滤"，方向对，但需要一个可查询的"过期 chunk 数量"出口。
> 出处：https://ragflow.io/docs/v1.0.0/dataset_configuration ；https://ragflow.io/docs/v1.0.0-rc3/knowledge_compilation/apply_knowledge_compilation_template

### 教训 4｜配置里塞环境相关物理 ID → 跨环境必然断链

Dify 导出 DSL 时**不带**关联知识库，跨 workspace/服务器导入后"每个知识检索节点都会丢失关联的知识库"，补救办法是手工把 `dataset_ids` 换成目标环境的知识库 ID。
**规则**：场景配置里只允许出现**逻辑键**（`scenario_key`、`kb_logical_id`），物理 ID 在导入时由环境映射表解析。物理 ID 进配置，等于把"能不能跑"绑死在某个环境上。
> 出处：https://docs.dify.ai/zh/cli/create-and-update-apps-from-dsl-files ；https://docs.dify.ai/en/self-host/use-dify/workspace/export-import-apps

### 教训 5｜"便捷默认值"比"显式报错"危险得多

缺失字段回落成"方便但危险"的默认（无限重试、无超时、过宽 CORS、debug 日志开），配置错误就**不 fail-fast 而是 fail-slow**，等压测或事故才暴露。
工程实践总结出的 8 条同类反模式中还包含：环境漂移当特性、feature flag 变永久控制面（有效运行状态数爆炸、测试组合爆炸）、字符串无 schema（ms 与 s 混用）、secret 与非 secret 混放、**隐藏的优先级/多层覆写**（同一个值来自 env、多份文件、远端配置、运行时 flag，没人能预测实际生效值）。
**约束手段**：单一"已解析配置（resolved config）"视图 + **provenance**（每个值来自哪一层）+ 启动时打印有效配置并标风险位。本项目 `runtime_config_snapshot()` 已经是这个"单一取值入口 + 脱敏快照"的雏形，**建议再加一列 provenance**（`env` / `scenario` / `tenant` / `request`）。
> 出处（工程博客，非一手厂商文档，仅作补充）：https://technori.com/?p=23986 ；安全侧的官方依据见 OWASP secure-by-default / fail-safe（见第 4 节第 5 条）

## 七、对本项目的 3 条直接建议（供 P1 架构师参考，不展开设计）

1. **把"场景"建成一张带版本的表，而不是一组环境变量前缀**：`scenario_profile(scenario_key, version, status, ..., index_fingerprint, config_fingerprint, checksum)`，发布后不可改、只能发新版本，`checksum` 用于保存时的乐观并发；`index_fingerprint` 不匹配的数据**拒绝检索**而不是降级。现有 `decisions.py`（L0）/`settings.py`（L1）不动，`index_profile` 直接复用为 L2 的指纹生成器。

2. **执行链拓扑写死，场景只配参数**：不做场景级 DAG。`recall_top_k / rerank_top_k / 阈值 / 是否混合检索 / 是否开 graph-wiki / 分块参数`进 L2；`embedding 模型+维度+文本公式`、`授权/可见性是否过滤`、`grounding/注入防护开关`、`阈值语义`锁在 L0/L1，且后者一旦被尝试配置应**报错拒绝**而不是忽略。L4 请求级只允许在 L2 给定区间内覆写，越界拒绝并落 audit。

3. **多租户从一开始就按"分区 + RLS 兜底"设计，不要先上 `WHERE tenant_id`**：`chunks` 按 `tenant_id` LIST 分区（或按租户分表），RLS 用 `FORCE ROW LEVEL SECURITY` + 独立应用角色作第二道闸；租户身份只从认证上下文推导，绝不接受请求体传入的 tenant_id；同时把 `multi_tenant` 从全局 bool 演进为 L1 能力开关 + L3 租户行（含配额与场景版本钉定）。
