## 被验证有效的模式

- **派生数据与新数据写同一事务**。清理旧派生结果（图/索引/缓存行）必须与主数据的删除写入同处一个事务，否则中途失败会留下指向已删行（`chunk_id`）的孤儿记录。触发场景：任何「重解析后重算派生层」的流程。
- **重抽先删后写，不靠 upsert 合并**。`ON CONFLICT` 只更新命中的行，清不掉「新结果里不再出现」的旧行。触发场景：实体抽取、标签重算、向量重算。
- **关闭态等价 = 探针定位 + 评测定论**。探针能证明「没走到那段代码」，证明不了行为等价；必须跑既有评测集拿到四项指标逐项相同。触发场景：任何默认关闭的新能力上线前。
- **迁移与 ORM 对拍要成测试**。把「索引名 / 唯一约束 / 生成列 / 列顺序」写成断言，比人工核对可靠；本机无 DB 时也至少能在有 DB 的环境一键复跑。触发场景：新增表或改列类型。
- **白名单键名要有测试钉住**。凡是靠字符串键从配置里取子集的逻辑（指纹、快照、导出），拼错键会静默少算一项，且不报错。触发场景：配置指纹、审计快照、报表字段。

## 反模式（踩过的坑）

- **拿全量配置算跨角色指纹**。角色专属字段（worker 没有重排端点）会让两侧指纹永久不同，检查变成假警；假警多了运维就学会忽略，真正的漂移也没人看。应当按「两侧取不同值会导致行为不可解释」筛字段。
- **只改 prod 编排不加 dev 编排**。同一份代码在两套编排下行为分裂：dev 设了变量不生效，prod 生效。凡是新增环境变量，api/worker × dev/prod 四处都要过一遍。
- **`except Exception` 吞掉「跳过」类异常**。跳过（零输入/超出上限）与失败（上游报错）混在一个分支里，状态会被记成失败，而重跑逻辑往往只排除「跳过」→ 该条被每轮重选、永远修不好。
- **用 `docker info` 判 Docker 是否可用**。它走的是 Docker Desktop 的命名管道，容器已经起来时也可能失败；判活要用 `docker ps`。
- **测试里用 stub 绕过被测的检查顺序**。stub 掉依赖会让「先报哪个错」这类顺序断言失效，测出来是假通过；该造真实依赖缺失的场景就造。
- **改了源码只重启容器**。镜像内没有源码挂载时，重启等于跑旧代码，而且接口照常返回成功——静默失败。改代码必须重建镜像，且 api 与 worker 两侧同 tag 一起重建。

## 个人偏好

- 文档与注释用中文；注释写「为什么这么定」，不写「这里做了什么」。
- 交付前不要自行 `git commit`；把工作区留给管家节点确认。
- 报告里凡引用数字，必须能给出复算方式（命令 + 输出），不接受「看起来合理」的估算。
